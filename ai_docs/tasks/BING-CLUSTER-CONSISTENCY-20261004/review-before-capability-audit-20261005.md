- [ ] **数据库回滚不清除内存副作用（本轮新增，对应FIX-006/013）**：保存点只恢复数据库，不自动恢复EF跟踪状态、FreeSQL实体变更回调、ITransactionActionManager登记或CAP内存发送缓冲。基础有序工厂尚未自动绑定CAP；后续同事务发布适配须测试回滚业务后提交失败标记不会Flush已回滚业务的消息，失败上下文应丢弃。此处为尚未验收的组合边界，不宣称当前已发生消息泄漏。
- [ ] **失败标记提交的诊断语义（本轮新增，对应FIX-012/013）**：候选业务异常在保存点回滚后提交失败标记，异常TransactionOutcome可为Committed，同时BusinessRolledBack=true。它表示外层物理事务提交，不表示业务成功。指南和测试映射已说明物理Committed与业务失败的区别；仍需宿主恢复示例和消费者实际处理这一诊断。标记提交确认丢失应为Unknown，先查询持久状态。
- [ ] **只读存储不等于无争锁的诊断入口（本轮新增，对应FIX-006/012）**：Coordinator.GetStateAsync仍调用同一写业务事务工厂；EFCore工厂使用默认BeginTransactionAsync，FreeSQL调用GetOrBeginTransaction。SQLite测试必须显式使用deferred事务，说明普通SELECT不能单独证明整个入口无写锁；MySQL Serializable及长期快照也有隔离限制。需直接验证真实工厂下的诊断并发/等待和取消，并定义只读观测事务策略，不宣传无条件无锁或总是最新。

- [ ] **重试预算与过载放大（本轮新增，对应FIX-006/012）**：最新入箱最多4次总尝试，间隔20/40/80毫秒；还需验证高竞争下的成功率、总延迟与取消，结合CAP重投策略约束总体放大。当前只处理1213，不自动重做业务回调、1205、清理失败或Unknown结果；不能泛化为全部事务的重试能力。
- [ ] **驱动与故障证据边界（本轮新增，对应FIX-006/013）**：谓词按实际驱动全名及Number识别，七项新测试使用MySqlConnector的原生SIGNAL错误形状注入；尚未运行，也不能代替真实InnoDB竞争重跑。MySql.Data分支没有对应直接证据；原生SIGNAL在Commit阶段抛错不能证明真实提交确认丢失。
