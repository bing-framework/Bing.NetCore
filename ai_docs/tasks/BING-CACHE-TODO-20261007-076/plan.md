# BING-CACHE-TODO-20261007-076：EasyCaching 分片清理首错快速取消

## 目标

修正 `ShardedRedisCacheManager.RunShardScansAsync` 的失败响应。当前每个并发窗口通过 `Task.WhenAll` 等待所有分片任务完成，只有窗口全部结束后才取消链接令牌；首个分片失败时，其他已经派发的扫描/删除仍可能继续运行，取消响应和资源释放滞后。

## 设计

- 保持 `MaxConcurrency` 分窗、共享 `CacheScanBudget`、分片完成/失败诊断和 `RunScanAsync` 的拓扑校验。
- 窗口内改为按任务完成顺序观察：成功任务继续等待，首个失败或取消的任务立即取消链接令牌，然后观察其余已派发任务并传播首个可观察异常。
- 调度器不再派发后续窗口；已经发出的 Redis 命令不承诺撤回，但底层扫描应收到链接取消令牌并停止后续命令。
- 调用方主动取消仍传播 `OperationCanceledException`；底层业务异常仍优先保留，不吞掉或改写为成功。
- 不改变同步清理 API、Hybrid 总线顺序、跨分片事务语义或公共接口。

## 测试

- 为模式删除失败用例增加对第二个已派发分片令牌的取消观察，证明首错发生后不必等第二个任务自然结束才取消。
- 保留前缀/模式/Clear 有界并发、取消停止派发和异常传播回归。
- 运行 L0、清理精准测试、EasyCaching 双 TFM 完整单元和生产 netstandard2.0 构建；分片实机门控继续按外部环境分类。

## 验收

- 首个任务失败后，已派发的其他任务在其仍未完成时收到取消信号。
- 首个异常对象仍由公共异步 API 传播；已派发任务均被观察，不产生未观察异常。
- 调度上限、共享预算和成功路径行为不回退。
