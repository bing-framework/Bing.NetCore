# 文件管理：管理页面与历史治理增强

Task ID：20261024-file-storage-design。用户授权继续实施后续增强；按 create-plan → execute-plan 执行。此前计划、执行及独立审查保存在 evidence/governance/before-*.md，根 review.md 保留。

## 目标与设计

现有两 ORM、两 Admin、可续传上传、用户资料附件、任务恢复、迁移批次及生命周期审计继续复用。本轮完成可操作的管理页面、消费者级 Outbox 确认及管理重放、历史记录的预览归档和恢复。

1. 消费者回执以 EventId + Consumer 唯一。首次投递冻结消费者名单；重试跳过已确认消费者。每个消费者独立超时、次数及下次重试时间，默认最多 8 次；耗尽后等待人工重放。移除消费者不会把未确认事件自动标为成功。新消费者不会自动订阅已冻结历史事件。
2. 每次回执提交使用事件版本和有效租约 CAS，回执与聚合状态在同一短事务内更新；事件 ID 不变，仍保持至少一次语义，消费者必须幂等。管理重放明确指定消费者、事件版本、请求 GUID 和原因，拒绝活动租约；支持重复请求返回原结果并原子记录管理审计。
3. 增加三张表：FileEventDelivery、FileGovernanceAudit、FileHistoryArchive。两个 ORM 统一契约；提供 SQLite/MySQL 独立增量升级脚本，不改旧脚本的升级起点，也不自动运行生产迁移。
4. 历史治理范围为成功任务、已全部投递事件、已完成迁移批次。默认保留 90 天，最小 7 天。预览按数据库条件排序限量，执行只处理预览中的 ID 和版本并重新校验终态、时间、无活动租约；任一冲突整批回滚。HTTP 预览凭据经 DataProtection 签名，绑定范围、操作者和 15 分钟期限。逻辑归档保留原始元数据、幂等键、回执、审计链及文件内容；默认管理列表隐藏匹配版本的标记，详情和归档列表仍可查看。恢复和事件重放清除标记。物理清除和冷库压缩不属于本轮，逻辑归档不宣称回收磁盘。
5. 文件管理页面由 Web 模块嵌入共享资源提供，两 Admin 和 Demo 共用；显式配置开启。页面支持上传续传、文件查询/下载/删除/业务关联、任务查询恢复、迁移批次控制、事件回执与重放、历史预览归档恢复。复用既有上传脚本，令牌仅在页面内存保存，文本通过 textContent 渲染。所有实际 API 继续执行身份、范围与 files.manage 校验；页面本身不授予权限。

## 实施顺序

| 任务 | 实现 | 验收 |
|---|---|---|
| GOV-01 | 冻结模型和仓储契约；两 ORM 事务、映射及增量 SQL | 两套 SQLite 真实 IO、建表/升级、版本冲突、租约隔离 |
| GOV-02 | 消费者投递、重试上限、事件查询/重放/审计 API | 成功消费者不重复、失败独立重试、重启持久化、幂等和跨范围拒绝 |
| GOV-03 | 历史预览、事务归档、列表及恢复 | 活动记录排除、版本变化回滚、重复执行、审计和恢复 |
| GOV-04 | 共享管理页面、配置、两宿主/Demo 接入 | 实际 HTTP 与浏览器上传、查询、管理操作和错误反馈 |
| GOV-05 | 受影响回归、部署说明、符号映射与 execution | net6/net8 业务矩阵、两 Admin 编译及相关接线测试、task-finish |

主代理负责架构、业务/API/UI、集成与验收；luna_worker 在明确契约后负责两 ORM 持久化及增量脚本。不得覆盖已有修改；所有读写 UTF-8；不提交/推送，不迁移真实业务数据。
