# 术语表（Glossary）

> **适用版本**：框架 `7.0.0`（`version.props`）｜ 目标框架：类库 `netstandard2.0`、Web / 应用 `net6.0`｜ 内容核对：2026-09-18｜ 版本历史见 [发行说明](../ReleaseNotes.md)

> **一句话定位**：本框架自造词与重载词很多——「存储」不是「仓储」、`IStore` 与 `IRepository` **并存且约束不同**、`Level` 不管依赖顺序、`AddMySqlUnitOfWork` 有两个同名不同义的版本。本文把这些词一次讲清，读任何一份文档卡住时回来查。
>
> 格式：**术语 | 对应类型/英文 | 它到底是什么 | 详见**。所有类型名均取自源码，若与源码冲突请信任源码。

## 1. 模块与启动

| 术语 | 类型 / 英文 | 说明 | 详见 |
| --- | --- | --- | --- |
| **模块** | `IBingModule` / `BingModule` | 一个可插拔的装配单元。实现 `ConfigureServices` 注册服务、`Initialize` 做启动后初始化。框架自己的每个能力包基本都以模块形式提供 | [架构文档 §8](../architecture/架构文档.md) |
| **模块依赖** | `[DependsOnModule]` | **递归**声明「我依赖哪些模块」。作用只有**包含**——保证被依赖模块一定会被加载 | 架构文档 §8 |
| **模块级别** | `ModuleLevel`（`Core=1` / `Framework=10` / `Application=20` / `Business=30`） | 决定模块的**加载顺序**。排序规则只有 `Level → Order → FullName`，**与 `[DependsOnModule]` 无关** | 架构文档 §8 |
| **`AddBing()`** | `IBingBuilder` 扩展 | 模块注册入口。**挂在 `IBingBuilder` 上，不是 `IServiceCollection`**——`services.AddBing().AddModule<T>()` | 架构文档 §12 |
| **`UseBing()`** | Web 宿主扩展 | 触发模块初始化。Web 用 `app.UseBing()`；非 Web（控制台/WinForm）用 `serviceProvider.UseBing()` | 架构文档 §8 |
| **`IBingBuilder`** | — | `AddBing()` 返回的建造器。`AddModule<T>()` 是它的方法，不要在 `IServiceCollection` 上找 | 架构文档 §8 |

> ⚠ **最常见的误解**：以为 `[DependsOnModule]` 能控制初始化顺序。不能。它只保证「被依赖者会被加载」，真正决定顺序的是 `ModuleLevel`。想让 A 在 B 之后初始化，只能给它们不同的 `Level` 或 `Order`。

## 2. 依赖注入

| 术语 | 类型 / 英文 | 说明 | 详见 |
| --- | --- | --- | --- |
| **约定式 DI** | Conventional DI | 不用手写 `services.AddXxx()`，靠实现标记接口/打特性自动注册 | 架构文档 §9 |
| **生命周期标记接口** | `ISingletonDependency` / `IScopedDependency` / `ITransientDependency` | 实现即按对应生命周期自动注册 | 架构文档 §9 |
| **`[Dependency]`** | `DependencyAttribute` | 显式指定 `Lifetime` / `TryAdd` / `ReplaceExisting` / `AddSelf`。**特性优先级高于接口** | 架构文档 §9 |
| **`AddSelf`** | — | 除注册接口外，**额外把实现类自身也注册一份**（`services.AddScoped<MyImpl>()`）。默认关闭 | 架构文档 §9 |
| **`TryAdd`** | — | 已存在同服务注册时**跳过**，不覆盖 | 架构文档 §9 |
| **`ReplaceExisting`** | — | **覆盖**已存在的同服务注册 | 架构文档 §9 |
| **`[IgnoreDependency]`** | — | 排除在约定扫描之外 | 架构文档 §9 |
| **注册全部接口** | — | 约定式 DI 会把一个类的**所有**实现的接口都注册进去（不是只注册第一个） | 架构文档 §9 |

> ⚠ 一个类同时实现多个接口时，约定式 DI 会给每个接口各注册一份，指向同一实现。若你只想要其中一个，用 `[IgnoreDependency]` 排除或改用显式注册。

## 5. 事件与消息

> **框架里有四套事件机制**，互不相通：进程内事件（`ISimpleEventBus`）、CAP 集成事件（`IMessageEventBus`）、DDD 领域事件（`DomainEvent`）、遗留总线（`Bing.EventBus*`）。完整对照见 **[事件与消息文档](../architecture/事件与消息文档.md)**。

| 术语 | 类型 / 英文 | 说明 | 详见 |
| --- | --- | --- | --- |
| **简单事件总线** | `ISimpleEventBus`（继承 `IEventBus`） | **进程内**、本地的事件分发，不跨服务。处理器从 DI 解析、串行 `await`、**无事务**。⚠ 注册入口 `AddDefaultEventBus()` **全仓无调用者** | [事件与消息文档 §3](../architecture/事件与消息文档.md) |
| **消息事件总线** | `IMessageEventBus` | **跨服务**的消息发布，底层走 CAP | [事件与消息文档 §4](../architecture/事件与消息文档.md) |
| **领域事件** | `DomainEvent` + `IDomainEventDispatcher` | DDD 的聚合根事件。由 `BasicAggregateRoot.AddDomainEvent` 收集。⛔ **当前不会被派发**（`DispatchAsync` 生产代码零调用） | [事件与消息文档 §5](../architecture/事件与消息文档.md) |
| **组合总线** | `Bing.Events.Cap.EventBus` | 实现 `IEventBus`：发布时**先走 `ISimpleEventBus`**，若事件是 `IMessageEvent` **再走 `IMessageEventBus`**。所以用 `IEventBus` 发消息会**同时触发本地处理器** | [事件与消息文档 §4.3](../architecture/事件与消息文档.md) |
| **Outbox（发件箱）** | `cap.published` / `cap.received` | 把待发消息与业务数据**同库同事务**落表，再由 CAP 异步投递，保证「业务成功则消息必发」。⚠ **仅当 `Send=false` 且后续确有 UoW 提交时才成立**，否则静默丢弃 | [事件与消息文档 §4.4](../architecture/事件与消息文档.md) |
| **`Send` 属性** | `IMessageEvent.Send` | `true` = 立即发；`false` = **延迟到事务提交时发**（Outbox） | 事件与消息文档 §4.4 |
| **`[EventHandler]`** | `EventHandlerAttribute : TopicAttribute` | 订阅端特性，**继承 CAP 的 `TopicAttribute`**。与 `[CapSubscribe]` 在 CAP 眼里**等价** | [事件与消息文档 §4.7](../architecture/事件与消息文档.md) |
| **`ICapSubscribe`** | — | CAP 订阅者标记接口，与 `[EventHandler]` 配合使用 | 事件与消息文档 §4.7 |

> ⚠ **`IEventBus` / `IMessageEventBus` / `IEvent` / `IEventHandler` 都有两套同名类型**：`Bing.EventBus`（遗留，零生产引用）与 `Bing.Events`（现行）。同时 `using` 两个命名空间会导致**歧义编译失败**（CS0104）。新代码一律用 `Bing.Events` 那套。
>
> 还有一层更隐蔽的：`Bing.EventBus` 与 `Bing.EventBus.Abstractions` 两个**程序集**定义了**完全相同的全限定类型名**，同时引用会 CS0433（所幸后者零引用）。

## 8. 易混词辨析

### 8.1 `IStore` 与 `IRepository`（⚠ 两个都存在）

**框架里 `IStore` 和 `IRepository` 都有**，且在同一个工程 `Bing.Ddd.Domain`。它们不是"谁替代谁"，而是**泛型约束范围不同**：

| | `IStore<TEntity, TKey>` | `IRepository<TEntity, TKey>` |
| --- | --- | --- |
| 位置 | `Bing/Domain/Data/IStore.cs` | `Bing/Domain/Repositories/IRepository.cs:37` |
| 实体约束 | 无（`where TEntity : class`） | **`IAggregateRoot, IKey<TKey>`** |
| 继承关系 | 根接口 | **`IRepository` + `IQueryRepository<TEntity,TKey>` + `IStore<TEntity,TKey>`** —— 是 `IStore` 的**超集** |
| 额外成员 | — | `IUnitOfWork GetUnitOfWork()`（`IRepository.cs:18`） |

**怎么选**：

- 实体是**聚合根** → 两者都能注入；用 `IRepository` 会多拿到 `GetUnitOfWork()` 与 `IQueryRepository` 的语义。
- 实体**不是**聚合根（普通实体 / 子实体） → 只能用 `IStore`；`IRepository` 的泛型约束会编译不过。

> ⚠ 判读实现用途请**看基类而不是看名字**：返回值形态仍是 `StoreBase` 系，而基类家族里又保留了 `CompactRepositoryBase`、`TreeRepositoryBase` 这类"Repository"命名（历史原因）。

### 8.2 工作单元 ≠ 数据库事务

`IUnitOfWork` 是**业务一致性边界**（一次请求一个），它在提交时开启数据库事务。但：

- 跨**三支 ORM** 不共享事务（EF 的事务与 Bing.Data.Sql 的 `ISqlTransactionScope` 是两条链路）；
- 跨库一致性请用 CAP 事件最终一致，不要指望分布式事务。

### 8.3 简单事件 vs 消息事件 vs 领域事件

三个都在"发事件"，但**完全不是一回事**：

| | 简单事件 | 消息事件 | 领域事件 |
| --- | --- | --- | --- |
| 契约 | `ISimpleEventBus` | `IMessageEventBus` | `DomainEvent` + `IDomainEventDispatcher` |
| 范围 | 同进程 | **跨服务**（CAP） | 同聚合根 → 期望进程内 |
| 持久化 | 无 | Outbox 表 | 无 |
| 状态 | 已实现，无调用者 | ✅ 现行 | ⛔ **不会被派发** |

**别混用**：本地事件用错成消息事件，会凭空多一次数据库写入 + 消息投递。

⚠ **最容易搞错的一处**：领域事件**不实现** `Bing.Events.IEvent`，也**不经过**任何事件总线——它有自己的派发器（`IDomainEventDispatcher`）。"两级发布"这个词描述的是 `Bing.Events.Cap.EventBus` 的组合行为（先本地、若为 `IMessageEvent` 再发 CAP），**不是**领域事件的行为。

### 8.4 模块 `Level` vs `[DependsOnModule]`

`[DependsOnModule]` 管**是否加载**，`ModuleLevel` 管**何时加载**。二者正交。

### 8.5 软删除过滤器 vs `IDataFilter`

前者是「查询自动加 `IsDeleted = false`」；后者是「本次查询临时把它关掉」。

### 8.6 两个 `AddMySqlUnitOfWork`

| 命名空间 | 属于 |
| --- | --- |
| `Bing.Datas.EntityFramework.MySql` | EF Core 支 |
| `Bing.FreeSQL` | FreeSQL 支 |

签名也不同。同时引用的后果见 [能力矩阵 §4.2](能力矩阵.md)。
