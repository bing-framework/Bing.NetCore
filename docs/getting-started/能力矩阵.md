# 数据访问能力矩阵

> **适用版本**：框架 `7.0.0`（`version.props`）｜ 目标框架：类库 `netstandard2.0`、Web / 应用 `net6.0`｜ 内容核对：2026-09-18｜ 版本历史见 [发行说明](../ReleaseNotes.md)

> **一句话定位**：用一张表回答「三种 ORM 我该选哪个」。本文只讲**能力边界与选型**，安装与代码示例见 [使用文档](使用文档.md)、代码级解析见 [子系统深挖](../architecture/子系统深挖.md)、分层结构见 [架构文档](../architecture/架构文档.md)。
>
> **数据以源码为准**：本文每一格都来自 `.csproj` / 注册入口 / 过滤器实现的实际读取，最后核对于 `version.props` 7.0.0 版本。若源码变了而本文没变，请信任源码并回来修正本文。

## 1. 三十秒选型

```
你要写业务系统的主要 CRUD？
├─ 是 → 需要数据库迁移 / 需要 Oracle、Sqlite？
│        ├─ 是 → 【EF Core】唯一提供迁移的一支，5 个 Provider 全覆盖
│        └─ 否，只用 MySQL → 【FreeSQL】或【EF Core】都行
│                             ⚠ FreeSQL 没有迁移、异步查询会退化成同步（见 §4.3）
└─ 否，我要的是报表 / 复杂查询 / 批量写入 / 跨库 Join / 存储过程
         → 【Bing.Data.Sql + Dapper】
           ⚠ 它不提供工作单元与仓储，是「SQL 构建器 + 执行器」，不是 ORM
```

**一句话总结三支**：

| 支 | 本质 | 选它的理由 | 别选它的理由 |
| --- | --- | --- | --- |
| **EF Core** | 完整 ORM | 唯一支持迁移；能力最全（软删除/审计/乐观锁全都有） | `net6.0` 起步；无批量写入（Bulk）扩展 |
| **FreeSQL** | 完整 ORM（仅 MySQL） | `netstandard2.0`，能喂给老工程；审计与乐观锁开箱可用 | **只有 MySQL**；**无迁移**；**异步查询是占位实现** |
| **Bing.Data.Sql + Dapper** | SQL 构建器 + 执行器 | Lambda 条件、批量写入、跨库查询、存储过程、原生 SQL | **没有 `IUnitOfWork`、没有 `IStore`、没有审计、没有乐观锁** |

> ⚠ 最容易犯的错：以为「装了 Bing.Data.Sql 就有仓储」。它没有。它是一个**查询构建器**，需要领域层能力请走 EF Core / FreeSQL 支。

## 3. EF Core 支（推荐默认）

### 3.1 工程与 Provider

| 工程 | 数据库 | EF Core 包 |
| --- | --- | --- |
| `Bing.EntityFrameworkCore` | 核心（无 Provider） | `Microsoft.EntityFrameworkCore` 6.0.* |
| `Bing.EntityFrameworkCore.SqlServer` | SqlServer | `Microsoft.EntityFrameworkCore.SqlServer` |
| `Bing.EntityFrameworkCore.MySql` | MySql | `Pomelo.EntityFrameworkCore.MySql` |
| `Bing.EntityFrameworkCore.PostgreSql` | PostgreSQL | `Npgsql.EntityFrameworkCore.PostgreSQL` |
| `Bing.EntityFrameworkCore.Oracle` | Oracle | `Oracle.EntityFrameworkCore` **6.21.90**（硬编码版本） |
| `Bing.EntityFrameworkCore.Sqlite` | Sqlite | `Microsoft.EntityFrameworkCore.Sqlite` |

### 3.2 注册入口

五个 Provider 的入口**名字不对称**，照抄会编译不过：

| 数据库 | 方法 | 命名空间 |
| --- | --- | --- |
| SqlServer | `AddSqlServerUnitOfWork` | `Bing.Datas.EntityFramework.SqlServer` |
| MySql | `AddMySqlUnitOfWork` | `Bing.Datas.EntityFramework.MySql` |
| PostgreSQL | **`AddPgSqlUnitOfWork`** | `Bing.Datas.EntityFramework.PgSql` |
| Oracle | `AddOracleUnitOfWork` | `Bing.Datas.EntityFramework.Oracle` |
| Sqlite | `AddSqliteUnitOfWork` | `Bing.Datas.EntityFramework.Sqlite` |

> ⚠ **PostgreSQL 是 `AddPgSqlUnitOfWork`，不是 `AddPostgreSqlUnitOfWork`**——工程目录叫 `PostgreSql`，命名空间却叫 `PgSql`。这是本框架最容易踩的命名坑之一。

每个入口有两个重载（`DbConnection` 版 / 连接字符串版），泛型约束为 `TService : class, IUnitOfWork`、`TImplementation : UnitOfWorkBase, TService`。

### 3.3 能力实现位置

| 能力 | 实现位置 |
| --- | --- |
| 工作单元 | `UnitOfWorkBase : DbContext, IUnitOfWork, IDatabase`，构造时注册进 `IUnitOfWorkManager` |
| 存储 | `StoreBase<TEntity>` / `StoreBase<TEntity,TKey>`（**接口叫 `IStore` 不叫 `IRepository`**）；另有 `CompactRepositoryBase`、`TreeRepositoryBase` |
| 软删除 | `ModelBuilderExtensions` 对所有 `ISoftDelete` 实体加 `HasQueryFilter(IsDeleted == false)`；`StoreBase` 删除时置 `IsDeleted = true` |
| 审计 | `UnitOfWorkBase.AuditPropertySetter`，`SaveChanges` 时填充创建/修改/删除审计字段 |
| 乐观锁 | `MapBase.MapVersion` 对 `IVersion.Version` 调 `.IsConcurrencyToken()`；捕获 `DbUpdateConcurrencyException` 转 `ConcurrencyException` |
| 迁移 | `MigrationService.Migrate(...)` 调用 `dotnet ef database update`；`MigrationModuleBase<TDbContext>` 负责种子数据 |

### 3.4 两个缺口

- **无批量写入扩展**：全目录未引用 `BulkInsert` / `ExecuteDelete` / `ExecuteUpdate` / `Z.EntityFramework`。大批量写入请走 Bing.Data.Sql 支，或自行引入第三方扩展。
- **多租户需重写 `CreateFilterExpression`**：⚠ **自定义过滤器不会被自动套用**。`UnitOfWorkBase.ConfigureGlobalFilters` 的开关是 `FilterManager.IsEntityEnabled<TEntity>()`，而该方法**硬编码只查 `ISoftDelete` 过滤器**（`FilterManager.cs:90-94`）；内置生效的也只有软删除（`CreateFilterExpression` 默认只返回软删除表达式）。
  要做多租户，请在自己的 `UnitOfWorkBase` 子类里**重写 `protected virtual Expression<Func<TEntity, bool>> CreateFilterExpression<TEntity>()`**，把租户条件与 `base.CreateFilterExpression<TEntity>()` 的结果组合后返回。完整代码见 [recipes 多租户配方](../guides/recipes/multi-tenancy.md)。

## 4. FreeSQL 支（仅 MySQL）

### 4.1 工程

| 工程 | 说明 |
| --- | --- |
| `Bing.FreeSQL` | 核心，`netstandard2.0`，FreeSql 3.2.* + `FreeSql.Provider.MySqlConnector` |
| `Bing.FreeSQL.MySql` | MySQL Provider + 注册入口 |

### 4.2 注册入口

```csharp
services.AddMySqlUnitOfWork<TUnitOfWork, TUnitOfWorkImplementation>(
    connection,
    (provider, builder) => { /* FreeSqlBuilder 配置 */ },
    (provider, freeSql) => { /* IFreeSql 配置 */ });
```

命名空间 **`Bing.FreeSQL`**。

> ⚠ **同名不同签名陷阱**：EF Core 支也有一个 `AddMySqlUnitOfWork`，但在命名空间 `Bing.Datas.EntityFramework.MySql`，且签名不同（带 `DataConfig` / `DbContextOptionsBuilder`）。两个 using 同时存在时请写全命名空间，否则重载解析会失败或选错实现。

### 4.3 ⚠ 异步查询是占位实现

`FreeSqlAsyncQueryableProvider.CanExecute<T>()` **直接 `return false`**，其余约 40 个异步方法（`ToListAsync` / `FirstOrDefaultAsync` / `CountAsync` / `SumAsync` …）全部 `throw new NotImplementedException()`。

这**不会**导致运行时抛异常——`AsyncQueryableExecuter.FindProvider` 找不到可用 Provider 时会退化为同步执行：

```csharp
// Bing.Core/Bing/Linq/AsyncQueryableExecuter.cs
var provider = FindProvider(queryable);
return provider != null
    ? provider.ToListAsync(queryable, cancellationToken)
    : Task.FromResult(queryable.ToList());   // ← 同步阻塞
```

**后果**：对 `IQueryable` 调异步扩展方法时，代码能跑，但**会在调用线程上同步执行数据库查询**——在 ASP.NET Core 里等于白白占用一个线程池线程，高并发下会拖垮吞吐。

**建议**：
- 高频路径改用仓储自带的异步方法（它们走 FreeSql 原生异步，不经过 `IAsyncQueryableProvider`）；
- 或者干脆选 EF Core 支（其 `EfCoreAsyncQueryableProvider` 是真异步）。

### 4.4 其它缺口

- **无迁移**：未发现 `Migrate()` / `SyncStructure()` 调用，只有 `CodeFirst.GetTableByEntity` 读元数据。表结构变更需自行处理。
- **无多租户过滤**：FreeSQL 支没有任何租户相关 `GlobalFilter`。

## 5. Bing.Data.Sql + Dapper 支（查询/批量场景）

### 5.1 工程

| 工程 | 数据库 | TFM |
| --- | --- | --- |
| `Bing.Data.Sql` | SQL 构建器内核 | `netstandard2.0` |
| `Bing.Data.Sql.Analyzers` | Roslyn 分析器（`BINGSQL002` 注入防护） | `netstandard2.0` |
| `Bing.Dapper.Core` | Dapper 2.1.28 执行内核 | `netstandard2.0` |
| `Bing.Dapper.SqlServer` | SqlServer | `netstandard2.0` |
| `Bing.Dapper.MySql` | MySql | `netstandard2.0` |
| `Bing.Dapper.PostgreSql` | PostgreSQL | `netstandard2.0` |
| `Bing.Dapper.Sqlite` | Sqlite | `netstandard2.0` |
| `Bing.Dapper.Oracle` | Oracle | **`netstandard2.1`** |

> 工程名是 `Bing.Dapper.*`，**不是** `Bing.Datas.Dapper.*`。

### 5.2 Provider Key 映射

映射表在 `Bing.Dapper.Core` 的 `DefaultSqlProviderResolver`，**只有 5 个 key**：

| Provider Key | 实现类 |
| --- | --- |
| `bing.sqlserver` | `SqlServerSqlProvider` |
| `bing.mysql` | `MySqlSqlProvider` |
| `bing.postgresql` | `PostgreSqlSqlProvider` |
| `bing.oracle` | `OracleSqlProvider` |
| `bing.sqlite` | `SqliteSqlProvider` |

**Doris 不是第 6 个 Provider**，而是把 `[DatabaseType.Doris]` 映射到 `"bing.mysql"` 同一个 key，再由 `ValidateDatabaseType` 开一个白名单例外放行。因此：

```csharp
// Doris 会自动被标记为只读、不支持事务
IsReadOnly = true;
SupportsTransactions = false;
```

### 5.3 注册入口

这一支**没有 `AddXxxUnitOfWork`**，入口是 `AddXxxProvider()`：

| 方法 | 命名空间 |
| --- | --- |
| `AddSqlCore()` | `Bing.Dapper`（核心服务，Provider 内部自动调用，一般不用手写） |
| `AddSqlDataSource(key, DatabaseType, connectionString, ...)` | `Bing.Dapper` |
| `AddSqlServerProvider()` | `Bing.Dapper.SqlServer` |
| `AddMySqlProvider()` | `Bing.Dapper.MySql` |
| `AddPostgreSqlProvider()` | `Bing.Dapper.PostgreSql` |
| `AddOracleProvider()` | `Bing.Dapper.Oracle` |
| `AddSqliteProvider()` | `Bing.Dapper.Sqlite` |

### 5.4 ⚠ 明确不支持的能力

这一支是「SQL 构建器 + 执行器」，**刻意不做**领域层抽象：

| 能力 | 状态 | 说明 |
| --- | --- | --- |
| `IUnitOfWork` | ❌ | `Bing.Dapper.Core` 源码树无任何 `IUnitOfWork`；不引用领域层包 |
| `IStore` / 仓储 | ❌ | `IStore` 定义在 `Bing.Ddd.Domain`，Dapper 支不引用 |
| 审计字段 | ❌ | 审计实现在 `Bing.Auditing` / EF / FreeSQL 支，与 Dapper 支无引用关系 |
| 乐观锁 | ❌ | 仅在 EF / FreeSQL 支存在 |
| 迁移 / DDL | ❌ | 无任何建表改表能力 |
| 多租户 | 🔌 | `TenantIdFilter` 存在，但 `AddSqlCore` 只默认注册 `IsDeletedFilter`，租户需自行注入 `ISqlTenantFilterContributor` |

### 5.5 已知限制（源码里的显式未完成点）

1. **Lambda 多源查询整体未实现**——`From` / `Join` / `Select` / `Group By` / `Order By` 五项**全不支持**，另有原子投影替换，共 6 处 `NotSupportedException`（`SqlLambdaQueryCore.cs:656/701/710/717/724/731`）。多表场景请走 Fluent 或原生 SQL 路径。
2. 不支持 `Returning` 子句（两处，`MutationClauseExtensions.cs`）
3. `Mutation Set` 不支持「来源列赋值」（如 `SET A = B`）
4. 含 CTE 的 `Union` / `Group` / `Distinct` 查询不支持自动分页计数，需预先设置 `TotalCount`
5. 原生 SQL 不支持自动分页
6. 不支持多表 DTO 投影绑定（`FromClause.cs`）
7. 7.0.0 破坏性移除：`IDbConnectionManager` / `IDbTransactionManager` / `IDatabaseFactory` / `ISqlQuery.GetConnection` / `BeginTransaction`——详见 [迁移指南](../migrations/README.md)
8. Doris 数据源强制只读、不支持事务
9. SQLite 不支持数据库名/架构名限定，只能写单段对象名

#### 框架自认的"未实现"：`ProviderImplementationGap`

`Bing.Data.Sql` 用一个枚举**主动声明**能力缺口（`framework/src/Bing.Data.Sql/Bing/Data/Sql/SqlCapabilityFailure.cs`），共 4 档：

| 枚举值 | 含义 | 算不算缺陷 |
| --- | --- | --- |
| `DatabaseUnsupported` | 数据库语义/版本不支持该能力 | ❌ 不算（DB 的限制） |
| **`ProviderImplementationGap`** | **数据库支持，但 Bing Provider 尚未实现** | ✅ **算** |
| `ProviderProfileMissing` | Provider 未声明统一能力档案 | ⚠️ 配置缺失 |
| `ProviderProfileMismatch` | 声明与实际执行不一致 | ⚠️ 声明打架 |

全仓 37 处 `SqlCapabilityFailure.Create` 调用中，**`ProviderImplementationGap` 占 10 处**：9 处集中在 `Bing.Dapper.Core/…/SqlExecutorBase.cs`（批量 Update 渲染上下文与渲染器、组合式 Delete 批量、组合式 Insert 批量、`MultiRowValues`），1 处在 `SqlTransactionScopeFactory.cs`（Provider 声明支持原生异步事务但运行时未提供对应成员）。逐行明细见 [功能完成度 §4.2](../architecture/功能完成度.md)。

> 💡 **批量写入默认是可用的**。这 10 处里，`SqlBatchDeleteStrategy.Auto` 与 `SqlBatchInsertStrategy.Auto`（以及 Update 的非 `ProviderOptimized` 路径）会**自动降级为逐条命令并正常返回**，不抛异常——只是失去 Provider 侧优化。**只有显式要求 Provider-optimized 策略时才拿到 `NotSupportedException`**。唯一例外是 `MultiRowValues` 那处：它由 Provider Profile 的 `SupportsMultiRowValues` 决定，在 `Auto` 分支之前就抛，**不受策略影响**。

> 这一支的缺口**全部是 fail fast**：调用即抛 `NotSupportedException`，异常 `Data` 中带结构化能力名与 Provider Key（可用 `SqlCapabilityFailure.TryGetReason` 程序化读取）。**不会静默出错**——与 FreeSQL 支异步缺口"不报错但阻塞线程"的性质正好相反，对比见 [功能完成度 §3.3](../architecture/功能完成度.md)。

## 6. 按场景推荐

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 新建业务系统，要迁移 + 全套领域能力 | **EF Core** | 唯一有迁移、能力最全 |
| 老 `netstandard2.0` 工程，只要 MySQL | **FreeSQL** | TFM 兼容；但接受无迁移 + 异步退化 |
| 报表 / 复杂查询 / 大批量写入 | **Bing.Data.Sql + Dapper** | 批量 + 跨库 + 存储过程，EF 支都没有 |
| 要接 Doris（OLAP） | **Bing.Data.Sql + Dapper**（`bing.mysql` key） | 唯一点名支持 Doris 的一支；注意只读无事务 |
| 要 Oracle | **EF Core** 或 **Dapper** | 前者 `net6.0`，后者 `netstandard2.1`；FreeSQL 无 Oracle |
| 多租户 | **EF Core**（重写 `CreateFilterExpression`）或 **Dapper**（注册 `ISqlTenantFilterContributor`） | 三支都需要自己写，没有开箱即用 |
| 想同时用 | **可以组合**：EF Core 管业务写入，Bing.Data.Sql 管报表查询 | 见下节 |

## 7. 能不能混用？

可以，且这是常见组合：**EF Core（或 FreeSQL）负责领域写入 + Bing.Data.Sql 负责复杂查询**。但要注意：

- 两者**不共享事务**。EF 的 `IUnitOfWork` 事务与 Bing.Data.Sql 的 `ISqlTransactionScope` 是两条独立链路，跨支的一致性要你自己保证（或改用 CAP 事件最终一致）。
- 两者**不共享实体映射**。EF 用 `IEntityTypeConfiguration`，Bing.Data.Sql 用 `IEntityMappingResolver`，同一张表的列名约定可能不一致，改列时要同步改两处。
- 注册的仓储 `IStore` 只覆盖 ORM 支；Bing.Data.Sql 的 `ISqlQuery` / `ISqlExecutor` 是独立的注入点。

## 8. 三支都不行的事（别指望）

| 你想要的 | 现状 |
| --- | --- |
| 开箱即用的多租户 | 三支都要自己写过滤器 |
| 开箱即用的 Bulk 批量写入（ORM 层） | 只有 Dapper 支有；EF / FreeSQL 没有 |
| 数据库迁移（非 EF） | FreeSQL / Dapper 都没有，只有 EF 支有 |
| 分布式事务（跨库） | 三支都没有，请用 CAP 事件最终一致 |
