# 日志与可观测性

> **适用版本**：框架 `7.0.0`（`version.props`）｜ 目标框架：类库 `netstandard2.0`、Web / 应用 `net6.0`｜ 内容核对：2026-09-18｜ 版本历史见 [发行说明](../ReleaseNotes.md)

> **一句话定位**：本文回答**"日志怎么接、请求日志记了什么、TraceId 怎么贯通、出问题去哪看"**。
>
> **分工**：本文是**链路视角**（五个层次怎么串起来）；只想学「怎么用 `ILog` 写一条日志」请直接看 **[日志使用说明](日志使用说明.md)**。
>
> 框架在可观测性上是**"提供零件、不提供装配"**：日志 Sink、Enricher、诊断中间件都有，但没有一个 `AddObservability()` 把它们串起来——实际的 Serilog 管道是宿主（如 `modules/admin`）**手工装配**的（见 §2.3）。
>
> 配置项与配置节见 [配置参考](../guides/配置参考.md)；敏感数据外发的风险见 [安全指南](安全指南.md)；扩展点的写法见 [扩展指南](../guides/扩展指南.md)。
>
> **所有类型与行号均取自源码。** 若源码变了而本文没变，请信任源码并回来修正本文。

## 2. 日志接入

### 2.1 三个包的分工

| 包 | 提供什么 | 注册入口 |
| --- | --- | --- |
| `Bing.Logging` | 日志抽象与链式 API（`Log` / `Log<T>` / `ILog<T>`） | `AddBingLogging(...)` |
| `Bing.Logging.Serilog` | Serilog **配置辅助**（级别映射、Enricher 扩展） | ⚠ **没有注册入口**，只有 `ConfigLogLevel` |
| `Bing.Logging.Sinks.Exceptionless` | Exceptionless Sink | ⚠ 入口在 **`Serilog` 命名空间**下，名为 `WriteTo.Exceptionless` |
| `Bing.AspNetCore.Serilog` | ASP.NET Core 专用 Enricher 中间件 | `UseBingSerilogEnrichers(app)` |

**最容易踩的一处**：`UseBingSerilogEnrichers` **不在** `Bing.Logging.Serilog`，而在 **`Bing.AspNetCore.Serilog`**（`BingAspNetCoreSerilogApplicationBuilderExtensions.cs:18`）。按包名去找会找不到。

### 2.2 `AddBingLogging` 与日志 API

```csharp
// ServiceCollectionExtensions.cs:17 —— 这是该包唯一的注册扩展
// ⚠ 返回类型是 BingLoggingBuilder，不是 IServiceCollection —— 后面不能直接链式 AddXxx
public static BingLoggingBuilder AddBingLogging(
    this IServiceCollection services,
    Action<BingLoggingOptions> setupAction = null);
```

要继续链式注册，用 `services.AddBingLogging().Services.AddXxx()`，或拆成两条语句。

> 链式 API 的完整用法（`Message` / `Property` / `ExtraProperty` / `Tag` / 参数化 / 作用域）见 **[日志使用说明](日志使用说明.md)**；本文只讲它在可观测链路里的位置。

`BingLoggingOptions`（`BingLoggingOptions.cs:13,20,26,33`）：

| 属性 | 默认 | 说明 |
| --- | --- | --- |
| `ClearProviders` | `false` | 是否清空已有 `ILoggerProvider` |
| `Extensions` | internal，空 List | 通过 `RegisterExtension(...)` 追加 |

日志写法有两种，**没有** `Log.Info(...)` 这种静态快捷方法：

```csharp
// 1) DI 注入泛型日志器（推荐）
public class OrderService
{
    private readonly ILog<OrderService> _log;      // 经 DI 解析
    public OrderService(ILog<OrderService> log) => _log = log;
}

// 2) 非 DI 场景用静态空实现占位
ILog log = Log.Null;                               // Log.cs:53
```

`Log.cs` 是**链式 API**（`:12`，`class Log : ILog`）：`EventId` / `Exception` / `Property` / `State` / `Message` / `LogXxx` / `BeginScope`。配套扩展在 `ILogExtensions.cs:17-158`（`Append` / `Tags` / `ExtraProperty` 等）。框架预置了一个错误事件 ID：`Log.LogErrorEventId = 91000`（`Log.cs:109-238` 区段）。

### 2.3 Serilog 管道：手工装配

`Bing.Logging.Serilog` **只有两个配置文件里的方法**，没有任何"一键接入"：

| 类型 | 方法 | 位置 |
| --- | --- | --- |
| `LoggerConfigurationExtensions` | `ConfigLogLevel(this LoggerConfiguration, IConfiguration)` —— **唯一方法** | `LoggerConfigurationExtensions.cs:17` |
| `LoggerEnrichmentConfigurationExtensions` | `WithLogContext`(:16) / `WithLogLevel`(:28) / `WithProperty`(:41) / `WithFunction` ×3(:57,75,94) / `WithEnvironment`(:113) | 同工程 |

所以真实装配长这样（`modules/admin/src/Bing.Admin/Modules/LogModule.cs:57-91`，示意）：

```csharp
Log.Logger = new LoggerConfiguration()
    .ConfigLogLevel(configuration)         // 读 "Logging:LogLevel"
    .Enrich.WithLogContext()               // 或其它 Enricher 扩展
    .WriteTo.Console()
    .WriteTo.Exceptionless(apiKey)         // 见 §2.5
    .CreateLogger();
```

### 2.4 日志级别映射

配置节 **`"Logging:LogLevel"`**，映射逻辑在 `LoggerConfigurationExtensions.cs:23-32`：

- `Default` → `MinimumLevel.ControlledBy(...)`（全局动态级别）
- 其余键（如 `Microsoft`、`DotNetCore.CAP`、`Bing`）→ `MinimumLevel.Override(...)`

级别名到 Serilog 的转换在 `LogLevelSwitcher.Switch`（`LogLevelSwitcher.cs:32-45`）：

```
Trace → Verbose    Debug → Debug      Information → Information
Warning → Warning  Error → Error      Critical → Fatal
None   → Fatal     未知值 → Warning
```

⚠ **两个静默降级**：

- **未知级别值 → `Warning`**。`"LogLevel": { "Bing": "Info" }`（不是合法级别名）会被当成 `Warning`，表现为"我把级别调低了但没看到 Debug 日志"。
- **`"None"` → `Fatal`**（`LogLevelSwitcher.cs:42`），**不是"关闭日志"**。本想关掉某个命名空间，结果只剩最严重的日志。

### 2.5 Exceptionless Sink

```csharp
// 命名空间是 Serilog（不是 Bing.Logging），partial 静态类
// LoggerSinkConfigurationExtensions.cs:23-28
public static LoggerConfiguration Exceptionless(
    this LoggerSinkConfiguration loggerSinkConfiguration,
    string apiKey,
    Func<EventBuilder, EventBuilder> additionalOperation = null,
    bool includeProperties = true,
    LogEventLevel restrictedToMinimumLevel = LevelAlias.Minimum);
```

用法：`.WriteTo.Exceptionless(apiKey)`（共 3 个重载）。

⚠ **`apiKey` 的来源要留意**：admin 的 `LogModule.cs` 里是**硬编码的**，且目标地址是内网。`samples/Bing.Samples.Hangfire` 同样硬编码了一个内网 Exceptionless 地址。外发端点与凭据的处置见 [安全指南](安全指南.md)。

## 4. 请求 / 响应日志

```csharp
// 注册（Extensions.ServiceCollection.cs:46；另有 TLogger / TLogCreator 泛型重载 :57,70）
services.AddRequestResponseLog(o =>
{
    o.WithRequest  = true;      // 默认 false
    o.WithResponse = true;      // 默认 false
    o.WithHeader   = true;      // 默认 false
    o.WithCookie   = true;      // 默认 false
});

// 启用（Extensions.ApplicationBuilder.cs:55）
app.UseRequestResponseLog();
```

`RequestResponseLoggerOptions`（`RequestResponseLoggerOptions.cs:11-46`）：

| 属性 | 默认 | 说明 |
| --- | --- | --- |
| `IsEnabled` | — | 总开关 |
| `Name` | — | 日志器名称 |
| `WithRequest` / `WithResponse` | `false` | 是否记录请求体 / 响应体 |
| `WithHeader` | `false` | 是否记录请求头 |
| `WithCookie` | `false` | 是否记录 Cookie |
| `RequestFilter` | — | 请求过滤 |
| `DateTimeFormat` | — | 时间格式 |

记录内容（`RequestResponseLoggerMiddleware.cs:66-106`）：请求方法 / 路径 / Query、请求头（`WithHeader`）、Cookie（`WithCookie`）、**请求体**、**响应体**（`WithResponse`）、状态码、异常栈。
自动跳过静态文件 / 上传 / `OPTIONS`（`:252-284`）。

### ⚠ 没有任何脱敏机制

这是本节最需要记住的一条：

- 全仓在 `Bing.AspNetCore` 下检索 `脱敏` / `Desensit` / `Mask` / `Sensitive` —— **零命中**
- Header 与 Cookie **原样输出**（`RequestResponseLoggerMiddleware.cs:136-155`）

**后果**：`WithHeader = true` 会把 `Authorization: Bearer ...`、`Cookie: ...` 整个写进日志；`WithRequest = true` 会把密码、身份证、卡号原样写进去。而这些日志可能又通过 Exceptionless 发往外部端点。

**建议**：把 `RequestFilter` 用起来，对登录、支付、实名等接口排除；或在日志外发前自己加脱敏层。详见 [安全指南](安全指南.md)。

## 5. 关联标识：`CorrelationId` 与 `TraceIdContext`

### 5.1 中间件行为

```csharp
app.UseCorrelationId();   // → app.UseMiddleware<BingCorrelationIdMiddleware>()
                          //   Microsoft/AspNetCore/Builder/BingApplicationBuilderExtensions.cs:71
```

| 项 | 值 | 位置 |
| --- | --- | --- |
| `CorrelationIdOptions.HttpHeaderName` | `"X-Correlation-Id"` | `CorrelationIdOptions.cs:11` |
| `CorrelationIdOptions.SetResponseHeader` | `true` | `:16` |

中间件逻辑（`BingCorrelationIdMiddleware.cs:47,60-69,77-85`）：

1. 从请求头取 `X-Correlation-Id`
2. 取不到 → 生成 `Guid("N")`
3. `TraceIdContext.Current ??= new TraceIdContext(correlationId)` —— **已有值时不覆盖**
4. 回写响应头（`SetResponseHeader = true` 时）

### 5.2 `TraceIdContext`

`Bing.Core/Bing/Tracing/TraceIdContext.cs`：

| 成员 | 说明 |
| --- | --- |
| `AsyncLocal<TraceIdContext> Current` | `:58-67`，跨 `await` 自动流动 |
| `TraceId` / `RootId` / `ParentId` / `ChildId` | 链路标识各层级 |

可用它把当前 TraceId 手工写进日志或业务表（例如业务要记录"这次操作属于哪条链路"）。

⚠ **但 TraceId 不会自动出现在用 `ILog` 写的日志里**。`Log.AddLogContext()` 中把 TraceId 写进日志属性的那段代码**整段被注释掉了**（`Log.cs:260-264`）：

```csharp
protected virtual void AddLogContext()
{
    if (LogContext == null)
        return;
    //if (!string.IsNullOrWhiteSpace(LogContext.TraceId))
    //{
    //    Debug.WriteLine($"【{nameof(Log)}】TraceId: {LogContext.TraceId}");
    //    Property("TraceId", LogContext.TraceId);
    //}
}
```

它只会出现在**装了 `.Enrich.WithLogContext()` 的 Serilog 事件**上（由 `LogContextEnricher` 补）。只挂 `AddConsole()` 的话，日志里没有 TraceId。详见 [日志使用说明 §6](日志使用说明.md)。

### 5.3 ⚠ CAP 消费端的坑

发布端能自动带上 TraceId，但**消费端默认不会**——CAP 的消费者不在 HTTP 请求上下文里，`TraceIdContext.Current` 是空的。

admin 的解法是自定义 `SubscribeInvoker`：

```csharp
// modules/admin/src/Bing.Admin/Modules/CapModule.cs:87,108-129
public class CapSubscribeInvoker : SubscribeInvoker
{
    protected override object GetInstance(...)   // 重写：调 InitTraceIdContext
}

// 从 CAP 消息头 "bing-trace-id" 读取并写入 TraceIdContext.Current
services.AddSingleton<ISubscribeInvoker, CapSubscribeInvoker>();   // :48
```

要点：**消息头名是 `bing-trace-id`**（不是 `X-Correlation-Id`）。自己接 CAP 时若不加这一步，消费端日志的 CorrelationId 会与发布端对不上，链路在消息处断掉。

> 发布端写入该头的常量在 `Bing.Events/Cap/Headers.cs:11`；完整的 CAP 收发链路、`send:false` 的事务语义见 [事件与消息文档 §4](../architecture/事件与消息文档.md)。⚠ FreeSQL 宿主**没有**注册 `CapSubscribeInvoker`，该宿主的消费端 TraceId 是断的。

## 6. 链路追踪：SkyAPM 的 SQL 诊断

```csharp
// SkyWalkingBuilderExtensions.cs:17-23
public static SkyApmExtensions AddSqlQuery(this SkyApmExtensions extensions);
```

作用：把 SQL 执行作为 SkyWalking 的追踪段上报，组件标识 `SQLCLIENT`。是否上报**参数值**由 `skyapm.json` 的 `Sampling.LogSqlParameterValue` 决定（`:56-58`）。

admin 的启用方式（`Modules/SkyApmModule.cs:30-33`，模块在 `Startup.cs:42` 注册）：

```csharp
.AddSkyApmExtensions()
.AddCap()              // CAP 的 SkyWalking 集成
.AddSqlQuery()         // 本框架提供
```

`skyapm.json` 的结构与各字段（含 `IgnorePaths`、gRPC `Servers`）见 [配置参考 §6.2](../guides/配置参考.md)。

⚠ **`Sampling.LogSqlParameterValue = true` 会把 SQL 参数值上报到追踪后端**——这是把业务数据送出边界，涉及敏感字段时请评估。见 [安全指南](安全指南.md)。

## 7. 诊断面板

| 面板 | 启用方式 | 默认路径 | 位置 |
| --- | --- | --- | --- |
| **MiniProfiler** | 用 `MiniProfilerModuleBase` 派生模块：`AddServices` → `AddMiniProfiler`；`UseModule` → `app.UseMiniProfiler()` | `/profiler`（结果页 `/profiler/results`） | `MiniProfilerModuleBase.cs:34,44,58` |
| **CAP Dashboard** | `o.UseDashboard()` | 组件默认 | `Modules/CapModule.cs:55` |
| **Hangfire Dashboard** | `app.UseHangfireDashboard()` + `app.UseHangfireServer()` | 组件默认 | `Modules/HangfireModule.cs:57-58` |

说明：

- MiniProfiler 的 `RouteBasePath` 默认 `/profiler`
- **`modules/admin` 并没有启用 MiniProfiler**（全仓无 `AddMiniProfiler` / `MiniProfilerModule` 引用），要用需自己接
- CAP 与 Hangfire 的路径都没在代码里显式指定，走组件默认；`skyapm.json` 的 `IgnorePaths` 里出现 `/cap`、`/hangfire/stats`，可作旁证
- ⚠ **Dashboard 访问控制要自己加**。CAP / Hangfire Dashboard 默认不受框架的全局 `AuthorizeFilter` 约束，生产环境暴露等于把运维入口放出去

## 8. 框架自身在哪打日志（写自己代码时的参考范式）

| 位置 | 打了什么 | 启示 |
| --- | --- | --- |
| `Bing.AspNetCore/…/Logs/DefaultRequestResponseLogger.cs:39,43,55` | `BeginScope` 结构化字典 + 请求/响应模板 | 留痕用 `BeginScope` 挂上下文 |
| `Bing.AspNetCore/…/ExceptionHandling/BingExceptionHandlingMiddleware.cs:61,75` | 响应已开始时的警告；`LogException(exception)` | 异常统一在一处记 |
| `Bing.AspNetCore/…/RealIp/RealIpMiddleware.cs:87,102` | 真实 IP 解析失败 → `LogError`；明细 → `LogTrace` | **失败用 Error、明细用 Trace** |
| `Bing.AspNetCore/…/Security/AdminSafeListMiddleware.cs:50,67` | 放行 → `LogTrace`；拒绝 → `LogWarning` | 安全事件用 Warning |
| `Bing.EntityFrameworkCore/Core/UnitOfWorkBase.cs:385,416` | 事务回滚 → `LogWarning` | 回滚是 Warning 不是 Error |
| `Bing.Dapper.Core/…/Sql/SqlQueryBase.cs:1192` | 原始 SQL / 调试 SQL / 参数 → `LogTrace` | SQL 明细一律 Trace（量大） |
| `Bing.AspNetCore.Mvc.UI/…/DefaultRazorHtmlGenerator.cs:102` | `LogError(ex, "生成html静态文件失败")` | 附带上下文短语 |
| `Bing.EntityFrameworkCore/…/Migrations/MigrationService.cs:38-108` | 迁移各步骤 → `LogTrace` | 长流程按步骤铺 Trace |

**可以照抄的两条约定**：① 框架自身的明细日志全部走 `Trace`，避免污染生产日志；② 中文日志消息简短、带动作对象。

## 9. 接入检查清单

- [ ] `AddBingLogging(...)` 已调用（否则 `ILog<T>` 解析不到）
- [ ] Serilog 管道手工装配了（`.ConfigLogLevel(configuration)` + 各 Sink）
- [ ] `UseBingSerilogEnrichers(app)` **放在 `UseAuthentication()` 之后**
- [ ] `UseCorrelationId()` 已启用（否则 `TraceIdContext` 为空）
- [ ] 用了 CAP → 接 `CapSubscribeInvoker`，用消息头 `bing-trace-id`
- [ ] 开了 `WithHeader` / `WithCookie` / `WithRequest` → **同时配 `RequestFilter` 排除敏感接口**（框架无脱敏）
- [ ] Exceptionless 的 `apiKey` 与地址**移出源码**（当前 admin / Hangfire 样例里是硬编码的）
- [ ] `skyapm.json` 的 `LogSqlParameterValue` 按数据敏感度决定
- [ ] CAP / Hangfire Dashboard 加了访问控制
- [ ] 需要健康检查 → 自己接 ASP.NET Core 原生 `AddHealthChecks()`
