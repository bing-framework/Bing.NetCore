> **适用版本**：框架 `7.0.0`（`version.props`）｜ 目标框架：类库 `netstandard2.0`、Web / 应用 `net6.0`｜ 内容核对：2026-09-18｜ 版本历史见 [发行说明](../ReleaseNotes.md)

> **一句话定位**：描述框架当前的安全能力边界，以及在 **凭据管理、JWT、SQL 注入、日志脱敏、多租户隔离** 五个方面需要注意的事项。
>
> **范围声明**：本文是**只读取证**的结果，所有结论都标注了「文件路径 + 行号」。**本文不复现任何明文密钥值**——涉及敏感值处一律用 `***` 遮蔽。文中指出的仓库内问题是给维护者的待办清单，不含任何修改或删除操作。

### 1.3 处置顺序（建议）

1. **轮换**：先把这些凭据全部作废重发（轮换优先于删除，因为历史提交仍可读到旧值）。

4. **防复发**：加一层提交前扫描（如检测常见凭据关键字），并在 CI 里对 `appsettings*.json` 做一次基线检查。

## 2. JWT 与认证：两条校验路径，行为不一样

框架同时提供了**两套** JWT 校验链路，`AddJwt` 会把它们都注册上。它们的**过期校验行为不同**，这是本节最需要知道的事。

### 2.1 标准中间件路径（有过期校验）

`Extensions.Service.cs` 里 `AddJwtBearer` 使用的 `TokenValidationParameters`：

```csharp
ValidateIssuerSigningKey = true,
ValidateIssuer          = true,
ValidateAudience        = true,
ValidateLifetime        = true,                                    // ✅ 校验有效期
LifetimeValidator = (before, expires, token, param) => expires > DateTime.UtcNow,
ClockSkew         = TimeSpan.FromSeconds(30),
RequireExpirationTime = true
```

✅ 这条路径**会**校验有效期与签发者、受众。

### 2.2 自定义校验器路径（不校验 exp / nbf）

`JsonWebTokenValidator.Validate` 只做三件事：格式检查、**HMAC-SHA256 签名校验**、自定义 payload 校验。`exp` / `nbf` 的校验代码是**注释状态**，且 XML 备注明确写着「本方法不校验 `exp` 和 `nbf` 有效期声明」：

```csharp
// 其次验证是否在有效期内
//var now = ToUnixEpochDate(DateTime.UtcNow);
//if (!(now >= long.Parse(payload["nbf"].ToString()) && now < long.Parse(payload["exp"].ToString())))
//    return false;
```

受影响的使用者：`JsonWebTokenCustomerAuthorizeMiddleware`、`JsonWebTokenAuthorizationHandler`（也就是 `"jwt"` 授权策略）。

**但别急着下结论**——`JsonWebTokenAuthorizationHandler` 有两条分支，行为不同：

| 分支 | 触发条件 | 过期校验 |
| --- | --- | --- |
| `ResultHandleAsync` | `ThrowEnabled = false`（**默认值**） | ✅ **有**——靠 `_tokenStore.GetTokenAsync(token).IsExpired()` 兜底（服务端令牌存储的过期时间，而非 JWT 的 `exp` 声明） |
| `ThrowExceptionHandleAsync` | `ThrowEnabled = true` | ⚠ **完全没有**——既不查 `exp`/`nbf`，也没有 `IsExpired()` 调用 |

> 🔴 **结论**：**如果你把 `ThrowEnabled` 设为 `true`，过期校验会静默消失。** 这也是我要重点提醒的一条：开了这个开关的项目，请务必自行补上过期检查，或改为依赖服务端令牌存储的过期 + 主动吊销。

### 2.3 其它 JWT 事实

| 项 | 说明 |
| --- | --- |
| 密钥来源 | `JwtOptions:Secret` 配置节；**为空时抛异常**（不会静默退化到无签名）✅ |
| 默认签发者 / 受众 | `bing_identity` / `bing_client`——**默认值请在生产替换** |
| 默认有效期 | Access Token **5 分钟**（未配置时兜底）；Refresh Token **7 天**（10080 分钟） |
| 建议 | 密钥长度足够、不外泄；启用 HTTPS；Refresh Token 用服务端存储 + 吊销能力 |

## 3. SQL 注入防护

### 3.1 分析器：目前只有一条规则

| 诊断码 | 内容 | 级别 |
| --- | --- | --- |
| **BINGSQL002** | 插值 SQL 未参数化——把插值字符串传给 `ISqlQuery.Sql(...)`、`ISqlExecutor.ExecuteSql(...)` / `ExecuteSqlAsync(...)` 的**普通文本入口**时告警 | `Warning`，分类 `Bing.Data.Sql.Security`，**默认启用** |

释放（安全）路径：**传入参数对象** 或 **`SqlInterpolated(...)`**——它们不会触发该诊断。

### 3.2 写法对照

```csharp
// ❌ 拼接/插值走进普通文本入口 → BINGSQL002
ExecuteSql($"SELECT * FROM t WHERE name = '{name}'");

// ✅ 参数化：分析器认可
SqlInterpolated($"SELECT * FROM t WHERE name = {name}");

// ✅ 参数对象：分析器认可
ExecuteSql("SELECT * FROM t WHERE name = @name", new { name });
```

底层执行链路是可靠的：`ExecuteSql` → `PrepareCommand` → Dapper 的 `connection.Execute(sql, parameters, ...)`，参数始终以参数化形式下发。

> ⚠️ 注意 `BINGSQL002` 是 **Warning 不是 Error**。如果构建没有开启 `TreatWarningsAsErrors`，它可能被忽略——建议在自己的 CI 里把这条单独提级。

## 4. 日志脱敏与外发

### 4.1 请求日志会记录什么

`RequestResponseLoggerMiddleware` 的行为：

| 内容 | 记录条件 |
| --- | --- |
| **请求体** | 中间件启用后**无条件读取并记录**（不受 `WithRequest` 子开关单独限制） |
| 响应体 | 受 `WithResponse` 控制，**默认关闭** |
| 请求头 / Cookie | 受 `WithHeader` / `WithCookie` 控制，**默认关闭** |
| 路径过滤 | 仅支持按 `RequestFilter` 的**路径前缀**过滤，以及「含文件上传」过滤 |

参考实现 `modules/admin` 里显式开了 `o.WithRequest = true`，并且同时开了 `AddHttpLogging(LoggingFields.All)`。

### 4.2 ⚠ 没有字段级脱敏

全仓检索确认：**HTTP 日志侧没有任何脱敏机制**（无 `[Sensitive]` / `Mask` 之类的概念）。这意味着登录、支付、改密等接口的请求体会**原样进入日志**——包括密码、身份证号、令牌。

**有意思的对比**：SQL 诊断侧**是**有脱敏的——参数名包含 `password` / `pwd` / `passphrase` 时会输出 `'<redacted>'`。也就是说框架作者意识到了这个风险，但只做在了 SQL 侧。

**建议**：

- 用 `RequestFilter` 把含敏感字段的路径排除掉；
- 或者继承/替换中间件，在写入前做字段脱敏；
- 日志级别与落盘策略按环境区分，避免敏感日志长期留存。

### 4.3 日志外发端点

`Bing.Logging.Sinks.Exceptionless` 会把日志发往配置的 Exceptionless 服务。仓库内**硬编码的内网 HTTP 端点**位于上述三个 `LogModule.cs`（明文协议，非 HTTPS）。

建议把端点与 API Key 一并移出源码配置系列，并确认内网日志服务的访问权限。

## 5. 框架**没有**提供的防护（诚实清单）

以下能力全仓检索确认**不存在**，需要你在应用层自行实现：

| 能力 | 现状 |
| --- | --- |
| **XSS 防护** | ❌ 无内置 |
| **CSRF / AntiForgery** | ❌ 无内置 |
| **速率限制** | ❌ 无内置 |
| **IP 白名单** | ❌ 无准入控制。`UseRealIp()` 只负责从 `x-forwarded-for` 解析真实 IP，**不做任何放行/拒绝**——别把它当安全边界用 |
| **全局权限过滤器** | ❌ 框架层没有。`Bing.Permissions` 只有 Identity 模型与管理器（如 `ISignInManager`、`UserBase`），没有 `IPermissionChecker` / 权限过滤器 |

✅ **参考实现补上了授权**：`modules/admin` 的两个宿主（EF 版与 FreeSQL 版）都通过 `AuthorizeControllerModelConvention` 给**所有** Controller 加了 `AuthorizeFilter("jwt")`——即「默认拒绝、显式放行」的模型。这是值得照抄的做法：

```csharp
internal class AuthorizeControllerModelConvention : IControllerModelConvention
{
    public void Apply(ControllerModel controller) => controller.Filters.Add(new AuthorizeFilter("jwt"));
}
```

> ⚠️ 但要注意第 2.2 节：`"jwt"` 策略最终走到 `JsonWebTokenAuthorizationHandler`，若你把 `ThrowEnabled` 设为 `true`，过期校验就没了。

## 6. 多租户隔离：解析 ≠ 隔离

框架提供**租户解析链**（`ITenantResolveContributor`：`CurrentUser` → `Header` / `QueryString` / `Route` / `Domain` / `Cookie`），但它只回答「当前租户是谁」，**不过滤任何数据**。

而 [能力矩阵 §8](../getting-started/能力矩阵.md) 证实：**三支 ORM 都没有开箱即用的租户查询过滤**。

| 支 | 怎么加租户过滤 |
| --- | --- |
| EF Core | **重写 `UnitOfWorkBase.CreateFilterExpression<TEntity>()`**。⚠ 注意：自定义过滤器**不会**因为注册到 `IFilterManager` 而自动生效——`FilterManager.IsEntityEnabled<TEntity>()` 硬编码只查 `ISoftDelete` |
| Bing.Data.Sql + Dapper | 自行注入 `ISqlTenantFilterContributor`（`AddSqlCore` 默认只注册 `IsDeletedFilter`） |
| FreeSQL | 无相关机制，需自行申请 `GlobalFilter` |

**漏配过滤 = 跨租户数据泄露**，这是本框架多租户场景最主要的正确性与安全风险。另外别忘了 [性能指南 §2](性能指南.md) 提到的那一点：实体映射缓存键**不含 `TenantId`**，多租户分表时必须把租户标识编进 `TableRouteKey`。

## 7. 上线前安全检查清单

**凭据**

- [ ] 数据库 / Redis / MQ / 日志服务凭据全部移出受版本控制的文件
- [ ] 已入库的旧凭据全部**轮换**（不是删了就算）
- [ ] JWT `Secret`、Exceptionless `ApiKey` 已从源码移除
- [ ] `UserSecretsId` 或环境变量方案已就位

**认证授权**

- [ ] 了解了 §2.2 的两条路径差异；如启用 `ThrowEnabled`，已自行补过期校验
- [ ] 生产更换了 `Issuer` / `Audience` 默认值
- [ ] 确认是否需要全局 `AuthorizeFilter`（默认拒绝模型）
- [ ] 是否用了 `UseRealIp()`——注意它不做准入控制

**注入与输入**

- [ ] CI 里把 `BINGSQL002` 提级为 Error（它默认是 Warning）
- [ ] 所有 `ExecuteSql` / `Sql(...)` 调用都走参数化或 `SqlInterpolated`

**日志**

- [ ] 敏感接口路径已加入 `RequestFilter`
- [ ] HTTP 日志侧已补字段级脱敏（框架未提供）
- [ ] 日志 retention 与访问权限符合预期
- [ ] 确认 `WithResponse` / `WithHeader` / `WithCookie` 的开关组合

**多租户（如适用）**

- [ ] 每一支在用的 ORM 都配好了租户过滤
- [ ] 分表场景把租户标识编进了 `TableRouteKey`
