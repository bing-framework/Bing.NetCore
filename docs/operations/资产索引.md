## 本文定位

仓库里除了 `docs/` 下的产品文档，还有几类**历史记录 / 过程产物 / 工具资产**：`ai_docs/`、`artifacts/`、`templates/`、`docs/plans/`、`docs/ai-workflow/`。它们**不是**框架的使用或设计文档，且会随任务持续增长，不说明清楚很容易误读。

本文回答三件事：**它们是什么、是否入库、还能不能信**。

## 2. `ai_docs/` —— AI 任务档案

### 2.1 组成

| 分类 | 内容 |
| --- | --- |
| 治理/设计稿 | SQL、缓存等能力的设计与治理记录；文件清单以目录为准 |
| 分阶段记录 | `stage-00-baseline.md` → `stage-08-multidatabase-completion.md` 等阶段快照 |
| 任务档案（`tasks/`） | 已完成局部任务归入 `completed/` 三份模块总览；24 个未完成、待确认或仍有效的任务完整保留计划/执行/Review。119 个原任务的入口与处置见[任务索引](../../ai_docs/tasks/README.md)，逐文件清理依据见[整理清单](../../ai_docs/tasks/CLEANUP.md) |

### 2.2 怎么读

1. **先读当前模块文档，再追溯治理/设计稿**——缓存的当前入口是[缓存模块](../modules/caching.md)；`sql-public-api-governance.md`、`cache-todo-index.md` 等仅供历史追溯，是否存在以当前目录为准。
2. `stage-00` ~ `stage-08` 是一次**渐进式重构的阶段记录**，按顺序读能还原演进脉络。
3. `tasks/` 下的目录**按需查阅**——只在你需要追查"某个 API 为什么变成现在这样"时才有价值。

### 2.3 ⚠ 时效性声明（重要）

- 这些档案来自多轮 SQL 与缓存加固任务，属于**历史快照**；目录中的日期只代表任务执行时间。
- 其中的 API 名称、测试数量、基准数字**不代表当前代码状态**。例如 7.0.0 之后 SQL 查询 API 又经过收敛，`ai_docs` 里旧的任务报告仍可能写着已被删除的入口。
- **以源码为准**。若 `ai_docs/` 与源码 / `docs/` 下正式文档冲突，**信任源码与 `docs/`**，并考虑在 `ai_docs/` 对应文件顶部加一行过期提示。

### 2.4 缓存基准共享基线

缓存基准任务 `BING-CACHE-HARDENING-20261004-001` 与 `BING-CACHE-PERF-STREAM-20261004-002` 共用固定提交 `24c93cb1a5355797223637e2d42ac3dce968d7ef`。在仓库根目录使用以下入口准备基线：

```powershell
./eng/ci/prepare-baseline.ps1 -Commit 24c93cb1a5355797223637e2d42ac3dce968d7ef
```

脚本返回/输出基线绝对路径；默认统一位置为仓库外相邻的 `H:/Bing_Framework/Bing.NetCore.baselines/24c93cb1a5355797223637e2d42ac3dce968d7ef`。`eng/baselines.props` 默认引用该相邻目录，构建时可用 `-p:BaselineStore=<统一目录>` 或 `-p:BaselineSourceRoot=<源码目录>` 覆盖。基线源码不复制进 `ai_docs/`，准备脚本也不自动移除共享目录；需在所有使用方和后续复核完成后，由维护者显式清理。

## 3. `artifacts/` —— 过程产物（不入库）

`artifacts/` 已被 `.gitignore` 忽略，**提交时不会带入**。测试与基准产物由相应脚本和工程生成，其中 Provider 发布证据由 `eng/Bing.ProviderEvidence.Cli` 校验。

任务 JSON 报告、checkpoint、源码身份快照和矩阵运行状态统一归档到 `artifacts/ai-tasks/`，保留任务 ID 与任务内相对路径；`ai_docs/tasks/` 只保留文档与复现源码。迁移入口、旧路径映射和共享方式见[任务产物归档说明](../../ai_docs/tasks/ARTIFACTS.md)。原始证据内容保持不变；产物仅在本地保存，新的克隆不含这些文件。

| 子目录 | 内容 | 怎么读 |
| --- | --- | --- |
| `ai-tasks/<任务ID>/` | 从 AI 任务目录归档的原始 JSON、checkpoint 与完成任务遗留日志，保留子目录结构 | 按任务 ID 定位；历史路径按归档说明映射 |
| `test-results/` | 单元/集成测试的 TRX、JSON、能力矩阵（`provider-capability-matrix.md` 汇总各 Provider 支持情况） | 看 `provider-capability-matrix.md` 最快 |
| `provider-test-results/<provider>-<tfm>-<时间戳>-<guid>/` | 按 Provider + TFM + 时间戳归档的集成测试结果与 `run-metadata` | 用时间戳判断新旧 |
| `benchmarks/` | 基准测试归档证据（含 BenchmarkDotNet 的 github 报告 md） | 与 `BenchmarkDotNet.Artifacts/`（默认输出、已忽略）区分 |
| `plans/`、`reports/` | 历史任务计划与最终报告 | — |
| `release-candidate/` | release lane 的验证产物 | — |

**解读要点**：这些是**单次任务的证据**，不是全局基线。报告里的测试数量**不构成当前 commit 的验收证据**——要验收请以当前 `dotnet test` 结果与 TRX 为准。

## 4. `templates/` —— 代码生成器（历史遗留）

| 目录 | 说明 |
| --- | --- |
| `templates/CodeSmith/` | 独立 `.sln` + `.csproj`，内置 `CodeSmith.Engine` / `SchemaExplorer` dll，约 50 个 `.cst` 模板（Domains / Datas / Services / Presentation / Tests / PersistObjects） |
| `templates/Pd/` | PowerDesigner 数据模型（`.xdb` / `.pdm`） |

- **与框架运行时无依赖关系**，不在 `Bing.All.sln` 内；
- 用途：从数据库模型**批量生成分层代码**；
- ⚠ **年代较早**：生成的代码风格可能已与现行 API 不符（7.0.0 后 SQL 查询 API 大幅收敛）。**使用前务必先验证生成结果能编译**；
- ⚠ 仓库内**没有**它的使用文档。

## 6. 维护约定

- **不要**把 `artifacts/` 或 `BenchmarkDotNet.Artifacts/` 提交进仓库（已在 `.gitignore` 中）；若需要长期留档，把关键结论**抄进** `docs/` 下的正式文档或 [ReleaseNotes](../ReleaseNotes.md)。
- 在 `ai_docs/tasks/` 下新建任务目录时，沿用既有命名（`plan.md` / `execution.md` / `review.md` ...）与 `<任务ID>` 目录名规范。
- 已完成且被总览覆盖的重复任务文档可按[整理清单](../../ai_docs/tasks/CLEANUP.md)清理，保留任务 ID、结论、源码/测试证据和限制；未完成或仍有效的任务完整保留原文。
- 新增任何一类资产目录时，回到本文 §1 的表格补一行。
