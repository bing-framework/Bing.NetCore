# 性能指南

> **适用版本**：框架 `7.0.0`（`version.props`）｜ 目标框架：类库 `netstandard2.0`、Web / 应用 `net6.0`｜ 内容核对：2026-09-18｜ 版本历史见 [发行说明](../ReleaseNotes.md)

> **一句话定位**：基于仓库实测基准数据与源码热路径分析，告诉你**在哪里能省、在哪里千万别踩**。不是理论分析，数字标注了来源。
>
> **数据来源**：基准数字取自 `artifacts/benchmarks/` 下已有的正式运行产物，环境为 **net8.0 / RyuJIT AVX2 / BenchmarkDotNet 0.14.0**。工程源码在 `framework/tests/Bing.Data.Sql.Benchmarks/`。
> **请把数字当相对量看**：不同机器绝对值会变，但**倍数关系**（如重复渲染快 60 倍）是稳定的。做优化决策前请自行重跑一遍。

| 场景 | 耗时 | 分配 | 结论 |
| --- | --- | --- | --- |

## 2. 缓存与热路径地图

改性能前先知道东西缓存在哪。以下每个缓存都注明了**键怎么算**和**什么情况会穿透**。

| 缓存 | 键的构成 | 什么时候会失效 / 穿透 |
| --- | --- | --- |
| **实体最终映射缓存** `_mappingCache` | `(TypeHandle, DbKey, DatabaseType, MappingProfile, TableRouteKey, Database, Schema, TableName)`；字符串一律 `Trim().ToUpperInvariant()` | ① `EntityMappingCacheCapacity = 0` → **完全不缓存**；② 默认策略 `AdmissionOnly`：容量满时**新路由永不入缓存，每次重建**；③ `LeastRecentlyUsed` → 触发淘汰开销 |
| **模型元数据缓存** `_modelCache` | `RuntimeTypeHandle` + `Lazy<T>` | 永不淘汰；构造失败时按引用移除 |
| **Mutation Plan 缓存** | `(TypeHandle, ProviderKey, Database, Schema, Table, MappingProfile, TableRouteKey, Operation, Include/Exclude 签名)` | 容量 0 旁路；满则 LRU；按 `IEntityMappingResolver` 实例**弱引用分区**（解析器释放即可回收） |
| **属性 Getter 缓存**（编译表达式委托） | `(sourceType.TypeHandle, 属性名大写)` | 同上；命中时是已编译委托，很快 |
| **Builder 查询 SQL 缓存** | 无键，比对 `_cachedVersion == _shapeVersion` | `Touch()`（结构变更）会让缓存失效；**`RequiresExecutionSnapshot(builder)` 为真时直接绕过** |
| **子句延迟创建** | 无键，字段懒创建 | 随 Builder 生命周期 |
| **DI 类型扫描缓存** | 无键，`Found` 布尔 + `ItemsCache` | `FindAll(fromCache: false)` 会**每次重扫并重写缓存** |
| **目录程序集缓存** | 静态 `ConcurrentDictionary<路径, Assembly[]>` | 同上，`fromCache: false`（**且是默认值**）会重复 `Directory.GetFiles` + `Assembly.LoadFrom` |

> 📌 **一个容易忽略的点**：实体映射缓存的键**包含 `TableRouteKey`，但不包含 `DatabaseContext.TenantId`**（`GetCacheTableRouteKey` 只取 `mappingOptions?.TableRouteKey`）。多租户按租户分表的场景，请务必把租户标识编进 `TableRouteKey`，否则不同租户会命中同一条缓存——这既是性能问题也是**正确性问题**。

## 3. 性能建议（按收益排序）

### 3.1 让实体映射缓存命中 —— 收益最高

**17 倍差距**（86 ns vs 1,489 ns），是所有优化里最划算的一条。

```csharp
// ✅ 为稳定、有限的实体集合配置足够容量
services.Configure<SqlMetadataOptions>(o =>
{
    o.EntityMappingCacheCapacity = 1024;                    // 0 = 完全不缓存
    o.EntityMappingCacheEvictionPolicy = ... LeastRecentlyUsed;  // 默认 AdmissionOnly
});
```

- **默认策略 `AdmissionOnly` 的含义**：容量满了以后，新来的路由**不再入缓存**（而非淘汰旧的），于是它们每次都走冷路径。如果你有**动态表名**场景（按月分表、多租户分表），请显式评估——否则稳态性能会长期停在 430 ns 那一档。
- 避免在同一进程里为同一张表构造**多种不同写法**的 `Database`/`Schema`/`TableName`（大小写会归一化，但空串 vs null、有无 schema 要看源码行为），否则键不同导致重复冷启动。

### 3.2 复用已构建的 Builder —— 约 60 倍

```
BuildRootsAndRender  6,739 ns   首次构建 + 渲染
RenderExistingRoots    113 ns   重复渲染已构建的 Builder   ← Ratio 0.009
```

**结论**：如果一个查询结构固定、只是参数不同，**构建一次、渲染多次**。

```csharp
// ❌ 循环里每次重建
foreach (var id in ids)
{
    var sql = query.From<T>().Where(x => x.Id == id).ToSql();
}

// ✅ 构建一次，只换参数反复渲染
```

配套注意：`Touch()` 会清 `_cachedSql`，渲染前若还想改结构就不要指望缓存；`RequiresExecutionSnapshot` 为真时会绕过缓存路径。

### 3.3 别在热路径里 `Clone()` Builder

`Clone()` **无缓存**，每次都要深拷贝参数管理器 + 8 个子句 + `new EntityResolver(...)` + `AliasRegister.Clone()`，实测 **~1 μs / 8.9 KB**。单次无所谓，循环里就是灾难。

### 3.4 生产环境不要频繁渲染调试 SQL

| 参数个数 | 耗时 | 分配 |
| --- | --- | --- |
| 10 | 3.4 μs | 10 KB |
| 100 | 32.8 μs | 66 KB |
| 1000 | **384.9 μs** | **669 KB** |

随参数数量**超线性**增长。框架内部已用 Trie 把参数名匹配限制为「SQL 文本一次前向扫描」以缓解，但**这个动作本身就不该出现在请求热路径上**——只在排错时手动打开，或采样开启。

### 3.5 批量写入务必分批 —— 最危险的非线性

| 批量规模 | 耗时 | 分配 |
| --- | --- | --- |
| 构建组合 Insert **1000 实体** | **127 ms** | **463 MB**（Gen2 20,333 次） |

**非线性且极其昂贵**，还会引发 Gen2 GC。别单次塞几千条。

```csharp
// ✅ 用 SqlBatchInsertOptions 分窗
await executor.InsertBatchAsync(entities, new SqlBatchInsertOptions
{
    BatchSize = 200,        // 按实测调整；别用默认值硬扛大集合
    UseTransaction = true
});
```

### 3.6 Update 构建本身就是贵操作

`BuildUpdateCommand` Ratio **63.8×**（155 μs / 45 KB）。批量更新请优先用 `UpdateBatch`，并检查是否真的需要逐条构建命令。

## 4. 已知性能陷阱（有源码证据）

| 陷阱 | 位置 | 建议 |
| --- | --- | --- |
| **FreeSQL 异步查询会同步阻塞** | `FreeSqlAsyncQueryableProvider.CanExecute` 恒 `false` → `AsyncQueryableExecuter` 回退 `Task.FromResult(queryable.ToList())` | 高频异步路径改用仓储自带异步方法，或改 EF Core 支。详见 [能力矩阵 §4.3](../getting-started/能力矩阵.md) |
| **参数源解析每次反射 `GetProperty`** | `SqlParameterMap`、`DefaultSqlParameterSourceResolver`（`GetType().GetProperty(name, IgnoreCase)` + `GetValue`），**无缓存** | 对比 Mutation 侧的属性 getter 有编译委托缓存——参数绑定是相对短板，高频路径考虑预解析 |
| **程序集目录扫描默认不走缓存** | `DirectoryAssemblyFinder.FindAll()` 默认 `fromCache: false` → 重复 `Assembly.LoadFrom` | 调用方显式传 `true`；启动一次扫完就别再扫 |
| **DI 类型查找默认重扫** | `FinderBase.FindAll(fromCache: false)` 每次重扫并重填 `ItemsCache` | 同上；框架启动期之外避免调用 |
| **sync-over-async** | `BingViewResultExtensions`：`view.RenderAsync(...).GetAwaiter().GetResult()` | 唯一一处，避免在请求并发路径上调用视图渲染扩展 |
| 反射取异步结果 | `SqlTransactionScopeFactory`（`GetProperty("Result")`） | 仅 Provider 缺原生异步成员时的回退分支，一般走不到 |

> 说明：`SqlTransactionScopeFactory` 里看似 `.Result` 的代码（如 `return result.Result;`）**不是** sync-over-async——`result` 是自定义的 `SqlTransactionAsyncOperationResult<T>` 结构体，不是 Task。

## 5. 自己跑基准测试

工程位置：**`framework/tests/Bing.Data.Sql.Benchmarks/`**（`net8.0`，BenchmarkDotNet 0.14.0，入口 `internal static class Program` 定义在 `SqlMetadataBenchmarks.cs` 末尾）。

```bash
# 全量（交互式选择 / BenchmarkSwitcher）
dotnet run -c Release --project framework/tests/Bing.Data.Sql.Benchmarks

# CI 冒烟：只跑 SqlCiSmokeBenchmarks（DryJob）
dotnet run -c Release --project framework/tests/Bing.Data.Sql.Benchmarks -- --ci-smoke

# 端到端冒烟：只跑 SQLite 真实落库路径
dotnet run -c Release --project framework/tests/Bing.Data.Sql.Benchmarks -- --e2e-smoke
```

覆盖的场景包括：映射缓存命中/冷启动/容量满/LRU、表名解析、Builder 构建与 Clone、**重复渲染**、Lambda 根/IN/Join、Mutation Insert/Update/批次规划/Returning/SQL Server OUTPUT、聚合渲染、`AppendTo` vs `ToSql`、CTE 与参数标记扫描、调试 SQL 渲染，以及 9 个 SQLite 真实端到端场景（ToList / 流式 / 异步流 / 多对象映射 / 多结果集 / 取消 / Activity / Trace / DiagnosticListener）。

> ⚠ **`AGENTS.md` 是硬性要求**：「修改映射缓存、格式化热路径或 Builder 克隆逻辑时，**必须更新 `Bing.Data.Sql.Benchmarks` 的基线场景或说明不适用原因**」，且必须覆盖命中/未命中与重复渲染行为。改这些地方请一并更新基准。

## 6. 优化检查清单

- [ ] 实体映射缓存容量是否为你的实体/路由规模而调整过？（默认策略满容量后新路由**不再缓存**）
- [ ] 多租户/分表场景：租户标识是否编进了 `TableRouteKey`？（既影响性能也影响正确性）
- [ ] 有没有在循环里 `Clone()` Builder 或重建查询结构？
- [ ] 结构固定的查询是否做到了「构建一次、渲染多次」？
- [ ] 生产是否关闭了调试 SQL 渲染？
- [ ] 批量操作是否分批？（单次 ≥1000 条已证实会到 127 ms / 463 MB）
- [ ] FreeSQL 支的高频路径有没有误用 `IQueryable` 异步扩展？
- [ ] 是否避免在请求路径中触发程序集/类型扫描？
