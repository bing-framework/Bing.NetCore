## 3. FreeSQL 支 ⛔

这是全仓**唯一会"静默失败"**的缺口——其余缺口都会明确抛异常，只有它不会。

### 3.1 现状

`framework/src/Bing.FreeSQL/Bing/FreeSQL/FreeSqlAsyncQueryableProvider.cs`

- 实现 `Bing.Linq.IAsyncQueryableProvider`
- **65 处 `NotImplementedException`**（`ToListAsync` / `CountAsync` / `SumAsync` / `FirstOrDefaultAsync` …）
- `CanExecute<T>(IQueryable<T>)` **直接 `return false`**，不看入参

### 3.2 为什么不报错——降级链路

`Bing.Core/Bing/Linq/AsyncQueryableExecuter.cs:27` 找 Provider：

```csharp
protected virtual IAsyncQueryableProvider FindProvider<T>(IQueryable<T> queryable)
    => Providers.FirstOrDefault(p => p.CanExecute(queryable));
```

`CanExecute` 恒 `false` ⇒ `FindProvider` 恒返回 `null` ⇒ 每个异步方法走 `else` 分支：

```csharp
// AsyncQueryableExecuter.cs:40-42（ContainsAsync 为例，其余方法同构）
return provider != null
    ? provider.ContainsAsync(queryable, item, cancellationToken)
    : Task.FromResult(queryable.Contains(item));   // ← 同步执行，包成已完成的 Task
```

**结论**：对 `IQueryable` 调异步扩展方法，**代码能编译、能跑、不抛异常、日志干净**，但数据库查询在**调用线程上同步执行**。在 ASP.NET Core 里等于白白占住一个线程池线程；高并发下表现为吞吐下降而**没有任何错误信号**。

### 3.3 与其它缺口的性质差异

| 支 | 缺口的暴露方式 | 可发现性 |
| --- | --- | --- |
| Dapper / `Bing.Data.Sql` | `throw NotSupportedException` | ✅ 一调用就报 |
| **FreeSQL 异步** | **无信号，行为静默改变** | ❌ 只能靠压测或读源码 |

`docs/FAQ与排错.md` Q11 与 [能力矩阵 §4.3](../getting-started/能力矩阵.md) 都记有这条，排查方法见本文 §11。

### 3.4 同一支的其它缺口

- **仅 MySql**：只有 `Bing.FreeSQL.MySql` 一个 Provider 工程
- **无迁移**：未发现 `Migrate()` / `SyncStructure()` 调用，表结构变更需自行处理
- **无多租户过滤**：FreeSQL 支没有任何租户相关 `GlobalFilter`

## 4. Dapper + `Bing.Data.Sql` ⛔

这一支的缺口**框架自己声明了**，不需要外部推断。

### 4.1 框架自带的"未实现"口径

`framework/src/Bing.Data.Sql/Bing/Data/Sql/SqlCapabilityFailure.cs` 定义了拒绝原因枚举：

| 枚举值 | 含义 | 是否算缺陷 |
| --- | --- | --- |
| `DatabaseUnsupported = 0` | 当前数据库语义或版本不支持该能力 | ❌ 不算（DB 的限制） |
| **`ProviderImplementationGap = 1`** | **数据库支持该能力，但 Bing Provider 尚未实现** | ✅ **算** |
| `ProviderProfileMissing = 2` | Provider 未声明统一能力档案 | ⚠️ 配置缺失 |
| `ProviderProfileMismatch = 3` | 能力声明与执行对象/上下文不一致 | ⚠️ 声明与实现打架 |

全仓 `SqlCapabilityFailure.Create(...)` 共 **37 处**调用，分布：

| 原因 | 处数 |
| --- | --- |
| `DatabaseUnsupported` | 11 |
| **`ProviderImplementationGap`** | **10** |
| `ProviderProfileMissing` | 8 |
| `ProviderProfileMismatch` | 8 |

### 4.2 那 10 处 `ProviderImplementationGap` 明细

**9 处在 `framework/src/Bing.Dapper.Core/Bing/Data/Sql/SqlExecutorBase.cs`**：

| 行 | 所属成员 | 能力名 | 触发条件 |
| --- | --- | --- | --- |
| 539 | `CreateUpdateBatchCommands<TEntity>` | `BatchUpdate` | 策略为 `ProviderOptimized` 但无法生成优化命令 |
| 562 | `CreateProviderOptimizedUpdateBatchCommands<TEntity>` | `BatchUpdate` | Mutation Builder 未实现 `ISqlBatchUpdateRenderContextBuilder` |
| 631 | `RenderProviderOptimizedUpdateCommand<TEntity>` | `BatchUpdate` | 同上（另一条渲染路径） |
| 649 | `ResolveBatchUpdateRenderer` | `BatchUpdate` | DI 中未注册该 Provider 的优化批量 Update 渲染器 |
| 703 | `CreateDeleteBatchCommands<TEntity>` | `BatchDelete` | 未实现 `ISqlCombinedDeleteMutationBuilder`，且策略非 `Auto` |
| 846 | `CreateCombinedInsertBatchCommands<TEntity>` | `MultiRowValues` | Provider Profile 声明 `SupportsMultiRowValues == false` |
| 853 | 同上 | `BatchInsert` | 未实现 `ISqlCombinedInsertMutationBuilder`，且策略非 `Auto` |
| 869 | 同上（`MaxSqlLength` 分批路径） | `BatchInsert` | 同上 |
| 886 | 同上（二分查找批次大小路径） | `BatchInsert` | 同上 |

**1 处在 `SqlTransactionScopeFactory.cs:1175`**，经由私有方法 `CreateImplementationGap(operation, providerKey)`：Provider **声明**支持原生异步事务，但运行时对象**未提供**对应成员。异常消息同时带 `[ProviderImplementationGap][ProfileMismatch]` 两个标签（`Transaction:{operation}`）。

> ✅ **一个可实际利用的事实**：9 处里有 8 处**只在显式策略下才抛**。`SqlBatchDeleteStrategy.Auto`（L700）与 `SqlBatchInsertStrategy.Auto`（L850）会**自动降级为逐条命令**并正常返回，不抛异常。也就是说批量级 `BatchInsert`/`BatchDelete` 在默认策略下是可用的，只是失去 provider 侧优化；**只有你显式要求 Provider-optimized 时才会拿到 `NotSupportedException`**。
>
> 例外是 **L846**：它由 Provider Profile 的 `SupportsMultiRowValues` 决定，在 `Auto` 分支之前就抛，**不受策略影响**。

### 4.3 Lambda 多源查询 6 处不支持

`framework/src/Bing.Data.Sql/Bing/Data/Sql/Queries/SqlLambdaQueryCore.cs`：

| 行 | 所属成员 | 不支持的能力 |
| --- | --- | --- |
| 656 | `ReplaceSelect(string columns)` | 原子投影替换 |
| 701 | `GetFromClause(...)` | Lambda **多源 From** |
| 710 | `GetJoinClause(...)` | Lambda **多源 Join** |
| 717 | `GetSelectClause(...)` | Lambda **多源 Select** |
| 724 | `GetGroupByClause(...)` | Lambda **多源 Group By** |
| 731 | `GetOrderByClause(...)` | Lambda **多源 Order By** |

即：**Lambda 风格的多表查询整体未实现**。多表场景请改用 Fluent / 原生 SQL 路径，或走 EF Core 支。

### 4.4 性质说明

这一支的缺口**全部是 fail fast**——调用即抛 `NotSupportedException`，并附带结构化的能力名与 Provider Key（存在 `Exception.Data` 里，可程序化读取）。这一点比 FreeSQL 支诚实得多，**不会静默出错**。

完整的"明确不支持能力"清单另见 [能力矩阵 §5.5](../getting-started/能力矩阵.md)（9 条）。

### 7.1 ⛔ 领域事件：收集了，但**没有任何地方派发**

这是本轮新发现的一处**框架级机制缺口**，性质与 §3 的 FreeSQL 异步类似——**不报错**。

**证据链**：

| 环节 | 位置 | 状态 |
| --- | --- | --- |
| 聚合根收集事件 | `Bing.Ddd.Domain/Bing/Domain/Entities/BasicAggregateRoot.cs:61,67,78,84`（容器在 `:40`） | ✅ `AddDomainEvent` / `GetDomainEvents` / `RemoveDomainEvent` / `ClearDomainEvents` 都实现了 |
| 派发器实现 | `Bing.Ddd.Domain/…/Entities/Events/DomainEventDispatcher.cs:84-98` | ✅ `DispatchAsync(DomainEvent)` 实现了（DI 解析处理器 + 方法反射调用） |
| 派发器注册 | `Bing.Ddd.Domain/…/Events/Extensions.Service.cs:10`（扩展）／`:47`（核心，`:49,:50,:51`） | ✅ **已注册**；生产注册点 2 处：`Bing.Admin/Modules/AppModule.cs:74`、`Bing.Admin.FreeSQL/Modules/AppModule.cs:68` |
| **调用 `DispatchAsync` 的地方** | 全仓仅 3 处：接口声明 `IDomainEventDispatcher.cs:39`、实现 `DomainEventDispatcher.cs:84`、测试 `framework/tests/Bing.Ddd.Domain.Tests/…/DomainEventHandlerTest.cs:63` | ❌ **生产代码中零调用** |
| **UoW 是否排空聚合根事件** | EF `UnitOfWorkBase` 的 `PublishEventsAsync`（`Bing.EntityFrameworkCore/Core/UnitOfWorkBase.cs:799-802`） | ❌ **是个空钩子**：`protected virtual Task PublishEventsAsync() => Task.CompletedTask;`——为这件事预留了位置，但没实现 |
| FreeSQL / `Bing.Uow` 是否排空 | FreeSQL `UnitOfWorkBase`（`Commit:179`、`CommitAsync:202`、`SaveChanges:224`、`SaveChangesAsync:273`）；`Bing.Uow.UnitOfWorkManager`（`Commit:21`、`CommitAsync:31`） | ❌ 全无 `DomainEvent` 代码 |

**运行时后果**：`AddDomainEvent(...)` 把事件塞进 `_domainEvents` 列表后，**这个列表永远不会被排空**，处理器的 `HandleAsync` 永远不会执行。

补充一条：`ClearDomainEvents()` 在**生产代码中从未被调用**（全仓仅出现于测试 `AggregateRootDomainEventsTest.cs:93`）。所以准确说法不是"清了却没派发"，而是**既没清也没派发**——事件一直躺在内存里，随 `DbContext` 一起被丢弃。

**仓库内的真实影响面**：

- `Bing.Admin.Systems.Domain/Models/User.cs:83` 的 `AddLoginLog` 里 `AddDomainEvent(new UserLoginDomainEvent(...))`
- 对应的 `Bing.Admin.EventHandlers/…/UserLoginDomainEventHandler.cs:12,31` 是**死代码**

> ⚠️ **但登录日志本身没有坏**——`SecurityService.SignInAsync`（`Bing.Admin.Service/Implements/SecurityService.cs:98`）走的是**另一条路**：发布 CAP 消息事件 `UserLoginMessageEvent(..., send: false)`，`send:false` 表示延迟到 `UnitOfWork.CommitAsync()`（:105）时经 Outbox 投递，由 `UserLoginLogMessageEventHandler.UserLoginAsync`（`…/UserLoginLogMessageEventHandler.cs:63`）消费后写入。**同一次登录实际上有两套并行的处理器，只有 CAP 那套是活的。**
>
> 这正是这条缺口最隐蔽的地方：**功能表面正常，所以没人会发现领域事件机制是空的**。

**使用建议**：不要依赖 `AddDomainEvent` 传播事件。要发事件请直接用 `ISimpleEventBus`（本地）或 `IMessageEventBus`（CAP）。领域事件相关的建模说明见 [领域建模指南 §5](../guides/领域建模指南.md)，四套事件机制的完整对照见 [事件与消息文档](事件与消息文档.md)。

### 7.2 ⛔ CAP：`send:false` 在事务外会**静默丢事件**

这是另一处**不报错**的机制缺口，与 §7.1 同类但影响面更广——因为它出在**现行在用**的通道上。

`MessageEventBus.PublishAsync` 对 `Send` 的处理（`Bing.Events/Cap/MessageEventBus.cs:64-77`）：

- `Send = true` → 立即 `Publisher.PublishAsync(...)`（`:70` → `:90`）
- `Send = false` → **完全不调用 `Publisher`**，只 `TransactionActionManager.Register(...)`（`:73-76`）把动作挂起

挂起的动作由**工作单元的提交路径**执行（EF `UnitOfWorkBase.cs:465` / `:590`；FreeSQL `UnitOfWorkBase.cs:243` / `:296`）。但 `SaveChanges` 只在 **`TransactionActionManager.Count > 0`** 时才进入 `TransactionCommit` 分支；`Count == 0` 时直接 `base.SaveChanges`，**不会调用 `CommitAsync`**（EF `:434-436`、`:557-560`；FreeSQL `:227-229`、`:277-279`）。

| 场景 | 结果 |
| --- | --- |
| `send:false` + 后续有 `UnitOfWork.CommitAsync()` | ✅ 正常：业务写入与消息入箱**同一事务**（Outbox 一致性） |
| `send:false` + **整条链路无任何 UoW 提交** | ❌ **注册的动作永不执行，事件静默丢失**——不报错、无日志、无兜底 |

源码中**没有**"不在事务中则降级为立即发送"的逻辑。

**真实风险点**：admin 的 `SecurityService.SignInAsync` 恰好是"`send:false` 后紧跟 `CommitAsync()`"（`SecurityService.cs:98-104` → `:105`）**才**能正常工作。**只要那一行 `CommitAsync()` 被删掉或改位置，登录日志就会静默失效，而登录功能本身不报错。**

**使用建议**：用 `send:false` 就必须确保后面有提交；不确定时用 `send:true`（失去原子性但不会丢）。完整链路见 [事件与消息文档 §4.4](事件与消息文档.md)。

## 8. Provider 覆盖：Oracle 与 Doris ❓

仓库对 Provider 状态有**官方口径**（[docs/sql/provider-capabilities.md](../sql/provider-capabilities.md)）：

| Provider | 事务 | Streaming | Batch / Returning | Procedure / Function | OUT 参数 | RC 定位 |
| --- | --- | --- | --- | --- | --- | --- |
| SQLite | 支持 | 支持 | 按 SQLite 语法 | **不支持存储过程** | 不支持 | 核心 Provider |
| MySQL | 支持 | 支持 | Batch 支持；Returning 不适用 | 存储过程 | **OUT/INOUT 合同需真实运行** | 核心 Provider |
| PostgreSQL | 支持 | 支持 | Batch、UPDATE FROM、DELETE USING、RETURNING | 文本 SQL 可调用 Function；**`Procedure()` 路径按数据库语义拒绝** | 不伪装为 SQL Server / MySQL OUT | 核心 Provider |
| SQL Server | 支持（同步回退） | 支持 | Batch、OUTPUT | 存储过程 | OUT / INOUT / ReturnValue | 核心 Provider |
| **Oracle** | 以当前安全 fixture 为准 | 同左 | **Limited** | **未完成安全 fixture 时不得声明支持** | 同左 | **Non-blocking** |
| **Doris** | 只读 | 以只读合同为准 | 不要求 Mutation parity | 不要求 Procedure parity | 不要求 | **Non-blocking / ReadOnly** |

关键点：**Oracle 当前口径是"尚未达到可声明支持的程度"**（安全 fixture 未完成），**Doris 定位为只读**，二者均属 `Non-blocking`——即**不阻塞 RC，但也不构成"已支持"**。

## 11. 如何自行复核

以上结论都可以独立验证。

**① 重跑未完成标记扫描**——按 §1 的口径在仓库根目录执行，统计各标记的文件分布。注意排除 `obj` / `bin`，并把 `framework/tests` 单独看待。

**② 读框架自认的缺口**——`Bing.Data.Sql` 的能力缺口不要靠 grep 猜，直接读：

```
framework/src/Bing.Data.Sql/Bing/Data/Sql/SqlCapabilityFailure.cs
```

`SqlCapabilityFailureReason.ProviderImplementationGap` 就是权威口径；再用 `SqlCapabilityFailure.Create` 反查调用点（本文 §4.2 的 10 处即由此得出）。

**③ 确认工程是否被引用**——对 `Bing.Events.Cap.MySql`、`Bing.EventBus*`、`Bing.MultiTenancy*` 搜索 `.csproj` / `.props` 里的 `ProjectReference` / `PackageReference`，并**逐行确认是否被注释**（这是最容易误判的一点：`Bing.Events.Cap.MySql` 的引用存在，但整行是注释）。

**④ 查 Provider 验证实况**——不要只读声明文档，去看 `artifacts/` 下最新的 `provider-capability-matrix.md`，按修改时间取最新一份，看 `Runs` 列有没有运行 ID。

**⑤ 排查静默降级**——如果怀疑 FreeSQL 异步查询在同步执行：在仓储方法入口打日志，观察查询执行期间调用线程是否被阻塞；或直接对 `IQueryable` 调 `ToListAsync` 并检查返回的 `Task` 是否**立即**处于 `RanToCompletion`（同步降级的典型特征）。

## 12. 缺口的三种处置方式

发现缺口后，通常只有三条路。**本文不替你选，也不改动任何代码**：

| 处置 | 适用场景 | 对应动作 |
| --- | --- | --- |
| **补实现** | 该能力对使用者是刚需（如 admin 的 Identity 注册、迁移与种子） | 改代码 + 按 `AGENTS.md` 的测试门槛补测试 |
| **显式声明** | 能力短期内不做，但要让使用者知道（如 Dapper 的 `ProviderImplementationGap`） | 保持 fail fast，别让它退化成静默降级；文档标注状态徽章 |
| **标记废弃** | 已有替代实现且无人引用（如 `Bing.EventBus.Abstractions`、`Bing.Events.Cap.MySql`） | 明确废弃或移除，避免持续误导 |

> 判断依据应是**使用意图**，而不是文档。§6 的注释、§7 的死代码，都需要维护者确认当初是有意停用还是已经废弃——这是本文刻意留白的地方。
