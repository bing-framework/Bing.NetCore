## 3. FreeSQL 支：通用异步查询边界

FreeSQL 的通用 IQueryable 异步入口采用同步回退，并非数据库异步 I/O；不再以占位异常结束。其它事件、AOP 等装配路径也有各自边界，见对应模块限制。

### 3.1 现状

`framework/src/Bing.FreeSQL/Bing/FreeSQL/FreeSqlAsyncQueryableProvider.cs`

- 实现 `Bing.Linq.IAsyncQueryableProvider`
- `CanExecute<T>(IQueryable<T>)` 保持 **`return false`**，避免抢占数据库 Provider
- 元素、数量、聚合、列表和数组方法执行取消检查后同步 LINQ，并包装为已完成的 `Task`

### 3.2 为什么不报错——降级链路

`Bing.Core/Bing/Linq/AsyncQueryableExecuter.cs:27` 找 Provider：

```csharp
protected virtual IAsyncQueryableProvider FindProvider<T>(IQueryable<T> queryable)
    => Providers.FirstOrDefault(p => p.CanExecute(queryable));
```

`CanExecute` 恒 `false` ⇒ `FindProvider` 恒返回 `null` ⇒ 通用执行器走 `else` 分支：

```csharp
// AsyncQueryableExecuter.cs:40-42（ContainsAsync 为例，其余方法同构）
return provider != null
    ? provider.ContainsAsync(queryable, item, cancellationToken)
    : Task.FromResult(queryable.Contains(item));   // ← 同步执行，包成已完成的 Task
```

**结论**：对 `IQueryable` 调异步扩展方法，数据库查询仍在**调用线程上同步执行**。这保证 API、取消和 LINQ 异常语义，但不提供异步 I/O；在 ASP.NET Core 里会占用线程池线程，高并发下可能拖累吞吐。需要真正异步 I/O 时使用仓储原生异步方法或 EF Core。直接回归见 `FreeSqlAsyncQueryableProviderTest`。

### 3.3 与其它缺口的性质差异

| 支 | 缺口的暴露方式 | 可发现性 |
| --- | --- | --- |
| Dapper / `Bing.Data.Sql` | `throw NotSupportedException` | ✅ 一调用就报 |
| **FreeSQL 异步** | **无信号，行为静默改变** | ❌ 只能靠压测或读源码 |

`docs/FAQ与排错.md` Q11 与 [能力矩阵 §4.3](../getting-started/能力矩阵.md) 都记有这条，排查方法见本文 §11。

### 3.4 同一支的其它缺口

- **仅 MySql**：只有 `Bing.FreeSQL.MySql` 一个 Provider 工程
- **无迁移**：未发现 `Migrate()` / `SyncStructure()` 调用，表结构变更需自行处理
- **无多租户过滤**：FreeSQL 支没有任何租户相关 `GlobalFilter`

## 4. Dapper + `Bing.Data.Sql` ⛔

这一支的缺口**框架自己声明了**，不需要外部推断。

### 4.1 框架自带的"未实现"口径

`framework/src/Bing.Data.Sql/Bing/Data/Sql/SqlCapabilityFailure.cs` 定义了拒绝原因枚举：

| 枚举值 | 含义 | 是否算缺陷 |
| --- | --- | --- |
| `DatabaseUnsupported = 0` | 当前数据库语义或版本不支持该能力 | ❌ 不算（DB 的限制） |
| **`ProviderImplementationGap = 1`** | **数据库支持该能力，但 Bing Provider 尚未实现** | ✅ **算** |
| `ProviderProfileMissing = 2` | Provider 未声明统一能力档案 | ⚠️ 配置缺失 |
| `ProviderProfileMismatch = 3` | 能力声明与执行对象/上下文不一致 | ⚠️ 声明与实现打架 |

### 4.2 `ProviderImplementationGap` 的触发边界

主要位置：`framework/src/Bing.Dapper.Core/Bing/Data/Sql/SqlExecutorBase.cs` 与 `SqlTransactionScopeFactory.cs`。

| 路径 | 触发条件与处理 |
| --- | --- |
| `BatchUpdate` | 显式要求优化策略，但缺少批量渲染上下文、渲染器或不适用当前上下文。 |
| `BatchDelete` / `BatchInsert` | 缺少组合 Mutation Builder；`Auto` 可回退逐条命令，显式组合策略拒绝。 |
| `MultiRowValues` | Profile 不支持多行 Values 时拒绝，不能依靠 `Auto` 绕过该边界。 |
| `Returning` | 冻结命令或当前执行器的 Profile 未声明支持；是否属于数据库限制由 FailureReason 决定。 |
| 原生异步事务 | Provider 声明支持，但实际运行时对象缺少相应成员；拒绝并带声明不匹配标签。 |

这些是条件性拒绝，不能把调用点总数等同于所有内置 Provider 均未实现。统一 Builder 已支持 PostgreSQL/SQLite 的 Returning 与 SQL Server 的 Output；应通过 `ExecuteReturning` / `ExecuteReturningAsync` 获取结果。`SqlExecutorBase` 普通执行入口拒绝带 Returning 的命令，避免丢弃结果集。详见[变更 API 生命周期](../sql/sql-mutation-api-lifecycle.md)。

### 4.3 Lambda 多源查询的实际边界

`framework/src/Bing.Data.Sql/Bing/Data/Sql/Queries/SqlLambdaQuery.cs` 与 `SqlLambdaQueryCore.cs` 已支持连续 `From`、二元 Join、Select、Where、GroupBy、Having 和 OrderBy；可重复二元 Join 组合更多来源。

| 项目 | 当前行为 |
| --- | --- |
| 公开投影参数 | 最多两个来源参数；更多来源通过重复二元 Join 或派生表组合。 |
| DTO 绑定 | 接受成员初始化表达式，绑定须是当前 Lambda 参数的直接成员；派生表只暴露已投影成员。 |
| 多源 SPI | 默认 Clause 已实现；外部 Provider 缺少 `ISqlMultiSource*` 时快速失败。 |
| 原子投影替换 | 当前统一 `SqlBuilderBase` 支持；外部 Builder 不继承该基类时拒绝。 |
| Right/Full Join | 受具体 Provider 能力限制。 |
| Dapper 多映射终结方法 | `SqlLambdaQuery` 当前未提供；需要该入口时使用 Fluent/文本 Query。 |

不能再把能力检查中的异常分支解释为“多表查询整体未实现”。接口和示例见[Lambda 查询用法](../sql/sqlquery-lambda-usage.md)，职责测试位于 `framework/tests/Bing.Data.Sql.Tests/SqlQueryLifecycleTest.cs` 和 `Builders/Clauses/SqlClauseContractTest.cs`。

### 4.4 性质说明

这一支的缺口**全部是 fail fast**——调用即抛 `NotSupportedException`，并附带结构化的能力名与 Provider Key（存在 `Exception.Data` 里，可程序化读取）。这一点比 FreeSQL 支诚实得多，**不会静默出错**。

完整的"明确不支持能力"清单另见 [能力矩阵 §5.5](../getting-started/能力矩阵.md)（9 条）。

### 7.1 领域事件：已接入工作单元，仍不是可靠消息

此前“收集后无人派发”的缺口已经修复。EF Core 的 `PrepareDomainEvents` 和 FreeSQL 的 `RegisterPendingDomainEvents` 会创建 `DomainEventDispatchSession`，把派发动作登记到事务动作管理器；会话成功完成后清理事件，并以有限轮次处理处理器新增的领域事件。

当前仍需注意：

- 领域事件是进程内处理，不提供 CAP 的持久化、重试和跨节点投递。
- `PublishEventsAsync` 仍是保存后的可选通知钩子，其空实现不代表领域事件未派发。
- 处理器产生无限事件链会在轮次上限处失败，不会无限递归。
- 可靠集成事件仍需在业务事务中登记 CAP 出箱，并由消费端保证幂等。

实现与使用边界见[事件与一致性](../modules/events-and-consistency.md)和[领域建模指南 §4](../guides/领域建模指南.md)。

### 7.2 ⛔ CAP：`send:false` 在事务外会**静默丢事件**

这是另一处**不报错**的机制缺口，与 §7.1 同类但影响面更广——因为它出在**现行在用**的通道上。

`MessageEventBus.PublishAsync` 对 `Send` 的处理（`Bing.Events/Cap/MessageEventBus.cs:64-77`）：

- `Send = true` → 立即 `Publisher.PublishAsync(...)`（`:70` → `:90`）
- `Send = false` → **完全不调用 `Publisher`**，只 `TransactionActionManager.Register(...)`（`:73-76`）把动作挂起

挂起的动作由**工作单元的提交路径**执行（EF `UnitOfWorkBase.cs:465` / `:590`；FreeSQL `UnitOfWorkBase.cs:243` / `:296`）。但 `SaveChanges` 只在 **`TransactionActionManager.Count > 0`** 时才进入 `TransactionCommit` 分支；`Count == 0` 时直接 `base.SaveChanges`，**不会调用 `CommitAsync`**（EF `:434-436`、`:557-560`；FreeSQL `:227-229`、`:277-279`）。

| 场景 | 结果 |
| --- | --- |
| `send:false` + 后续有 `UnitOfWork.CommitAsync()` | ✅ 正常：业务写入与消息入箱**同一事务**（Outbox 一致性） |
| `send:false` + **整条链路无任何 UoW 提交** | ❌ **注册的动作永不执行，事件静默丢失**——不报错、无日志、无兜底 |

源码中**没有**"不在事务中则降级为立即发送"的逻辑。

**真实风险点**：admin 的 `SecurityService.SignInAsync` 恰好是"`send:false` 后紧跟 `CommitAsync()`"（`SecurityService.cs:98-104` → `:105`）**才**能正常工作。**只要那一行 `CommitAsync()` 被删掉或改位置，登录日志就会静默失效，而登录功能本身不报错。**

**使用建议**：用 `send:false` 就必须确保后面有提交；不确定时用 `send:true`（失去原子性但不会丢）。完整链路见 [事件与消息文档 §4.4](事件与消息文档.md)，可照抄的收发手册见 [分布式事件使用说明](../guides/分布式事件使用说明.md) §4。

> **附**：还有一条同源的隐性依赖——登记动作**忽略传入的 `IDbTransaction`**（`MessageEventBus.cs:73-76` 的 lambda 参数从未被使用），是否写发件箱完全取决于 **CAP 自己的环境事务**是否已开启。所以"基类工作单元把事务递进去"并不等于接上了 Outbox，必须像 `AdminUnitOfWork` 那样用 `Database.BeginTransaction(publisher, autoCommit: false)` 先把 CAP 的环境事务立起来。

## 8. Provider 覆盖：Oracle 与 Doris ❓

仓库对 Provider 状态有**官方口径**（[docs/sql/provider-capabilities.md](../sql/provider-capabilities.md)）：

| Provider | 事务 | Streaming | Batch / Returning | Procedure / Function | OUT 参数 | RC 定位 |
| --- | --- | --- | --- | --- | --- | --- |
| SQLite | 支持 | 支持 | 按 SQLite 语法 | **不支持存储过程** | 不支持 | 核心 Provider |
| MySQL | 支持 | 支持 | Batch 支持；Returning 不适用 | 存储过程 | **OUT/INOUT 合同需真实运行** | 核心 Provider |
| PostgreSQL | 支持 | 支持 | Batch、UPDATE FROM、DELETE USING、RETURNING | 文本 SQL 可调用 Function；**`Procedure()` 路径按数据库语义拒绝** | 不伪装为 SQL Server / MySQL OUT | 核心 Provider |
| SQL Server | 支持（同步回退） | 支持 | Batch、OUTPUT | 存储过程 | OUT / INOUT / ReturnValue | 核心 Provider |
| **Oracle** | 以当前安全 fixture 为准 | 同左 | **Limited** | **未完成安全 fixture 时不得声明支持** | 同左 | **Non-blocking** |
| **Doris** | 只读 | 以只读合同为准 | 不要求 Mutation parity | 不要求 Procedure parity | 不要求 | **Non-blocking / ReadOnly** |

关键点：**Oracle 当前口径是"尚未达到可声明支持的程度"**（安全 fixture 未完成），**Doris 定位为只读**，二者均属 `Non-blocking`——即**不阻塞 RC，但也不构成"已支持"**。

## 11. 如何自行复核

以上结论都可以独立验证。

**① 重跑未完成标记扫描**——按 §1 的口径在仓库根目录执行，统计各标记的文件分布。注意排除 `obj` / `bin`，并把 `framework/tests` 单独看待。

**② 读框架自认的缺口**——`Bing.Data.Sql` 的能力缺口不要靠 grep 猜，直接读：

```
framework/src/Bing.Data.Sql/Bing/Data/Sql/SqlCapabilityFailure.cs
```

`SqlCapabilityFailureReason.ProviderImplementationGap` 表示声明的实现缺口；再反查调用点、Profile 与实际触发条件（见 §4.2），不要仅统计异常分支数量。

**③ 确认工程是否被引用**——对 `Bing.Events.Cap.MySql`、`Bing.EventBus*`、`Bing.MultiTenancy*` 搜索 `.csproj` / `.props` 里的 `ProjectReference` / `PackageReference`，并**逐行确认是否被注释**（这是最容易误判的一点：`Bing.Events.Cap.MySql` 的引用存在，但整行是注释）。

**④ 查 Provider 验证实况**——不要只读声明文档，去看 `artifacts/` 下最新的 `provider-capability-matrix.md`，按修改时间取最新一份，看 `Runs` 列有没有运行 ID。

**⑤ 排查静默降级**——如果怀疑 FreeSQL 异步查询在同步执行：在仓储方法入口打日志，观察查询执行期间调用线程是否被阻塞；或直接对 `IQueryable` 调 `ToListAsync` 并检查返回的 `Task` 是否**立即**处于 `RanToCompletion`（同步降级的典型特征）。

## 12. 缺口的三种处置方式

发现缺口后，通常只有三条路。**本文不替你选，也不改动任何代码**：

| 处置 | 适用场景 | 对应动作 |
| --- | --- | --- |
| **补实现** | 该能力对使用者是刚需（如 admin 的 Identity 注册、迁移与种子） | 改代码 + 按 `AGENTS.md` 的测试门槛补测试 |
| **显式声明** | 能力短期内不做，但要让使用者知道（如 Dapper 的 `ProviderImplementationGap`） | 保持 fail fast，别让它退化成静默降级；文档标注状态徽章 |
| **标记废弃** | 已有替代实现且无人引用（如 `Bing.EventBus.Abstractions`、`Bing.Events.Cap.MySql`） | 明确废弃或移除，避免持续误导 |

> 判断依据应是**使用意图**，而不是文档。§6 的注释、§7 的死代码，都需要维护者确认当初是有意停用还是已经废弃——这是本文刻意留白的地方。
