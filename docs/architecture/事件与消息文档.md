# 事件与消息

> **适用版本**：框架 `7.0.0`（`version.props`）｜ 目标框架：类库 `netstandard2.0`、Web / 应用 `net6.0`｜ 内容核对：2026-09-18｜ 版本历史见 [发行说明](../ReleaseNotes.md)

> **一句话定位**：本框架有**四套**互不相通的事件机制，其中两套存在同名类型、一套**不会派发**、一套是遗留。本文回答**"我该用哪一套、怎么用、哪一套其实是死的"**。

> 相关文档：[子系统深挖 §1](子系统深挖.md)（CAP 出箱的实现细节）、[横切能力文档 §5](../guides/横切能力文档.md)（两套包的选型）、[领域建模指南 §4](../guides/领域建模指南.md)（领域事件与聚合根）、[recipes/cap-event-outbox.md](../guides/recipes/cap-event-outbox.md)（可运行闭环）、[功能完成度 §7.1](功能完成度.md)（缺口登记）。

## 1. 四套机制全景

| | 机制 I<br>进程内事件 | 机制 II<br>CAP 集成事件 | 机制 III<br>领域事件 | 机制 IV<br>遗留总线 |
| --- | --- | --- | --- | --- |
| **核心契约** | `ISimpleEventBus` | `IMessageEventBus` | `DomainEvent` + `IDomainEventDispatcher` | `IEventBus` / `ILocalEventBus` / `IDistributedEventBus` |
| **命名空间** | `Bing.Events` | `Bing.Events.Messages` | `Bing.Ddd.Domain` 下的 `...Entities.Events` | `Bing.EventBus.*` |
| **所在包** | `Bing.Core` | `Bing.Core` + `Bing.Events` | `Bing.Ddd.Domain` | `Bing.EventBus` |
| **传递范围** | 同一进程 | **跨服务**（RabbitMQ 等） | 同一聚合根 → 期望进程内 | 进程内 / 分布式（未接通） |
| **持久化** | 无 | **`cap.published` / `cap.received`** | 无 | 无 |
| **注册入口** | `AddDefaultEventBus()` | `AddCapEventBus(...)` | `AddDomainEventDispatcher(...)` | ⚠ **无** |
| **状态** | 🔶 已实现，**全仓无调用者** | ✅ **现行，admin 在用** | ⛔ **派发器已注册，但零调用** | ❌ **遗留，勿用** |

**它们互不相通**——这不是夸张：

- 机制 III 的 `DomainEvent` 是纯 `abstract class`，**不实现**机制 I/II 的 `Bing.Events.IEvent`（`Bing.Core/Bing/Events/IEvent.cs:6`）。领域事件派发走的是 `IDomainEventHandlerTypeStore` + `IDomainHandlerFactory`，**完全不经过任何事件总线**。
- 机制 IV 与机制 I/II **存在同名类型**（`IEventBus`、`IMessageEventBus`、`IEvent`、`IEventHandler`），同时 `using` 会编译失败（见 §6.2）。

## 2. 先记住这 6 条结论

| # | 结论 | 详见 |
| --- | --- | --- |
| 1 | **领域事件收集了，但没有任何地方派发** —— `DispatchAsync` 在生产代码中**零调用** | §5.4 |
| 2 | **工作单元不会帮你排空领域事件** —— EF 支的 `PublishEventsAsync` 是**空钩子** | §5.5 |
| 3 | **CAP 的 `send:false` 若在事务外发布，事件会静默丢失** —— 没有兜底 | §4.4 |
| 4 | 机制 I（`ISimpleEventBus`）**已实现但全仓无人调用** | §3.4 |
| 5 | `[EventHandler]` **继承自 CAP 的 `TopicAttribute`**，与 `[CapSubscribe]` 等价 | §4.7 |
| 6 | 框架**不提供**消费端幂等辅助，**也没有 CAP 的测试** | §4.6 |

如果你只想要一个能跑的组合：**用机制 II（CAP），领域事件先别用**（除非自己接派发，见 §5.7）。

## 3. 机制 I：`ISimpleEventBus`（进程内事件）

| `Event` | `: IEvent`，构造时填 `Guid` + `DateTime.Now`，`GetEventName` 读 `[EventName]` 特性 | `Bing.Core/Bing/Events/Event.cs:9-65` |

### 3.2 注册入口

```csharp
// Bing.Events/Default/Extensions.Service.cs:17
public static IServiceCollection AddDefaultEventBus(this IServiceCollection services);

// 内部注册（:19-21）：
//   IEventHandlerManager → EventHandlerManager   （Singleton）
//   ISimpleEventBus      → EventBus              （Singleton）
//   IEventBus            → EventBus              （Singleton）
```

### 3.3 发布链路

```
ISimpleEventBus.PublishAsync(evt)
  → Default.EventBus.PublishAsync          // Default/EventBus.cs:29-40
       → IEventHandlerManager.GetHandlers<TEvent>()
       → foreach: await handler.HandleAsync(evt)      // 顺序 await，串行
```

处理器从哪来：`EventHandlerManager` 走 **`ServiceLocator.Instance.GetServices<IEventHandler<TEvent>>()`**（`Default/EventHandlerManager.cs:16`）——是 **DI 解析**，不是反射扫类。所以处理器必须先注册进容器。

⚠ **没有任何事务参与**。`PublishAsync` 逐个 `await`，**前一个处理器抛异常，后面的不会执行**，且已执行的无法回滚。

### 3.4 ⚠ 全仓无调用者

`AddDefaultEventBus` 在整个仓库里**只出现在它自己的定义处**（`Default/Extensions.Service.cs:17`）——没有一个宿主调用它，也没有任何生产代码注入 `ISimpleEventBus`。

也就是说：**机制 I 是一套实现完整、但当前无人使用的通道。** 想用的话自己调 `AddDefaultEventBus()` 即可，它本身是好的。

### 4.2 注册入口：`AddCapEventBus`

`Bing.Events/Cap/Extensions.Service.cs:22-31` **完整实现**：

```csharp
public static IServiceCollection AddCapEventBus(
    this IServiceCollection services,
    Action<CapOptions> action,
    Action<CapBuilder> builderSetup = null)
{
    services.TryAddSingleton<IEventHandlerManager, EventHandlerManager>();
    services.TryAddSingleton<ISimpleEventBus, Default.EventBus>();     // ← 顺带把机制 I 也注册了
    services.TryAddScoped<IMessageEventBus, MessageEventBus>();
    services.TryAddScoped<IEventBus, EventBus>();                      // ← Cap.EventBus（组合总线）
    var builder = services.AddCap(action);
    builderSetup?.Invoke(builder);
    return services;
}
```

注意第 2 行：**调 `AddCapEventBus` 会连带注册机制 I**。所以宿主里 `ISimpleEventBus` 是解析得到的——只是没人用。

### 4.3 `Bing.Events/Cap/` 的 5 个文件

| 文件 | 职责 |
| --- | --- |
| `EventBus.cs` | **组合总线**。`PublishAsync` 先走 `SimpleEventBus`，若事件实现 `IMessageEvent` 再走 `MessageEventBus`（`:36-42`）——见下方⚠ |
| `MessageEventBus.cs` | CAP 发布入口。`Send` 分支 + 事务延迟注册（`:64-77`） |

### 4.4 ⛔ `send: false` 在事务外会静默丢事件

这是本文最需要记住的一条。

`MessageEventBus.PublishAsync` 的两个分支（`Cap/MessageEventBus.cs:64-77`）：

| `Send` | 行为 |
| --- | --- |
| `true` | 立即 `Publisher.PublishAsync(...)`（`:70` → `:90`），交给 CAP 写入出箱表 |
| `false` | **完全不调用 `Publisher`**，只 `TransactionActionManager.Register(...)`（`:73-76`） |

延迟动作由**工作单元的提交路径**执行：

| 执行点 | 位置 |
| --- | --- |
| EF Core 同步 | `Bing.EntityFrameworkCore/Core/UnitOfWorkBase.cs:465` |
| EF Core 异步 | 同文件 `:590`（`TransactionCommitAsync`） |
| FreeSQL 同步 | `Bing.FreeSQL/Bing/Uow/UnitOfWorkBase.cs:243` |
| FreeSQL 异步 | 同文件 `:296` |

`ITransactionActionManager` 本体：接口 `Bing.Data/Bing/Data/Transaction/ITransactionActionManager.cs:11`（`CommitAsync` `:28`），实现 `TransactionActionManager.cs:8`（`Register` `:24-29`、`CommitAsync` `:32-37`）。

**问题在这**：`Register` 只是往 `_actions` 里加（`TransactionActionManager.cs:28`）。而 `SaveChanges` 只有在 **`TransactionActionManager.Count > 0`** 时才走 `TransactionCommit` 分支；`Count == 0` 时直接 `base.SaveChanges`，**根本不调 `CommitAsync`**（EF `:434-436`、`:557-560`；FreeSQL `:227-229`、`:277-279`）。

所以：

> **若整条调用链没有任何工作单元触发 `SaveChanges` / `SaveChangesAsync`，`send:false` 注册的动作永远不会执行，事件静默丢失——不报错、无日志、无兜底。**

源码中**没有**任何"不在事务中则降级为立即发送"的逻辑。

**实践建议**：
- 用 `send:false` 就**必须**确保后面有 `UnitOfWork.CommitAsync()`
- 不确定时用 `send:true`（立即发，但失去"业务写入与消息入箱同事务"的原子性保证）
- 关键业务建议加一个"这条消息最终有没有发出去"的对账

### 4.7 订阅：`[EventHandler]` 与 `ICapSubscribe`

```csharp
// Bing.Events/EventHandlerAttribute.cs:8,14
public class EventHandlerAttribute : TopicAttribute
{
    public EventHandlerAttribute(string name, ...);
    // 继承 CAP 的 DotNetCore.CAP.Internal.TopicAttribute
}
```

**关键点**：`[EventHandler]` **继承自 CAP 的 `TopicAttribute`**，所以 CAP 的订阅发现机制会照常扫描到它。**`[EventHandler]` 与 `[CapSubscribe]` 在 CAP 眼里是等价的**——框架只是统一用前者作为订阅标记。

订阅类需实现 **`ICapSubscribe`**（CAP 的接口）。admin 里通过基类统一实现：`MessageEventHandlerBase : ICapSubscribe`（`modules/admin/src/Bing.Admin.EventHandlers/Implements/MessageEventHandlerBase.cs:10`）。

Bing 侧**没有**自己的 `SubscribeAttribute`。

### 4.8 TraceId 贯通

发布侧 `MessageEventBus` 把 TraceId 写进消息头（`Cap/MessageEventBus.cs:125-131`），头名常量 **`bing-trace-id`**（`Cap/Headers.cs:11`）。

消费侧默认**拿不到**（消费者不在 HTTP 请求上下文里），需要替换 CAP 的订阅执行者——见 admin 的 `CapSubscribeInvoker`（§8）。若不接这一步，消费端日志的 CorrelationId 与发布端对不上，**链路在消息处断掉**。

### 5.3 派发器：实现是完整的

`DomainEventDispatcher.DispatchAsync` 的实现体（`:84-98`）逻辑清楚：

```
_eventHandlerTypeStore.GetHandlers(eventType)        // 取该事件类型的处理器集合
  → _handlerFactory.Create(handlerInfo.Type)         // DependencyInjectionHandlerFactory.Create
       = _serviceProvider.GetService(handlerType)    // DependencyInjectionHandlerFactory.cs:24
  → handlerInfo.Method.Invoke(handler, new object[] { @event })
  → 返回值是 Task 则 await
```

即：**走 DI 解析处理器，方法级反射调用**。它是好的——问题不在这里。

**注册入口**：`AddDomainEventDispatcher`（`Extensions.Service.cs:10`），核心在 `:47`：

| `framework/tests/Bing.Ddd.Domain.Tests/.../DomainEventHandlerTest.cs:63` | **测试调用** |

其余全是 `docs/*.md` 与 `bin/**/*.xml` 编译产物。`modules` / `samples` / `eng` / `framework/src` 的**生产代码中零调用**。

**结论：领域事件被收集后就停在那里，没有任何机制把它们送出去。**

### 5.5 ⛔ 工作单元不会排空领域事件

EF Core 支的 `UnitOfWorkBase` 里**恰好有一个为这件事预留的钩子**，但它是空的：

```csharp
// framework/src/Bing.EntityFrameworkCore/Core/UnitOfWorkBase.cs:799-802
protected virtual Task PublishEventsAsync() => Task.CompletedTask;
```

它被 `SaveChangesAfter`（`:787`）调用——**但空实现意味着什么也不做**。

逐一核对过的方法（供复核）：

| 检查对象 | 相关方法（行号） | 是否派发领域事件 |
| --- | --- | --- |
| EF `UnitOfWorkBase` | `SaveChanges :430`、`SaveChangesAsync :553`、`Commit :369`、`CommitAsync :400`、`SaveChangesBefore :677`（只做审计/版本）、`SaveChangesAfter :787` → `PublishEventsAsync :799` | ❌ 否（空钩子） |
| FreeSQL `UnitOfWorkBase` | `Commit :179`、`CommitAsync :202`、`SaveChanges :224`、`SaveChangesAsync :273` | ❌ 否（无任何 `DomainEvent` 代码） |
| FreeSQL `MySql.UnitOfWork` | 仅重写 `GetMapInstances` | ❌ 否 |
| `Bing.Uow.UnitOfWorkManager` | `Commit :21`、`CommitAsync :31` | ❌ 否（仅转发） |

另外 `ClearDomainEvents()` 在生产代码中**从未被调用**（只出现在测试 `AggregateRootDomainEventsTest.cs:93`）。所以不是"清了却没派发"，而是**既没清也没派发**。

### 5.6 admin 的实例：一个被静默丢弃的领域事件

admin 里**真实存在**这样一条死掉的链路：

```csharp
// modules/admin/src/Bing.Admin.Systems.Domain/Models/User.cs:81-84
public void AddLoginLog(string ip, string userAgent)
{
    AddDomainEvent(new UserLoginDomainEvent(this, ip, userAgent));   // ← 收集进 _domainEvents
}
```

配套的 `UserLoginDomainEvent`（`.../DomainEvents/UserLoginDomainEvent.cs:9`）与处理器 `UserLoginDomainEventHandler`（`Bing.Admin.EventHandlers/Implements/Systems/UserLoginDomainEventHandler.cs:12`）**都存在**，处理器也会被 `AddDomainEventDispatcher` 扫描注册（§5.3）。

但因为没人调 `DispatchAsync`，这个事件**留在 `_domainEvents` 里随 DbContext 一起被丢弃**。

> **重点澄清**：admin 的登录日志**确实能写进数据库**——但那**不是**通过领域事件，而是通过 §8 里另一条 CAP 通道。两条路并存，一条通、一条死。这正是这条缺口最难被发现的原因：功能表现正常，只有读源码才知道有半条链路是死的。

### 5.7 想让它真正可用：三条路径

**本文只描述现状，不替你选**——这属于代码决策（见 [功能完成度 §12](功能完成度.md)）。三条可行路径：

| 路径 | 做法 | 代价 |
| --- | --- | --- |
| **A. 重写空钩子**（改动最小） | 在 `UnitOfWorkBase.PublishEventsAsync`（`:799`）里取 `ChangeTracker` 中的 `BasicAggregateRoot`、遍历 `GetDomainEvents()`、逐个 `await _dispatcher.DispatchAsync(...)`，之后 `ClearDomainEvents()` | 领域事件在**事务提交后**派发 → 处理器内的写入不在同一事务里 |
| **B. 派发器改接总线** | 让领域事件处理器内部改走 `ISimpleEventBus` / `IMessageEventBus`，或让派发器转调总线 | 需要额外接线；可获得 Outbox 的原子性 |
| **C. 显式调用** | 在应用服务里手工 `foreach (var e in agg.GetDomainEvents()) await _dispatcher.DispatchAsync(e); agg.ClearDomainEvents();` | 无侵入框架，但**每个用例都要记得写**，容易漏 |

⚠ 无论哪条路径，都要同时决定：**放在提交前还是提交后**（决定是否同一事务）、**失败如何处理**（回滚？记录？重试？）、**是否要清空**（不清会重复派发）。

## 6. 机制 IV：`Bing.EventBus*`（遗留，不要新用）

### 6.1 类型清单

| 接口 | 命名空间 | 成员 | 位置 |
| --- | --- | --- | --- |
| `IEventBus` | `Bing.EventBus` | `PublishAsync<TEvent>` ×2、5× `Subscribe`、4× `Unsubscribe`、`UnsubscribeAll` | `Bing/EventBus/IEventBus.cs:8-111` |
| `IMessageEventBus` | `Bing.EventBus` | `PublishAsync<TEvent>(TEvent)`、`PublishAsync(string, object, string, bool = false)` | `Bing/EventBus/IMessageEventBus.cs:6-22` |
| `IEvent` / `IMessageEvent` | `Bing.EventBus` | 标记接口；`IMessageEvent` 含 `Id/Time/Name/Data/Callback/Send` | `IEvent.cs:6` / `IMessageEvent.cs:6-36` |
| `ILocalEventBus` | `Bing.EventBus.Local` | `: IEventBus` + `IDisposable Subscribe<TEvent>(ILocalEventHandler<TEvent>)` | `Local/ILocalEventBus.cs:6-14` |
| `IDistributedEventBus` | `Bing.EventBus.Distributed` | `: IEventBus` + `Subscribe<TEvent>(...)` + 带 `onUnitOfWorkComplete` 的 `PublishAsync` | `Distributed/IDistributedEventBus.cs:6-30` |
| `IEventHandler` / `<T>` | `Bing.EventBus` | `bool Enabled`；`HandleAsync(TEvent, CancellationToken)` | `IEventHandler.cs:6-25` |
| `LocalEventBusOptions` | `Bing.EventBus.Local` | `Handlers : ITypeList<IEventHandler>` | `Local/LocalEventBusOptions.cs:8-21` |

实现侧：`LocalEventBus` / `NullLocalEventBus`、`ActionEventHandler`、`IEventHandlerFactory`（→ `IocEventHandlerFactory` / `TransientEventHandlerFactory` / `SingleInstanceHandlerFactory`）、`EventHandlerDisposeWrapper`。构造 `LocalEventBus` 需要 `IOptions<LocalEventBusOptions>` + `IServiceScopeFactory`，并在构造时 `SubscribeHandlers(Options.Handlers)`（`Local/LocalEventBus.cs:36-45`）。

⚠ **没有 `AddLocalEventBus` 之类的注册扩展**，要用手工注册（测试里的写法可参考 `framework/tests/Bing.EventBus.Tests/.../EventBusModule.cs:23-24,39-43`）。

### 6.2 类型名撞车对照表

这是"别混用"的**具体原因**：

| 类型简单名 | 现行（`Bing.Events` 体系） | 遗留（`Bing.EventBus` 体系） | 撞车后果 |
| --- | --- | --- | --- |
| `IEventBus` | `Bing.Events.IEventBus` | `Bing.EventBus.IEventBus` | 同时 `using` → **CS0104 二义性** |
| `IEvent` | `Bing.Events.IEvent` | `Bing.EventBus.IEvent` | 同上 |
| `IMessageEvent` | `Bing.Events.Messages.IMessageEvent` | `Bing.EventBus.IMessageEvent` | 同上 |
| `IMessageEventBus` | `Bing.Events.Messages.IMessageEventBus` | `Bing.EventBus.IMessageEventBus` | 同上 |
| `IEventHandler` / `<T>` | `Bing.Events.Handlers.IEventHandler` | `Bing.EventBus.IEventHandler` | 同上 |
| `ILocalEventBus` | **不存在** | `Bing.EventBus.Local.ILocalEventBus` | 无撞车（但会误导你以为它现行） |
| `IDistributedEventBus` | **不存在** | `Bing.EventBus.Distributed.IDistributedEventBus` | 同上 |

**第二类撞车更隐蔽**：`Bing.EventBus` 与 `Bing.EventBus.Abstractions` 两个**程序集**里定义了**完全相同的全限定类型名**（都是 `Bing.EventBus.IEventBus` 等）。同时引用两个程序集会得到 **CS0433**（类型在两个程序集中都存在）。

所幸 `Bing.EventBus.Abstractions` **零引用**，且 `Bing.EventBus` 的 `references.props:3` 只引 `Bing.Data`、**不引 Abstractions**——所以现实中不会触发。但这是个雷。

### 6.3 为什么不要用

| 理由 | 证据 |
| --- | --- |
| **无生产引用** | `Bing.EventBus` 只被自身的测试工程引用（`Bing.EventBus.Tests.csproj:19`）；`Bing.EventBus.Abstractions` **零引用** |
| **无注册入口** | 没有 `AddXxx` 扩展，需手工装配 |
| **类型名与现行体系撞车** | 见 §6.2 |
| **ABP vNext 早期风格，已被取代** | 现行是 `Bing.Events`（CAP 8.0.1） |

> **ABP 迁移者注意**：如果你在找 `ILocalEventBus` / `IDistributedEventBus`——它们在 Bing 里**确实存在**，但属于这个遗留包。`using` 上去能编译通过，用的是无人维护的实现。现行对应物是 `ISimpleEventBus` / `IMessageEventBus`。详见 [ABP 迁移对照](../getting-started/abp-migration.md)。

## 7. 怎么选

```
需要跨进程 / 跨服务传递？
├─ 是 → 机制 II：IMessageEventBus（CAP）
│        ├─ 要求"业务写入与消息入箱同一事务" → send:false + 确保后面有 CommitAsync（§4.4）
│        └─ 只要发出去、不需要原子性       → send:true
└─ 否 → 只是本进程内解耦？
         ├─ 是 → 机制 I：ISimpleEventBus（记得先 AddDefaultEventBus()，§3.4）
         └─ 否 → 是不是"聚合根发生变化后要触发副作用"？
                  ├─ 是 → 理论上该用机制 III 领域事件，但**它当前不会派发**（§5.4）
                  │        要么自己接派发（§5.7），要么改用机制 II 走 CAP
                  └─ 否 → 直接方法调用，不要为解耦而解耦

遇到 ILocalEventBus / IDistributedEventBus → 那是遗留包，别用（§6）
```

## 8. 案例解剖：admin 的一次登录到底触发了什么

`modules/admin/src/Bing.Admin.Service/Implements/SecurityService.cs` 的 `SignInAsync`（`:88`）：

```csharp
var ip = Ip.GetIp();
var result = await SignInManager.SignInAsync(user, request.Password);   // :96
user.AddLoginLog(ip, Web.Browser);                                      // :97 ← 路 A（死）
await MessageEventBus.PublishAsync(new UserLoginMessageEvent(new UserLoginMessage
{
    UserId = user.Id,
    Name = user.Nickname,
    Ip = ip,
    UserAgent = Web.Browser
}, false));                                                             // :98-104 ← 路 B（活）
await UnitOfWork.CommitAsync();                                         // :105 ← 路 B 靠这句才发出去
```

两条通道并列：

| 通道 | 触发 | 机制 | 结果 |
| --- | --- | --- | --- |
| **路 A** | `user.AddLoginLog(...)`（`:97`） | 领域事件 | ⛔ 事件进入 `_domainEvents`，**无人派发，随上下文丢弃** |
| **路 B** | `MessageEventBus.PublishAsync(..., send: false)`（`:98-104`） | CAP 消息事件 | ✅ 注册为延迟动作，**由 `:105` 的 `CommitAsync()` 触发**，写入 `cap.published` 后投递到 RabbitMQ |

**路 B 能通，依赖 `:105` 那一行**——按 §4.4，如果 `CommitAsync()` 被删掉或改了位置，这条路会**静默失效**，且登录功能本身**不会报错**。

消费端（`Bing.Admin.EventHandlers/Implements/Systems/UserLoginLogMessageEventHandler.cs:62-68`）：

```csharp
[EventHandler(MessageEventConst.UserLogin, Group = QueueGroupConst.UserLoginLog)]
public async Task UserLoginAsync(UserLoginMessage message)
{
    await Task.Delay(5000);                                                   // ⚠ 演示用，睡眠 5 秒
    await UserLoginLogManager.CreateAsync(message.MapTo(new UserLoginLogParameter()));
    await UnitOfWork.CommitAsync();
}
```

`UserLoginLogManager.CreateAsync`（`UserLoginLogManager.cs:34-41`）只做 `AddAsync`——**不再发布任何事件**。

⚠ 两处工程细节：
- 处理器里的 `Task.Delay(5000)` 是**演示代码**（用来观察消费过程），生产应删除
- 该处理器**不幂等**：CAP 失败重试最多 5 次（§4.6），每次都会再插一条登录日志。要防重需自己加唯一键或状态判断

### `CapSubscribeInvoker`：消费端接回 TraceId

EF 宿主的 `CapModule.cs` 里有一个自定义订阅执行者（`Bing.Admin/Modules/CapModule.cs:87-130`）：

```csharp
public class CapSubscribeInvoker : SubscribeInvoker
{
    protected override object GetInstance(IServiceProvider provider, ConsumerContext context)
    {
        var capHeader = new CapHeader(context.DeliverMessage.Headers);
        InitTraceIdContext(capHeader);                 // 从消息头恢复 TraceId
        return base.GetInstance(provider, context);
    }

    private void InitTraceIdContext(CapHeader capHeader)
    {
        if (!capHeader.TryGetValue("bing-trace-id", out var traceId))   // :122 头名硬编码
            return;
        if (TraceIdContext.Current == null)
            TraceIdContext.Current = new TraceIdContext(traceId);
        else
            TraceIdContext.Current.TraceId = traceId;
    }
}
```

消息头名 **`bing-trace-id`** 与发布端常量 `Cap/Headers.cs:11` 对应。⚠ FreeSQL 宿主**没有**这个类，链路追踪在消费端会断。

## 9. 陷阱清单

| # | 陷阱 | 后果 | 详见 |
| --- | --- | --- | --- |
| 1 | 用 `send:false` 但后面没有 `CommitAsync()` | **事件静默丢失**，无报错无日志 | §4.4 |
| 2 | 以为领域事件会自动派发 | 事件永久滞留，随 DbContext 丢弃 | §5.4 |
| 3 | 以为 `UnitOfWork` 会帮你排空领域事件 | `PublishEventsAsync` 是空实现 | §5.5 |
| 4 | 同时 `using Bing.Events` 与 `Bing.EventBus` | **CS0104 二义性**编译失败 | §6.2 |
| 5 | 因为"能找到 `ILocalEventBus`"就用了它 | 用了零维护的遗留实现 | §6.3 |
| 6 | 通过 `IEventBus` 发布 `MessageEvent` | **本地处理器也会被触发**，再发 CAP | §4.3 |
| 7 | 处理器没做幂等 | CAP 重试 5 次 → 重复副作用 | §4.6 |
| 8 | `EntityBase` 上调 `AddDomainEvent` | 编译不过——能力在 `BasicAggregateRoot` 上 | §5.2 |
| 9 | 消费端 TraceId 为空 | 链路在消息处断掉 | §4.8 |
| 10 | 想启用 `Bing.Events.Cap.MySql` | 它与现行 CAP 差数个主版本，且包内版本标注自相矛盾 | §4.10 |
| 11 | RabbitMQ 凭据硬编码在 `CapModule.cs` | 凭据已入库 | §4.9 |
| 12 | 开 `UseDispatchingPerGroup` 但不设 `Group` | 分组语义不生效（admin 只设了 EF 宿主） | §4.6 |

## 10. 如何自行复核

本文的结论都可以自己验一遍。

**① 确认领域事件确实无人派发**

```bash
# 搜 DispatchAsync 的全部出现位置，看有没有生产调用
grep -rn "DispatchAsync" --include=*.cs framework/src components/src modules samples
# 预期：只在 IDomainEventDispatcher 的声明、DomainEventDispatcher 的实现里出现
```

**② 确认工作单元不排空领域事件**

```bash
# 看空钩子
grep -n "PublishEventsAsync" framework/src/Bing.EntityFrameworkCore/Core/UnitOfWorkBase.cs
# 预期：:799 的 protected virtual Task PublishEventsAsync() => Task.CompletedTask;
```

**③ 验证 `send:false` 在事务外的行为**

在没有任何 `UnitOfWork.CommitAsync()` 的代码路径里发布一个 `send:false` 的消息，然后查 `cap.published` 表——**预期不会新增记录，也不会有异常**。这就是"静默丢失"。

**④ 确认 CAP 版本**

```bash
grep -rn "DotNetCore.CAP" --include=*.props --include=*.csproj framework/src
# 预期：Bing.Events 用 8.0.1；Bing.Events.Cap.MySql 用 3.1.2（与其 csproj 注释声称的 "2.6" 不符）
```

**⑤ 确认引用关系**

```bash
# 谁真正引用了 Bing.Events / Bing.EventBus / Bing.Events.Cap.MySql
grep -rn "Bing.Events\|Bing.EventBus" --include=*.csproj --include=*.props framework modules samples
```
