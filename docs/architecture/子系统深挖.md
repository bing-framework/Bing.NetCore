## 1. CAP 事件总线与事务一致性

### 1.1 抽象分层：本地总线与分布式总线解耦

事件总线的全部抽象接口**物理位于 `Bing.Core` 项目**（`framework/src/Bing.Core/Bing.Core.csproj`），而不是独立的 `*Abstractions` 项目。这点是阅读源码时容易找错地方的地方。

| 接口 | 命名空间 | 文件 |
| --- | --- | --- |
| `IEventBus` | `Bing.Events` | `framework/src/Bing.Core/Events/IEventBus.cs` |
| `ISimpleEventBus : IEventBus` | `Bing.Events` | `framework/src/Bing.Core/Events/ISimpleEventBus.cs` |
| `IMessageEventBus` | `Bing.Events.Messages` | `framework/src/Bing.Core/Events/Messages/IMessageEventBus.cs` |
| `IEventHandlerManager` | `Bing.Events.Handlers` | `framework/src/Bing.Core/Events/Handlers/IEventHandlerManager.cs` |
| `IEventHandler<in TEvent>` | `Bing.Events.Handlers` | `framework/src/Bing.Core/Events/Handlers/IEventHandler.cs` |
| `IEvent` | `Bing.Events` | `framework/src/Bing.Core/Events/IEvent.cs` |
| `IMessageEvent : IEvent` | `Bing.Events.Messages` | `framework/src/Bing.Core/Events/Messages/IMessageEvent.cs` |

关键签名：

```csharp

// IEvent：承载事件标识与时间戳
```

> **纠正**：仓库里另有一份**遗留/独立**的 `Bing.EventBus` 与 `Bing.EventBus.Abstractions` 项目（命名空间 `Bing.EventBus`），但 CAP 集成使用的是上面 `Bing.Core` 这组接口。文档化时不要混淆两者。

### 1.2 两层发布机制（本地优先，分布式按需）

文件：`framework/src/Bing.Events/Cap/EventBus.cs`，命名空间 `Bing.Events.Cap`，`public class EventBus : IEventBus`。

```csharp
public async Task PublishAsync<TEvent>(TEvent @event) where TEvent : IEvent
{
    await SimpleEventBus.PublishAsync(@event);            // (a) 本地内存总线：同一进程内 IEventHandler<T> 同步派发
    if (!(@event is IMessageEvent messageEvent)) return;  // (b) 仅实现 IMessageEvent 的事件才会走分布式
    await MessageEventBus.PublishAsync(messageEvent);     // (b) CAP 分布式总线：投递到消息队列
}
```

设计要点：

- **本地分支**（默认）始终执行：`Bing.Events.Default.EventBus` 通过 `IEventHandlerManager.GetHandlers<TEvent>()` 取出所有 `IEventHandler<TEvent>` 逐一 `HandleAsync`（串行 `await`，无事务）。适合进程内本地事件（如「订单创建后更新统计」）。⚠ 注意这与 DDD 的**领域事件**不是一回事——领域事件走独立的 `IDomainEventDispatcher`，且**当前不会被派发**。
- **分布式分支**只在事件实现 `IMessageEvent` 时触发。⚠ **它不是一个"先注册再投递"的两步过程，而是按 `Send` 二选一**（`Cap/MessageEventBus.cs:64-77`）：
  - `Send = true` → 直接 `Publisher.PublishAsync(name, data, headers)`（`:70` → `:90`），立即投递到 CAP 支持的 MQ（RabbitMQ / Kafka 等）
  - `Send = false` → **完全不调用 `Publisher`**，只 `TransactionActionManager.Register(...)`（`:73-76`），把投递延迟到工作单元提交时

这带来一个清晰的语义约定：**不实现 `IMessageEvent` 的事件是纯本地事件；实现 `IMessageEvent` 的事件才会跨进程广播**。调用方无需关心消费者在哪台机器上。

⚠ **`Send = false` 的代价**：它依赖后续确实发生 `UnitOfWork.CommitAsync()`。若整条链路没有 UoW 提交，挂起的动作**永远不会执行，事件静默丢失且不报错**。详见 [事件与消息文档 §4.4](事件与消息文档.md)。

### 1.4 订阅者模型：CAP 原生 `[Topic]` 桥接，而非 `[CapSubscribe]` 装饰方法

> **纠正**：本框架**不使用** `[CapSubscribe]` 装饰方法的方式。

桥接方式是直接复用 CAP 的原生发现机制：

- 处理器基类实现 CAP 标记接口：`MessageEventHandlerBase : DotNetCore.CAP.ICapSubscribe`（`modules/admin/src/Bing.Admin.EventHandlers/Implements/MessageEventHandlerBase.cs`）。
- 方法用 `Bing.Events.EventHandlerAttribute` 声明主题，而它**继承自 `DotNetCore.CAP.Internal.TopicAttribute`**（`framework/src/Bing.Events/EventHandlerAttribute.cs`）。因此 CAP 通过 `ICapSubscribe` + `TopicAttribute` 自动发现并派发消费者，无需手写适配器。

```csharp
// 例：modules/admin/.../TestMessageEventHandler.cs
[EventHandler(MessageEventConst.TestMessage1)]   // 继承自 CAP 的 TopicAttribute
public Task HandleAsync(TestMessageEvent1 @event) { /* ... */ }
```

两套模型并行存在：

- **本地内存处理器**：实现 Bing 的 `IEventHandler<TEvent>`，由 `Default.EventBus` + `IEventHandlerManager` 派发。
- **分布式消费者**：实现 CAP 的 `ICapSubscribe`、用 `[EventHandler]`（=CAP `TopicAttribute`）标注，由 CAP 直接消费。

自定义桥接器 `CapSubscribeInvoker : SubscribeInvoker`（实现 `ISubscribeInvoker`）在 `GetInstance` 中注入 `TraceIdContext`（`modules/admin/src/Bing.Admin/Modules/CapModule.cs:87`），用于跨服务传递链路追踪 ID。

### 1.5 Outbox 事务一致性：AdminUnitOfWork 包裹 CAP 事务

> **纠正（重要）**：本仓库的 CAP Outbox 包装在 **MySql** 管理模块，而不是 SqlServer。
> 文件：`modules/admin/src/Bing.Admin.Data.EFCore/UnitOfWorks/MySql/AdminUnitOfWork.cs`，
> 命名空间 `Bing.Admin.Data.UnitOfWorks.MySql`，`class AdminUnitOfWork : Bing.Datas.EntityFramework.MySql.MySqlUnitOfWorkBase`。

（`Bing.EntityFrameworkCore.SqlServer` 项目存在，但**没有**此 UoW 实现。）

```csharp
public override async Task<int> SaveChangesAsync(CancellationToken cancellationToken = default)
{
    SaveChangesBefore();
    var transactionActionManager = LazyServiceProvider.LazyGetService<ITransactionActionManager>();
    if (transactionActionManager.Count == 0) return await base.SaveChangesAsync(cancellationToken);
    return await TransactionCommit(transactionActionManager, cancellationToken);
}

private async Task<int> TransactionCommit(ITransactionActionManager transactionActionManager, CancellationToken cancellationToken)
{
    using var connection = Database.GetDbConnection();
    if (connection.State == ConnectionState.Closed) await connection.OpenAsync(cancellationToken);
    var publisher = LazyServiceProvider.LazyGetService<ICapPublisher>();
    using (var capTransaction = Database.BeginTransaction(publisher, autoCommit: false)) // 开启 CAP 事务
    {
        try
        {
            await transactionActionManager.CommitAsync(
                publisher.Transaction.Value.DbTransaction as IDbTransaction); // 1. 先注册消息发布
            var result = await base.SaveChangesAsync(cancellationToken);      // 2. 业务数据落库
            await capTransaction.CommitAsync(cancellationToken);              // 3. 提交 Outbox，消息出队
            return result;
        }
        catch (Exception)
        {
            await capTransaction.RollbackAsync(cancellationToken);            // 任一失败整体回滚
            throw;
        }
    }
}
```

机制说明（经典的 **事务性发件箱 / Transactional Outbox** 模式）：

- 事件发布时（`MessageEventBus.PublishAsync`）只是 `TransactionActionManager.Register(...)`，**不立即投递**。
- 工作单元 `SaveChangesAsync` 时，在同一 EF Core 事务内**先发消息、再落库**，最后统一 `capTransaction.CommitAsync`。消息表与业务表同库、同事务，保证「业务数据已提交 ⇔ 消息已可见」的最终一致性。
- 若落库或消息任一失败，整段 `RollbackAsync`，避免「数据已写但消息丢失」或「消息发了但数据回滚」的不一致。

## 2. FreeSQL 集成：仅 MySql Provider 与设计扩展路径

### 2.1 模块布局：Provider 层是薄壳

项目根：`framework/src/`

- 核心库：`Bing.FreeSQL`（`Bing.FreeSQL.csproj`，target `netstandard2.0`）
- 唯一 Provider：`Bing.FreeSQL.MySql`（`Bing.FreeSQL.MySql.csproj`）

`Bing.FreeSQL.MySql` 仅引用 `FreeSql.Provider.MySqlConnector`（`dependency.props`）。全仓检索 FreeSQL 范围内的 `DataType.SqlServer/PostgreSQL/Sqlite/Oracle` **无匹配**；命中的 SqlServer/Sqlite/Oracle 文件全部属于独立的 `Bing.EntityFrameworkCore.*` 项目（EF Core 集成，与 FreeSQL 无关）。

**结论：FreeSQL 模块下确实只发布了 MySql Provider。** 这是有意为之——核心 `Bing.FreeSQL` 完全数据库无关，Provider 层只是切换 `DataType.*` 与 NuGet 包的薄壳。

### 2.2 注册入口：`AddMySqlUnitOfWork`

文件：`framework/src/Bing.FreeSQL.MySql/Bing/FreeSQL/Extensions.Services.cs`，命名空间 `Bing.FreeSQL`。

```csharp
public static IServiceCollection AddMySqlUnitOfWork<TUnitOfWork, TUnitOfWorkImplementation>(
    this IServiceCollection services,
    string connection,
    Action<IServiceProvider, FreeSqlBuilder> setupAction = null,
    Action<IServiceProvider, IFreeSql> freeSqlSetupAction = null)
    where TUnitOfWork : class, IUnitOfWork
    where TUnitOfWorkImplementation : UnitOfWorkBase, TUnitOfWork
```

方法体内构造 FreeSQL 实例并注册：

```csharp

    .UseConnectionString(DataType.MySql, connection)
    .UseLazyLoading(false);
```

两个可选 `setupAction` / `freeSqlSetupAction` 回调，分别用于在 `Build()` 前微调 `FreeSqlBuilder`、在 `Build()` 后微调 `IFreeSql`（如注册自定义类型映射、AOP）。

### 2.3 工作单元基类与乐观锁

文件：`framework/src/Bing.FreeSQL/Bing/Uow/UnitOfWorkBase.cs`，命名空间 `Bing.Uow`。

```csharp
public abstract class UnitOfWorkBase : DbContext, Bing.Uow.IUnitOfWork, IDatabase
```

确实派生自 FreeSQL 的 `FreeSql.DbContext`。行级乐观锁在 `Commit()`/`CommitAsync()` 中处理：


### 2.4 `IUnitOfWork` 的契约边界

> **纠正**：`IUnitOfWork` **位于 `Bing.Uow` 命名空间/项目**（不是 `Bing.Ddd.Domain`）；且接口本身只声明两个成员。

文件：`framework/src/Bing.Uow/Bing/Uow/IUnitOfWork.cs`。

```csharp
public interface IUnitOfWork
{
    int Commit();
    Task<int> CommitAsync(CancellationToken cancellationToken = default);
}
```

`SaveChanges` / `SaveChangesAsync`（来自 FreeSQL `DbContext` 重写）以及回滚逻辑**不在该接口**——回滚由事务提交路径内的 `UnitOfWork.Rollback()` 同步处理。文档化时不要把 `IUnitOfWork` 描述成包含 `SaveChangesAsync`/`RollbackAsync` 的大接口。

### 2.5 软删除与审计 AOP

全局过滤器（`Extensions.Services.cs`）：

```csharp
freeSql.GlobalFilter.Apply<ISoftDelete>("SoftDelete", x => x.IsDeleted == false);
```

审计值 `Aop.AuditValue`（约第 46–93 行）覆盖：

- **乐观锁**：对实现 `IVersion` 的实体，`Version`（`byte[]`）为空时赋 `Guid` 字节；
- **时间戳**：插入/更新时 `CreationTime` / `ModificationTime` 赋 `DateTime.Now`；
- **操作人**：通过 `ServiceLocator` 取 `ICurrentUser` 填充 `Creator` / `Modifier` / `CreatorId` / `ModifierId`。

实体映射本身与数据库无关，位于核心库：

- `IMap`（`Bing.FreeSQL/Bing/FreeSQL/IMap.cs`）：`void Map(ICodeFirst modelBuilder);`
- `MapBase<TEntity>`（`MapBase.cs`）：`Map()` 依次调用 `MapTable` / `MapVersion` / `MapProperties` / `MapAssociations`，其中 `MapVersion` 对 `IVersion` 实体调用 `.IsRowVersion()`。
- MySql 的 `EntityMap<TEntity> : MapBase<TEntity>, IMap` 与 `AggregateRootMap<TEntity> : MapBase<TEntity>, IMap` 均为空抽象壳（无数据库特定代码），扩展时通常原样复制即可。

### 2.6 扩展为其他数据库（以 SqlServer 为例）

以 `Bing.FreeSQL.MySql` 为模板新建 `Bing.FreeSQL.SqlServer`：

1. `dependency.props` 改包：`FreeSql.Provider.MySqlConnector` → `FreeSql.Provider.SqlServer`；
2. 复制 `Extensions.Services.cs`，将 `.UseConnectionString(DataType.MySql, connection)` 改为 `DataType.SqlServer`，方法改名 `AddSqlServerUnitOfWork`，`IMap` 引用改为 `Bing.FreeSQL.SqlServer.IMap`；
3. 复制 `Bing/Uow/UnitOfWork.cs`，使 `GetMapInstances` 返回 `Bing.FreeSQL.SqlServer.IMap`；
4. 复制 `MySql/IMap.cs`、`EntityMap.cs`、`AggregateRootMap.cs` 到新命名空间（三者为空壳，仅继承基类）。

**扩展本质**：切换 `DataType.*`、换 NuGet 包、重命名 `IMap` / `Add*UnitOfWork`。核心库 `Bing.FreeSQL` 无需改动。这也印证了「Provider 层是薄壳」的设计判断。

### 3.3 方言抽象：`Dialect` 负责标识符引用

`DialectBase.SafeName` 默认用 `[]`（SQL Server 风格）。各库覆写引用符：

```csharp
// Bing.Dapper.SqlServer/.../Builders/SqlServerDialect.cs
class SqlServerDialect : DialectBase { /* 不覆写，沿用 OpeningIdentifier='[' ClosingIdentifier=']' */ }

// Bing.Dapper.MySql/.../Builders/MySqlDialect.cs

public override char ClosingIdentifier => '`';
```

`DialectBase.SafeName` 先 `FilterName`（去掉已有的 `[ ] \` "` 包裹）再调用 `GetSafeName` → `$"{OpeningIdentifier}{name}{ClosingIdentifier}"`。这样上层拼 SQL 时只用裸列名，引用符由方言统一处理，避免跨库 SQL 注入/转义问题。

```csharp
    string connectionStringName = null,
    Action<SqlDataSourceDescriptor> setupAction = null,
    string providerKey = null)
// 用法：AddSqlDataSource("crm", DatabaseType.SqlServer, connStr, providerKey: "bing.sqlserver");
```

**③ 路由终点** —— `SqlQueryFactory.Create` → `DefaultSqlProviderResolver.Resolve` → `ActivatorUtilities` 实例化：

```csharp
// Bing.Dapper.Core/Bing/Data/Sql/SqlQueryFactory.cs
public ISqlQuery Create(string dbKey = null) =>
    CreateInstance<ISqlQuery>(string.IsNullOrWhiteSpace(dbKey) ? GetCurrentContext() : CreateContext(dbKey));

// Bing.Dapper.Core/Bing/Data/Sql/DefaultSqlProviderResolver.cs
public ISqlProvider Resolve(DatabaseContext context, ISqlProvider provider = null, DatabaseType? databaseType = null)
    => /* 据 context.DataSource.ProviderKey（或 DatabaseType 经 OfficialProviderKeys 映射）解析出 provider.Key */;

// Bing.Dapper.Core/Bing/Data/Sql/SqlFactoryBase.cs（路由终点）
protected TService CreateInstance<TService>(DatabaseContext context) where TService : class
{
    var providerKey        = ResolveProviderKey(context);
    var implementationType = GetImplementationType(typeof(TService), providerKey); // 从 SqlProviderRuntime 查 QueryType
    var options            = CreateOptions(implementationType, context);
    return (TService)ActivatorUtilities.CreateInstance(_serviceProvider, implementationType, _serviceProvider, options);
}
```

`GetImplementationType` 通过 `_serviceProvider.GetServices<SqlProviderRuntime>().SingleOrDefault(r => r.ProviderKey == providerKey)?.Resolve(serviceType)` 取回具体 `QueryType`，再用 DI 容器 `ActivatorUtilities` 实例化。

**Provider Key（硬编码于各 `XxxSqlProvider.Key`）**：

| 数据库 | Provider Key | 备注 |
| --- | --- | --- |
| SqlServer | `bing.sqlserver` | — |
| MySql | `bing.mysql` | — |
| PgSql | `bing.postgresql` | — |
| Oracle | `bing.oracle` | — |
| Sqlite | `bing.sqlite` | — |
| Doris | `bing.mysql` | `DefaultSqlProviderResolver.OfficialProviderKeys` 中 `[DatabaseType.Doris] = "bing.mysql"`（复用 MySql 方言） |

**`DatabaseType` 枚举**（`Bing.Data/Bing/Data/Enums/DatabaseType.cs`）：`SqlServer, MySql, PgSql, Oracle, Sqlite, Doris`（共 6 值，确认含 Doris）。

**路由链一句话总结**：`AddSqlProviderRuntime(SqlProviderRuntime)` 登记「Key → 具体 Query/Executor 类型」；`AddSqlDataSource(key, DatabaseType, conn, providerKey)` 登记「数据源 → ProviderKey」；`factory.Create(key)` 时由 `DefaultSqlProviderResolver` 依据 `ProviderKey` 找到 `SqlProviderRuntime`，再用 `ActivatorUtilities` 实例化出对应 `XxxSqlQuery` / `XxxSqlExecutor`。

### 3.5 五个 Dapper Provider 项目

`Bing.Dapper.{SqlServer, MySql, PostgreSQL, Oracle, Sqlite}`（均引用 `Bing.Dapper.Core` 与 `Bing.Data.Sql`）。每个项目贡献：

- `DapperServiceCollectionExtensions`：`Add{SqlServer|MySql|PostgreSQL|Oracle|Sqlite}Provider()`，内部 `AddSqlCore()` + `AddSqlBuilderProvider(...)` + `AddSqlProviderRuntime(new SqlProviderRuntime(...))`，并注册 `SqlOptions<...>`、`ISqlDbConnectionFactory`、`ISqlDbParameterCustomizer`、`IDatabaseTypeConverter`；
- `Builders/XxxSqlProvider.cs`：`sealed class XxxSqlProvider : ISqlProvider`（`Instance` 单例 + `Key` + `Dialect` + `ClauseFactory` + `PaginationRenderer`）；
- `Builders/XxxDialect.cs`：`sealed class XxxDialect : DialectBase`（覆写引用符/前缀）；
- `Builders/XxxBuilder.cs`：具体 `ISqlBuilder` 实现（`SqlServerBuilder` / `MySqlBuilder` 等）；
- 由 `SqlProviderRuntime` 指向的查询/执行器类型（`SqlServerSqlQuery` / `SqlServerSqlExecutor` / `SqlServerSqlMultipleQueryExecutor` 等）。

这正是「新增数据库只需复制一个 Provider 项目、改 `DataType`/引用符/Key」的可扩展设计——与 FreeSQL 的 Provider 薄壳思路一致。

### 3.6 最小用法示例

```csharp
// 注册（Program.cs / Module 内）
services.AddSqlServerProvider();                                  // 或 AddMySqlProvider()
services.AddSqlDataSource("crm", DatabaseType.SqlServer, connStr, providerKey: "bing.sqlserver");

// 使用
using var scope   = serviceProvider.CreateScope();
var factory = scope.ServiceProvider.GetRequiredService<ISqlQueryFactory>();
var query   = factory.Create("crm")
                     .Select("Id, Name")
                     .From("Customer")
                     .Where(t => t.Col("Status") == 1);
var list = await query.ToListAsync<CustomerDto>();
```

调用 `factory.Create("crm")` 的解析路径：`SqlQueryFactory.Create` → `CreateContext("crm")`（解析 `crm` 数据源）→ `DefaultSqlProviderResolver.Resolve` 得 `bing.sqlserver` → 查 `SqlProviderRuntime` 得 `QueryType = SqlServerSqlQuery` → `ActivatorUtilities.CreateInstance` 实例化为 `ISqlQuery`。

## 附：三个子系统的共性设计取向

1. **接口与实现分离，但接口尽量贴近核心**：事件总线接口在 `Bing.Core`，`IUnitOfWork` 在 `Bing.Uow`，`Bing.Data.Sql` 接口在自身项目——不另起 `*Abstractions` 项目，降低阅读跳转成本。
2. **Provider 即薄壳**：FreeSQL 的 MySql 包、`Bing.Data.Sql` 的五个 Dapper 包，本质都是「切换数据库特定位（DataType / 引用符 / Key / NuGet 包）」的薄壳，核心库完全数据库无关，扩展成本极低。
3. **运行时路由靠 `ActivatorUtilities` + 注册表**：CAP 用 `AddCap` 原生注册；`Bing.Data.Sql` 用 `SqlProviderRuntime` 注册表 + `ActivatorUtilities` 按 Key 实例化——新增实现不修改框架代码，只新增注册。
4. **事务一致性优先**：CAP Outbox 用「同库同事务先发消息后落库」保证最终一致；FreeSQL 用 `Aop.AuditValue` + 全局过滤器把审计/软删除/乐观锁收敛到基础设施层，业务实体零感知。
