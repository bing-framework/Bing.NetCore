# 领域建模指南

> **适用版本**：框架 `7.0.0`（`version.props`）｜ 目标框架：类库 `netstandard2.0`、Web / 应用 `net6.0`｜ 内容核对：2026-09-18｜ 版本历史见 [发行说明](../ReleaseNotes.md)

> **一句话定位**：本框架提供了一整套 DDD 基类（实体 / 聚合根 / 值对象 / 审计 / 乐观锁 / 存储 / 应用服务）。本文回答**"该继承哪个基类、该实现哪些接口、什么时候谁替我填字段"**。
>
> 本文只讲**建模**。安装与启动见 [使用文档](../getting-started/使用文档.md)；三支 ORM 的选型见 [能力矩阵](../getting-started/能力矩阵.md)；端到端可运行代码见 [recipes](recipes/README.md)。
>
> **所有类型与行号均取自源码**，核心工程是 `framework/src/Bing.Ddd.Domain`。若源码变了而本文没变，请信任源码并回来修正本文。

## 1. 继承体系总览

```
IDomainObject ─ DomainObjectBase                      （DomainObjectBase.cs:11）
                    : IDomainObject, IChangeTrackable
                └ DomainObjectBase<TObject>           （:107）
                    : IVerifyModel<TObject>
                  ├ EntityBase                         （EntityBase.cs:12）
                  │   : IEntity
                  └ EntityBase<TEntity, TKey>          （:62）
                      : DomainObjectBase<TEntity>, IEntity<TEntity, TKey>
                      ├ BasicAggregateRoot<TEntity, TKey>          （BasicAggregateRoot.cs:34）
                      │   : IAggregateRoot<TEntity, TKey>  ← 领域事件在这里
                      │   ├ AggregateRoot<TEntity, TKey>           （AggregateRoot.cs:38）
                      │   │   + IVersion                   ← 乐观锁在这里
                      │   └ TreeEntityBase<TEntity, TKey, TParentId>（TreeEntityBase.cs:33）
                      └ CreationAuditedEntity → AuditedEntity → FullAuditedEntity
                        CreationAuditedAggregateRoot → AuditedAggregateRoot → FullAuditedAggregateRoot
```

还有一套**审计基类家族**（与上面并联，不重叠）：`CreationAuditedAggregateRoot` → `AuditedAggregateRoot` → `FullAuditedAggregateRoot`（各自 `.cs:11`），以及实体版的 `CreationAuditedEntity` → … → `FullAuditedEntity`（`FullAuditedEntity.cs:11`）。

都有**单参重载**（主键默认 `Guid`）：`EntityBase<TEntity>`（`EntityBase.cs:41`）、`BasicAggregateRoot<TEntity>`（`:10`）、`AggregateRoot<TEntity>`（`:10`）。

### 1.1 三十秒选择表

| 你的对象是… | 继承 | 已自带 |
| --- | --- | --- |
| 需要乐观锁的业务主体 | **`AggregateRoot<TEntity, TKey>`** | 领域事件 + `IVersion` |
| 树形结构（菜单 / 分类 / 组织） | **`TreeEntityBase<TEntity, TKey, TParentId>`** | 领域事件 + `ParentId` / `Path` / `Level` / `SortId` |
| 聚合根但不需要乐观锁 | `BasicAggregateRoot<TEntity, TKey>` | 领域事件 |
| 只是一张表，不是聚合根 | `EntityBase<TEntity, TKey>` | 仅 `Id` |
| 需要完整审计（创建+修改+删除） | `FullAuditedAggregateRoot<…>` | 审计字段 + 领域事件 |
| 值对象（无标识、按值相等） | **`ValueObjectBase<TValueObject>`** | `IEquatable<TValueObject>`（`Values/ValueObjectBase.cs:12`） |

> ⚠️ **注意**：以上任何基类都**不含软删除**。要软删除必须额外声明 `ISoftDelete`（详见 §3）。
> ⚠️ **没有**名为 `ValueObject` 的类，只有 `ValueObjectBase<TValueObject>`。

## 2. 实体与聚合根

### 2.1 两者到底差在哪

| | `EntityBase<TEntity, TKey>` | `AggregateRoot<TEntity, TKey>` |
| --- | --- | --- |
| 主键 | `[Key, Required] virtual TKey Id`（`EntityBase.cs:67`） | 同左 |
| **领域事件** | ❌ 无 | ✅ `AddDomainEvent` / `GetDomainEvents` / `RemoveDomainEvent` / `ClearDomainEvents`（`BasicAggregateRoot.cs:61-84`） |
| **乐观锁** | ❌ 无 | ✅ `[DisableAuditing] virtual byte[] Version`（`AggregateRoot.cs:56`） |
| 软删除 / 审计字段 | ❌ 无 | ❌ **也无**，需自行声明接口 |
| 一致性边界 | 不是聚合根 | 是（实现 `IAggregateRoot<TEntity,TKey>`） |

**关键差异只有两条：会不会收集领域事件、有没有 `IVersion`。**

### 2.2 主键类型的约定

| 主键类型 | 写法 | 主键是否自动生成 |
| --- | --- | --- |
| `Guid` | `EntityBase<TEntity>`（单参即默认 Guid） | ✅ 自动（`CreateId → EntityHelper.CreateKey`，`EntityBase.cs:144`） |
| `string` | `EntityBase<TEntity, string>` | ✅ 自动 |
| `int` / `long` | `EntityBase<TEntity, int>` | ❌ **不自动**，由数据库自增（`EntityBase.cs:134,158`） |

> 没有 `IntEntityBase` 这类专用类，直接用双参版本即可。

### 2.3 实体标识接口

`IEntity`（`IEntity.cs:6`）、`IEntity<out TKey>`（`:24`）、`IEntity<in TEntity, out TKey>`（`:32`，**已标记弃用**）。
聚合根侧：`IAggregateRoot`（`IAggregateRoot.cs:7`）、`IAggregateRoot<out TKey>`（`:13`）、`IAggregateRoot<in TEntity, out TKey>`（`:20`）。
主键约束接口 `IKey<out TKey>`（`IKey.cs:7`）——仓储泛型约束要用到它。

### 3.1 三个必须记住的事实

1. **`IFullAuditedObject` 不含 `ISoftDelete`**。用了 `FullAuditedAggregateRoot` 之后**仍要显式声明 `ISoftDelete`**。仓库里 `Role` 就是这么写的（`Role.Base.cs:12`）。

2. **EF 与 FreeSQL 的填充能力不对等**。EF 支在 `UnitOfWorkBase.cs:708-709,723,737-738` 统一挂 Added/Modified/Deleted 拦截 → 审计 + `SetVersion` 全自动。**FreeSQL 支未发现审计自动填充器**，软删除也是手写在 `StoreBase.Remove/Delete` 里的。

3. **没有 `IHasConcurrencyStamp`**，全库并发控制统一走 `IVersion`（`byte[]`）。从 ABP 迁过来时注意：ABP 的 `IHasConcurrencyStamp` 是 `string`。

## 4. 领域事件 ⛔ 重要警告

### 4.1 组成

| 角色 | 类型 | 位置 |
| --- | --- | --- |
| 事件标记 | `abstract class DomainEvent {}` | `Events/DomainEvent.cs:6` |
| 收集 | `AddDomainEvent` / `GetDomainEvents` / `RemoveDomainEvent` / `ClearDomainEvents` | `BasicAggregateRoot.cs:61-84` |
| 派发器接口 | `IDomainEventDispatcher.DispatchAsync(DomainEvent)` | `Events/IDomainEventDispatcher.cs:39` |
| 派发器实现 | `DomainEventDispatcher` | `Events/DomainEventDispatcher.cs:84` |
| 处理器 | `IDomainEventHandler<TEvent>` | `Events/IDomainEventHandler.cs:7` |
| 注册 | `services.AddDomainEventDispatcher()` | `Events/Extensions.Service.cs:35,49` |

注意：`DomainEvent` **不继承** `IEvent` / `ILocalEvent`，与 `ISimpleEventBus` / `IMessageEventBus` 是**完全独立的两套体系**（源码上无继承关系）。

### 4.2 ⛔ 框架不会自动派发聚合根的领域事件

**这是使用本框架做 DDD 时最容易踩的空。** 实测证据：

- `AddDomainEvent(...)` 只把事件推进 `_domainEvents` 列表；
- **没有任何生产代码调用 `DispatchAsync`**——全仓只出现在 `DomainEventDispatcher.cs:84`（自身）与测试 `DomainEventHandlerTest.cs:63`；
- EF 的 `UnitOfWorkBase` 与 `AdminUnitOfWork` 的 `SaveChanges` 路径中 **`DomainEvent` 零命中**。

**结论**：事件被收集后**永远不会派发**，处理器的 `HandleAsync` 永不执行。仓库内的真实案例：`User.cs:83` 的 `AddDomainEvent(new UserLoginDomainEvent(...))` 与 `UserLoginDomainEventHandler` 都是**死代码**（但登录日志本身靠 CAP 消息事件另有一条活路，详见 [功能完成度 §7.1](../architecture/功能完成度.md)）。

**正确做法**：要发事件，直接用事件总线——

```csharp
// 本地事件（进程内同步派发）
await SimpleEventBus.PublishAsync(new OrderCreatedEvent(order));

// 分布式消息事件（经 CAP + Outbox，与业务落库同事务）
await MessageEventBus.PublishAsync(new OrderCreatedMessageEvent(new OrderCreatedMessage { ... }, send: false));
await UnitOfWork.CommitAsync();   // ← send:false 时靠这一步投递
```

完整机制与 `send` 参数语义见 [子系统深挖](../architecture/子系统深挖.md) 与 [recipes/cap-event-outbox](recipes/cap-event-outbox.md)。

### 4.3 其它约束

- **一个处理器只能处理一个事件**：`IDomainEventHandler<TEvent>` 多实现会抛异常（`Events/Extensions.Service.cs:75-76`）。

> **领域事件是四套事件机制中的一套**，且是**唯一一套不会被派发的**。它**不实现** `Bing.Events.IEvent`、**也不经过**任何事件总线——有独立的 `IDomainEventDispatcher`。四套机制的完整对照、发布链路与"想让它真正可用"的三条路径见 **[事件与消息文档](../architecture/事件与消息文档.md)**。

## 7. 变更追踪源生成器

`framework/src/Bing.Ddd.Domain.Extensions.Analyzers` 里有一个 Roslyn **源生成器**：

`[Generator] ChangeTrackableSourceGenerator : ISourceGenerator`（`Bing/Analyzers/ChangeTrackableSourceGenerator.cs:13-14`）

**没有 `[ChangeTrackable]` 特性**，它按约定触发——**三个条件同时满足**才生成：

1. 类是 `partial`（`:90`）
2. 类继承 `DomainObjectBase`（`:45-47,70-80`）
3. 类**没有**自己 `override AddChanges`（`:92`）

生成产物为 `{命名空间}.{类名}.AddChanges.g.cs`，为每个 public 实例属性（含继承来的）生成 `AddChange(t => t.Prop, other.Prop)`，并**跳过** `Version` 与 `IsDeleted`（`:117-131,175-179`）。

## 8. 完整建模示例：`Role`

取自参考实现（`modules/admin/src/Bing.Admin.Systems.Domain/Models/Role.Base.cs`），是 `partial` 类的一半（`Role.cs` 是空壳）：

```csharp
[Display(Name = "角色")]
public partial class Role : Bing.Permissions.Identity.Models.RoleBase<Role, Guid, Guid?>, ISoftDelete, IAuditedObjectWithName
{
    public Role() : this(Guid.Empty, "", 0) { }
    public Role(Guid id, string path, int level) : base(id, path, level) { }

    [Display(Name = "创建人")]
    [StringLength(200, ErrorMessage = "创建人输入过长，不能超过200位")]
    public string Creator { get; set; }

    [Display(Name = "最后修改人")]
    [StringLength(200, ErrorMessage = "最后修改人输入过长，不能超过200位")]
    public string LastModifier { get; set; }
}
```

要点解读：

- 基类 `RoleBase<TRole, TKey, TParentId> : TreeEntityBase<…>, ISoftDelete, IAuditedObject`（`Bing.Permissions/Identity/Models/RoleBase.Base.cs:15`）
- 因为走 `TreeEntityBase`（它继承 `BasicAggregateRoot`），**`Role` 是聚合根但没有 `IVersion`**——需要乐观锁就别用这个基类
- 提供 `Code` / `Name` / `NormalizedName` / `Type` / `IsAdmin` … 及审计字段（`:25-122`），并有 `AddDescriptions`（`:143`）与 `AddChanges`（`:173`）
- **软删除是显式声明的**（`ISoftDelete`）——这正是 §3.1 第 1 条说的
- 仓储：`IRoleRepository : …IRoleRepository<Role, Guid, Guid?>`（`Systems.Domain/Repositories/IRoleRepository.cs:11`）
- 使用方：领域服务 `RoleManager`（`Systems.Domain/Services/Implements/RoleManager.cs:23,47,112`）与应用服务 `RoleService`（`Bing.Admin.Service/Implements/Systems/RoleService.cs:35,49,107,140`）

## 9. 建模陷阱清单

| # | 陷阱 | 依据 |
| --- | --- | --- |
| 1 | **实体必须有可访问的无参构造** | 基类提供 `protected` 无参（`EntityBase.cs:73`、`AggregateRoot.cs:44`）；`Role` 另提供 `public` 无参（`Role.cs:17`） |
| 2 | **EF 映射必须实现 `IMap.Map(ModelBuilder)`** | `IMap.cs:8`；推荐继承 `MapBase<TEntity> : IMap`（`MapBase.cs:11`）。`MapVersion` 只在实体实现 `IVersion` 时才把 `Version` 配为并发令牌（`:42-48`） |
| 3 | **单参基类要求 `Guid` + `IVersion`** | `AggregateRoot.cs:10,38`；FreeSQL `StoreBase.cs:14` |
| 4 | **`IStore` / `IQueryStore` 是 `IScopedDependency`** | `IQueryStore.cs:20`——单例里注入会造成 captive dependency |
| 5 | **不要往聚合根/实体里注入仓储** | 源码中聚合根无仓储构造注入；仓储由应用服务 / 领域服务注入（`RoleService.cs:49`、`RoleManager.cs:23`） |
| 6 | **`IFullAuditedObject` 不含 `ISoftDelete`** | `Role.Base.cs:12` 需显式声明 |
| 7 | **变更追踪需 `partial` + 继承 `DomainObjectBase` + 未手写 `AddChanges`** | `ChangeTrackableSourceGenerator.cs:88-93`——缺一即不生成，且**不报错** |
| 8 | **一个领域事件处理器只能处理一个事件** | `Events/Extensions.Service.cs:75-76` 会抛异常 |
| 9 | **领域事件不会被自动派发** | 见 §4.2——这是最隐蔽的一条 |
| 10 | **没有 `IHasConcurrencyStamp`** | 并发统一用 `IVersion`（`byte[]`） |
