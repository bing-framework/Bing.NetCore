# 最佳实践与反模式

> **适用版本**：框架 `7.0.0`（`version.props`）｜ 目标框架：类库 `netstandard2.0`、Web / 应用 `net6.0`｜ 内容核对：2026-09-18｜ 版本历史见 [发行说明](../ReleaseNotes.md)

> **一句话定位**：[FAQ 与排错](../getting-started/FAQ与排错.md)回答「为什么报错」，本文回答「怎么写才对」。每条给出 **✅ 推荐 / ❌ 反模式 / 为什么**。
>
> 规则分两级：**🔴 必须**——违反会导致线上故障、数据错乱或安全事件；**🟡 建议**——违反会埋坑，但不立刻爆炸。

---

## 1. 模块与启动

### 1.1 🔴 顺序靠 `Level`，不靠 `[DependsOnModule]`

```csharp
// ✅ 需要「晚于别人初始化」时用 Level / Order
[ModuleLevel(ModuleLevel.Application)]   // 20
public class MyBusinessModule : BingModule { }

// ❌ 以为声明依赖就能排顺序
[DependsOnModule(typeof(OtherModule))]   // 这只保证 OtherModule 被加载
public class MyBusinessModule : BingModule { }
```

**为什么**：排序规则只有 `Level → Order → FullName`。`[DependsOnModule]` 是**递归包含**语义，不是拓扑排序。想控制先后，只能调 `Level`。

### 1.2 🔴 非 Web 宿主必须补 `UseBing()`

```csharp
// ✅ 控制台 / WinForm
var provider = services.BuildServiceProvider();
provider.UseBing();

// ❌ 只 AddBing() 就跑
services.AddBing().AddModule<AppModule>();
```

**为什么**：`AddBing()` 只做注册，`UseBing()` 才触发 `Initialize`。不调用的话模块里的启动逻辑（迁移、种子、订阅注册）全部静默不执行——不报错，只是「什么都没发生」。参考 `samples/Bing.Samples.Winform` 目前就缺这一步。

### 1.3 🟡 一个模块只负责一件事

**为什么**：模块是 `Level` 排序的最小单位。把日志、缓存、业务塞进一个模块，就没法用 `Level` 表达先后了。

## 2. 依赖注入

### 2.1 🟡 生命周期别倒挂

```csharp
// ❌ 单例持有 Scoped
public class MySingleton : ISingletonDependency
{
    public MySingleton(IStore<Order, Guid> store) { }   // IStore 是 Scoped
}
```

**为什么**：`IStore` / `IQueryStore` / `IUnitOfWorkManager` / `IDataFilter` 都是 `IScopedDependency`。单例捕获它们会造成「captive dependency」——作用域内的 `DbContext` 会被单例长期持有。

### 2.2 🟡 想覆盖内置实现，显式声明

```csharp
// ✅
[Dependency(ServiceLifetime.Scoped, ReplaceExisting = true)]
public class MyStore : StoreBase<Order, Guid>, IStore<Order, Guid> { }

// ❌ 直接再写一个，期待它赢
public class MyStore : IStore<Order, Guid> { }
```

**为什么**：约定式 DI 默认行为是「注册」，不是「替换」；最终解析到哪个取决于注册顺序。要覆盖请显式 `ReplaceExisting = true`。

### 2.3 🟡 需要拿实现类本身时开 `AddSelf`

```csharp
[Dependency(AddSelf = true)]   // 除了接口，额外注册 MyServiceImpl 自身
public class MyServiceImpl : IMyService { }
```

**为什么**：默认只注册接口。有时你要注入具体类型（如测试替身、或同一接口多实现需要区分），不开 `AddSelf` 会解析失败。

### 2.4 🟡 别让一个类实现一堆无关接口

**为什么**：约定式 DI 会把**所有**实现的接口都注册一遍。一个服务顺手实现 `IDisposable` 或标记接口，可能产生意外的注册。用 `[IgnoreDependency]` 排除。

## 3. 领域与仓储

### 3.1 🔴 别在实体里注入仓储

```csharp
// ❌
public class Order : IAggregateRoot<Guid>
{
    public Order(IStore<OrderItem, Guid> itemStore) { }   // 实体不该知道持久化
}
```

**为什么**：实体应当是纯粹的业务对象。跨聚合的查询逻辑放应用服务或领域服务，实体只管自己边界内的一致性。

### 3.2 🟡 仓储只在应用服务/领域服务里用

**为什么**：`IStore` 是 `IScopedDependency` 且持有 `DbContext`。在 Controller 里直接注入也能跑，但会让事务边界变得模糊，且难以复用业务逻辑。

### 3.3 🟡 跨聚合查询走只读存储

```csharp
// ✅ 只读场景注入 IQueryStore，语义更清楚
public OrderAppService(IQueryStore<Order, Guid> queryStore, IStore<Order, Guid> store)
```

**为什么**：`IStore : IQueryStore`。只读路径注入 `IQueryStore` 能明确表达「这里不写」，也避免误调用写方法。

## 4. 工作单元与事务

### 4.1 🔴 一次请求一个工作单元，别在循环里提交

```csharp
// ❌ N 次事务
foreach (var item in items)
{
    await _store.AddAsync(item);
    await _unitOfWork.CommitAsync();
}

// ✅ 一次事务
foreach (var item in items) await _store.AddAsync(item);
await _unitOfWork.CommitAsync();
```

> 写方法是 **`AddAsync`**（`IStore.cs:39`），**没有 `InsertAsync`**。详见 [工作单元仓储与应用服务](工作单元仓储与应用服务.md)。

**为什么**：每次 `Commit` 都是一次数据库事务往返，N 条数据就是 N 次。批量大时请改用 Bing.Data.Sql 的 `InsertBatch`（见 [能力矩阵 §5.4](../getting-started/能力矩阵.md)）。

### 4.2 🔴 别指望跨 ORM 共享事务

```csharp
// ❌ 以为 EF 的 UoW 能罩住 Bing.Data.Sql 的执行
await _efUnitOfWork.CommitAsync();
await _sqlExecutor.ExecuteSqlAsync("...");   // 这是另一条连接、另一个事务
```

**为什么**：EF 的事务与 `ISqlTransactionScope` 是两条独立链路。混合使用时，一致性要么靠**同一支**完成，要么改用 CAP 事件做最终一致。

### 4.3 🟡 长事务是大忌

**为什么**：事务里做 HTTP 调用、发消息、读文件，会把数据库连接占住。先把外部调用挪出事务，或用 Outbox 把消息落库后异步投递。

## 5. 事件与消息

### 5.1 🔴 本地事件别用消息总线

```csharp
// ✅ 进程内消费
await _simpleEventBus.PublishAsync(new OrderCreatedEvent(...));

// ❌ 明明只在本地用，却发到消息总线
await _messageEventBus.PublishAsync(new OrderCreatedEvent(...));   // 多一次落库 + 一次投递
```

**为什么**：`IMessageEventBus` 走 CAP + Outbox，会往数据库写一条消息记录再异步投递。纯本地场景白白付出这个成本。

### 5.2 🔴 订阅端必须幂等

```csharp
// ✅
public async Task HandleAsync(OrderCreatedEvent e)
{
    if (await _store.ExistsAsync(x => x.ExternalId == e.Id)) return;   // 幂等检查
    ...
}
```

**为什么**：消息是**至少一次**投递，重复消费一定会发生。不幂等就是重复下单、重复扣款。

### 5.3 🔴 用 `[EventHandler]`，不是 `[CapSubscribe]`

```csharp
// ✅
public class OrderHandler : ICapSubscribe
{
    [EventHandler("order.created")]
    public Task HandleAsync(OrderCreatedEvent e) { ... }
}

// ❌ [CapSubscribe] 不是本框架的订阅写法
```

**为什么**：`[EventHandler]` 继承 CAP 的 `TopicAttribute`，框架按它扫描注册。用 `[CapSubscribe]` 会订阅不生效。

### 5.4 🟡 消息要小而稳

**为什么**：消息会被序列化落库并长期保留。塞大对象或实体（而非 DTO）会让消息体积膨胀，且实体结构一变历史消息就反序列化失败。

## 6. 数据访问选型

### 6.1 🔴 别以为装了 Bing.Data.Sql 就有仓储

**为什么**：那一支**没有 `IUnitOfWork`、没有 `IStore`、没有审计、没有乐观锁**。它是 SQL 构建器 + 执行器。要领域层能力请选 EF Core / FreeSQL。详见 [能力矩阵](../getting-started/能力矩阵.md)。

### 6.2 🟡 FreeSQL 支的高频异步路径要绕开 `IQueryable`

```csharp
// ❌ 会同步阻塞调用线程
var list = await queryable.ToListAsync();

// ✅ 用仓储自带的异步方法
var list = await _store.FindAllAsync(x => x.Status == 1);
```

**为什么**：`FreeSqlAsyncQueryableProvider.CanExecute` 恒为 `false`，`AsyncQueryableExecuter` 会退化为 `Task.FromResult(queryable.ToList())`——不报错，但同步阻塞。详见 [能力矩阵 §4.3](../getting-started/能力矩阵.md)。

### 6.3 🟡 原生 SQL 必须参数化

```csharp
// ❌
ExecuteSql($"SELECT * FROM t WHERE name = '{name}'");

// ✅
SqlInterpolated($"SELECT * FROM t WHERE name = {name}");
```

**为什么**：`Bing.Data.Sql.Analyzers` 会报 `BINGSQL002` 提示注入风险。字符串拼接是注入的直接来源。

## 7. 缓存

### 7.1 🟡 缓存没有 `AddCache`，必须手工装配

```csharp
// ✅
RedisHelper.Initialization(config);
services.AddScoped<ICache, CSRedisCacheManager>();
```

**为什么**：框架**没有**内置缓存注册入口（没有 `AddCache` / `AddCaching`）。`Bing.EasyCaching` 的 `AddCaching` 目前整段被注释，不可用。详见 [使用文档 §3.3](../getting-started/使用文档.md) 与 [组件库文档](组件库文档.md)。

### 7.2 🟡 缓存键要带版本/前缀

**为什么**：实体结构变了但缓存键没变，会读到旧结构的数据。键里带上类型名或版本号可低成本规避。

## 8. 异常与日志

### 8.1 🔴 别吞异常

```csharp
// ❌
try { ... } catch { }

// ✅ 至少记录，或转成框架异常类型
catch (Exception e) { _logger.LogError(e, "..."); throw; }
```

**为什么**：静默失败是线上最难排查的问题类型。框架的统一异常处理（`UseBingExceptionHandling()`）依赖异常能传到中间件。

### 8.2 🟡 用框架异常类型而非裸抛

**为什么**：`ConcurrencyException`、`BingException` 等会被统一异常处理映射成合适的状态码与响应格式；裸抛 `Exception` 一律按 500 处理。

## 9. 安全与配置

### 9.1 🔴 凭据不要写进受版本控制的配置文件

```json
// ❌ appsettings.json 里硬编码
{ "ConnectionStrings": { "Default": "Server=...;Password=RealPassword" } }

// ✅ 环境变量 / 用户机密 / appsettings.Development.json（不入库）
```

**为什么**：`modules/admin` 目前把 MySQL / Redis / RabbitMQ 的真实凭据写在了**受版本控制**的 `appsettings.json` 与 `CapModule.cs` 里。这是真实的安全风险，建议尽快迁移到环境变量或用户机密。本文档不复述这些值。

### 9.2 🟡 日志脱敏

**为什么**：请求响应日志中间件会把请求体写进日志。含密码、身份证、令牌的接口要脱敏，否则凭据会落到日志系统里。

## 10. 性能

### 10.1 🟡 优先让实体映射缓存命中

**为什么**：`Bing.Data.Sql` 的实体映射有缓存，反复用不同的方式构造查询（如动态类型、每次新建映射）会击穿缓存，导致每次都重新反射解析。

### 10.2 🟡 大批量写入别走 ORM 逐条

**为什么**：EF / FreeSQL 支都没有 Bulk 扩展。上万条请用 `Bing.Data.Sql` 的 `InsertBatch`（带分窗与事务选项）。

### 10.3 🟡 分页记得处理「不支持自动分页」的场景

**为什么**：含 CTE 的 `Union`/`Group`/`Distinct` 查询、以及原生 SQL 都**不支持自动分页计数**，需要预先设置 `TotalCount`。详见 [能力矩阵 §5.5](../getting-started/能力矩阵.md)。

## 11. 测试

### 11.1 🔴 改数据访问必跑 SQLite 集成测试

**为什么**：`AGENTS.md` 规定——涉及 Provider、连接、执行器、查询工厂的改动必须跑本地 SQLite 集成测试（默认可跑，无需外部数据库）。外部库测试才需要 `RUN_INTEGRATION_TESTS` 门控。

### 11.2 🟡 改公开 API 记得更新 PublicAPI 基线

**为什么**：`common.props` 把 RS0016/17/18/RS0026 提为 **error**，不更新基线会直接编译失败。注意**只有 7 个工程**启用了基线，其余工程的公开 API 变更不会被拦截——改之前先确认目标工程在不在名单里。详见 [工程化文档](../operations/工程化文档.md)。

## 12. 反模式速查表

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 靠 `[DependsOnModule]` 排顺序 | 顺序不生效 | 用 `ModuleLevel` / `Order` |
| 只 `AddBing()` 不 `UseBing()` | 模块初始化静默不执行 | 补 `provider.UseBing()` |
| 单例注入 `IStore` | Captive dependency | 改为 Scoped |
| 把 Bing.Data.Sql 当 ORM 用 | 没有 UoW/仓储/审计 | 用 EF Core / FreeSQL |
| 循环里 `CommitAsync()` | N 次事务往返 | 批量提交或 `InsertBatch` |
| 跨 ORM 期待同一事务 | 一致性不成立 | 同支完成或 CAP 最终一致 |
| 消息消费者不幂等 | 重复业务副作用 | 幂等检查 |
| 用 `[CapSubscribe]` 订阅 | 订阅不生效 | 用 `[EventHandler]` |
| 硬编码连接串密码 | 凭据泄露 | 环境变量 / 用户机密 |
| 期待缓存有 `AddCache` | 没有该入口 | 手工 `RedisHelper.Initialization` + `AddScoped` |
| FREESQL 上用 `ToListAsync()` | 同步阻塞线程 | 用仓储异步方法 |
| 改动数据访问不跑集成测试 | 线上才发现 | 跑 SQLite 本地集成测试 |
