## 0. 先记住这 8 条

读完这 8 条再翻细节，能避开本篇 90% 的坑：

1. **只有一个分布式事件入口**：`IMessageEventBus`（`Bing.Events.Messages`），底层是 CAP 8.0.1。`ISimpleEventBus` 是**进程内**的，不是分布式。
2. **`send` 参数决定是"立即发"还是"随事务发"**。`send=true` → 立刻投递 MQ；`send=false`（默认）→ 登记进当前事务，等 `SaveChangesAsync` 时才发。
3. **`send=false` 的可靠性靠工作单元兜底**，而**框架基类的工作单元不认识 CAP** —— 只有像 admin 的 `AdminUnitOfWork` 那样重写过 `SaveChangesAsync` 的工作单元才真正把消息和业务数据放进同一个事务。
4. **没有任何工作单元保存动作时，`send=false` 的消息会静默消失**。不抛异常、不打日志。这是本篇最危险的坑。
5. **订阅端特性是 `[EventHandler]`，不是 `[CapSubscribe]`**。前者继承自后者的基类 `TopicAttribute`，功能等价，但**本框架的代码一律用 `[EventHandler]`**。
6. **消息头里的链路标识叫 `bing-trace-id`**，不是 `X-Correlation-Id`。发布端自动写、消费端自动读（靠替换 `ISubscribeInvoker`），通常不需要你手工处理。
7. **`IEventBus` 是"两级发布"的合并入口**：它先发本地处理器，**若事件还实现了 `IMessageEvent`**，再发 CAP。用它可以让一个事件同时具备本地与跨服务语义。
8. **CAP 的存储表与业务表在同一个库**（admin 用 `AdminUnitOfWork`），这是 Outbox 成立的前提；换了工作单元就要重新确认这一点。

## 1. 五分钟上手

### 1.1 装哪些包

| 包 | 作用 | 必需 |
| --- | --- | --- |
| `Bing.Core` | 事件抽象：`IEvent` / `ISimpleEventBus` / `IMessageEventBus` / `IMessageEvent` / `MessageEvent<T>` / `IEventHandler<T>` | ✅ |
| `Bing.Events` | 两套实现：`Bing.Events.Default.EventBus`（本地）、`Bing.Events.Cap.MessageEventBus`（CAP） | ✅ |
| `Bing.Data` | `ITransactionActionManager`（Outbox 登记表，`Bing.Data.Transaction`）—— 通常是传递依赖 | ✅ |

> `Bing.Events.Cap.MySql`（CAP 源码 fork）**当前无人引用**，不要装。详见 [功能完成度 §7](../architecture/功能完成度.md)。

### 1.2 只有本地事件（进程内）

```csharp
using Bing.Events.Default;          // AddDefaultEventBus

services.AddDefaultEventBus();
```

只注册三样（`Bing.Events/Default/Extensions.Service.cs:17-23`）：`IEventHandlerManager`、`ISimpleEventBus`、`IEventBus`，**全部 Singleton**，实现都是 `Bing.Events.Default.EventBus`。

⚠ 这套下 **`IMessageEventBus` 没有被注册**——注入它会直接抛"无法解析服务"。

### 1.3 要分布式事件（CAP）

```csharp
using Bing.Events.Cap;              // AddCapEventBus

services.AddCapEventBus(o =>
{
    o.UseEntityFramework<AdminUnitOfWork>();   // Outbox 表建在业务库
    o.UseDashboard();                          // /cap 面板
    o.FailedRetryCount = 5;
    o.SucceedMessageExpiredAfter = 24 * 3600;
    o.Version = "admin";
    o.UseRabbitMQ(x => { x.HostName = "…"; x.UserName = "…"; x.Password = "…"; });
});
```

`AddCapEventBus` 的完整实现（`Bing.Events/Cap/Extensions.Service.cs:22-31`）：

```csharp
public static IServiceCollection AddCapEventBus(this IServiceCollection services,
    Action<CapOptions> action, Action<CapBuilder> builderSetup = null)
{
    services.TryAddSingleton<IEventHandlerManager, EventHandlerManager>();
    services.TryAddSingleton<ISimpleEventBus, Default.EventBus>();
    services.TryAddScoped<IMessageEventBus, MessageEventBus>();
    services.TryAddScoped<IEventBus, EventBus>();      // 注意：Scoped，且是 CAP 版
    var builder = services.AddCap(action);
    builderSetup?.Invoke(builder);
    return services;
}
```

注意两点：**`IMessageEventBus` 是 Scoped**（它要注入同样 Scoped 的 `ITransactionActionManager`）；**`IEventBus` 在这里注册的是 `Bing.Events.Cap.EventBus`**，与 1.2 那套的 `Bing.Events.Default.EventBus` 是**两个不同的类**。

### 1.4 定义消息事件

```csharp
using Bing.Events;
using Bing.Events.Messages;

public class OrderPaidMessage
{
    public Guid OrderId { get; set; }
    public decimal Amount { get; set; }
}

// 消息事件 = 事件 + 消息名 + 负载 + Send 开关
public class OrderPaidMessageEvent : MessageEvent<OrderPaidMessage>
{
    public OrderPaidMessageEvent(OrderPaidMessage data, bool send = true) : base(data)
    {
        Send = send;
        Name = "myapp.order.paid";        // 消息名，发布/订阅两端必须一致
    }
}
```

### 1.5 发布

```csharp
public class OrderAppService : IOrderAppService
{
    private readonly IMessageEventBus _messageEventBus;

    public OrderAppService(IMessageEventBus messageEventBus) => _messageEventBus = messageEventBus;

    [UnitOfWork]
    public async Task PayAsync(Guid orderId)
    {
        // …业务写入…

        // send: false —— 随当前工作单元一起提交（推荐，见 §4）
        await _messageEventBus.PublishAsync(new OrderPaidMessageEvent(
            new OrderPaidMessage { OrderId = orderId, Amount = 99m }, send: false));
    }
}
```


### 2.2 继承链

```
IEvent
 ├─ Event                      (Id, Time, GetEventName())
 │   └─ MessageEvent           (+ Name, Data, Callback, Send)  ─┐
 │       └─ MessageEvent<T>    (构造注入 Data)                  │ implements
 │                                                              │
 └──────────────────────────────────────── IMessageEvent ◄──────┘
```

关键点：**`IMessageEvent` 是 `MessageEvent` 上挂的标记接口**（`MessageEvent.cs:8`：`public class MessageEvent : Event, IMessageEvent`）。所以「是不是分布式事件」取决于类型是否实现了 `IMessageEvent`——不是看你调了哪个总线。

### 2.3 三个总线接口的分工

| 接口 | 谁实现 | 生命周期 | 干什么 |
| --- | --- | --- | --- |
| `ISimpleEventBus` | `Default.EventBus` | Singleton | 遍历 `IEventHandler<T>` 逐个 `HandleAsync`（**进程内、无持久化**） |
| `IMessageEventBus` | `Cap.MessageEventBus` | **Scoped** | 落到 CAP：立即投递 或 登记到事务 |
| `IEventBus` | `Default.EventBus`（本地套）或 `Cap.EventBus`（CAP 套） | Singleton / **Scoped** | 两级合并：先本地，再（若实现 `IMessageEvent`）CAP |

本地分发的实现极简（`Bing.Events/Default/EventBus.cs:29-40`）——**同步顺序执行所有处理器，一个抛异常后面的就不执行了**：

```csharp
public async Task PublishAsync<TEvent>(TEvent @event) where TEvent : IEvent
{
    var handlers = Manager.GetHandlers<TEvent>();
    if (handlers == null) return;
    foreach (var handler in handlers)
    {
        if (handler == null) continue;
        await handler.HandleAsync(@event);
    }
}
```

处理器从哪来？`EventHandlerManager` 用 **`ServiceLocator.Instance.GetServices<IEventHandler<TEvent>>()`**（`Default/EventHandlerManager.cs:16`）—— 即**从 DI 容器解析**，所以本地处理器必须注册进容器。

## 3. 发布：`IMessageEventBus`

### 3.1 两个重载

```csharp
// 泛型版：自动从事件对象取 Name / Data / Callback / Send
Task PublishAsync<TEvent>(TEvent @event, CancellationToken cancellationToken = default)
    where TEvent : IMessageEvent;

// 原始版：手工指定四个字段
Task PublishAsync(string name, object data, string callback = null,
                  bool send = false, CancellationToken cancellationToken = default);
```

泛型版只是转发（`Cap/MessageEventBus.cs:52-54`）：

```csharp
public Task PublishAsync<TEvent>(TEvent @event, CancellationToken cancellationToken = default)
    where TEvent : IMessageEvent =>
    PublishAsync(@event.Name, @event.Data, @event.Callback, @event.Send, cancellationToken);
```

> 想不带事件类、直接发个匿名对象？用原始版：`await bus.PublishAsync("myapp.ping", new { At = DateTime.Now });`。注意 **`send` 默认 `false`**，而原始版**没有默认 `true`**，所以直发要显式写 `send: true`。

### 3.2 `send` 参数：立即发 vs 随事务发

`Cap/MessageEventBus.cs:64-77`：

```csharp
public async Task PublishAsync(string name, object data, string callback = null,
    bool send = false, CancellationToken cancellationToken = default)
{
    var headers = new Dictionary<string, string> { { DotNetCore.CAP.Messages.Headers.CallbackName, callback } };
    InitTraceIdContext(headers);
    if (send)
    {
        await InternalPublishAsync(name, data, headers, callback, cancellationToken);
        return;                                    // ← 立刻投递
    }
    TransactionActionManager.Register(async transaction =>   // ← 登记，等提交
    {
        await InternalPublishAsync(name, data, headers, callback, cancellationToken);
    });
}
```

| `send` | 行为 | 适用 |
| --- | --- | --- |
| `true` | **立即** `ICapPublisher.PublishAsync`，不等待任何事务 | 通知类、日志类、失败不影响主流程 |
| `false`（默认） | 登记进 `ITransactionActionManager`，**等当前工作单元保存时**才发 | 业务事件，要求"业务成功则消息必发" |

### 3.3 两级发布：`IEventBus` 做了什么

`Bing.Events/Cap/EventBus.cs:36-42`：

```csharp
public async Task PublishAsync<TEvent>(TEvent @event) where TEvent : IEvent
{
    await SimpleEventBus.PublishAsync(@event);              // ① 进程内处理器
    if (!(@event is IMessageEvent messageEvent))
        return;                                             // ② 不是消息事件就到此为止
    await MessageEventBus.PublishAsync(messageEvent);       // ③ 再走 CAP
}
```

**这带来一个清晰约定**：让事件类实现 `IMessageEvent`，它就"本地 + 跨服务"双发；不实现，就纯本地。调用方注入 `IEventBus` 即可，不用自己判断。

⚠ 但注意 `IEventBus` 的注册实现取决于你调了哪个注册方法：`AddDefaultEventBus` 给的是**只做本地**的 `Default.EventBus`；要两级语义必须调 `AddCapEventBus`（它注册 CAP 版且是 Scoped）。

### 3.4 本地事件 vs 分布式事件：怎么选

| 场景 | 用哪个 |
| --- | --- |
| 同一进程内的副作用（更新统计、写审计） | `ISimpleEventBus` |
| 跨服务/跨进程通知 | `IMessageEventBus` |
| 需要"本地处理 + 跨服务广播" | `IEventBus` + 事件实现 `IMessageEvent` |
| 聚合根内部收集、稍后统一派发 | ⛔ **不可用**，领域事件派发机制未接通，见 [功能完成度 §7.1](../architecture/功能完成度.md) |

## 4. Outbox：`send=false` 的完整链路

这是本篇最关键的一节。`send=false` 的可靠性**完全依赖工作单元的配合**，而这里有几个容易忽略的前提。

### 4.1 链路

```
应用服务调用
  _messageEventBus.PublishAsync(evt, send: false)
      └─> ITransactionActionManager.Register(action)          [登记进当前作用域]
              ↓
  _unitOfWork.CommitAsync() / SaveChangesAsync()
      └─> Create<ITransactionActionManager>()  ← 从同一 DI 作用域解析
          └─> Count == 0 ? 直接保存
                        : TransactionCommitAsync(...)
                            ├─ 开事务
                            ├─ transactionActionManager.CommitAsync(transaction)  ← 真正发消息
                            └─ base.SaveChangesAsync()                            ← 写业务数据
                            └─ commit
```

源码依据：

| 环节 | 位置 |
| --- | --- |
| 登记 | `Bing.Events/Cap/MessageEventBus.cs:73` |
| 登记表是 Scoped | `Bing.Data/…/ITransactionActionManager.cs:11`（`: IScopedDependency`） |
| 取登记表 | `Bing.EntityFrameworkCore/Core/UnitOfWorkBase.cs:557`（`Create<ITransactionActionManager>()`） |
| 分叉 | 同上 `:558-560` |
| 先发消息后写库 | 同上 `:590`（`CommitAsync`）→ `:593`（`base.SaveChangesAsync`） |
| 提交 | 同上 `:615` |
| admin 重写 | `Bing.Admin.Data.EFCore/UnitOfWorks/MySql/AdminUnitOfWork.cs:27-66` |

`Create<T>()` 用的是 **`_serviceProvider.GetService(typeof(T))`**（`UnitOfWorkBase.cs:96-102`），`_serviceProvider` 就是工作单元构造时注入的那个作用域容器——**所以登记与读取是同一个实例**，链路成立。

### 4.2 三个前提（缺一个就失效）

**前提一：工作单元必须"认识 CAP"。**

⚠ 这是最容易踩的一条。**框架基类 `Bing.EntityFrameworkCore` 里没有任何 CAP 引用**（全仓 grep `ICapPublisher` / `DotNetCore.CAP` 在该工程零命中）。所以基类的 `TransactionCommitAsync`（`UnitOfWorkBase.cs:571-621`）用的是**普通 ADO.NET 事务**：

```csharp
await using (var transaction = await connection.BeginTransactionAsync(cancellationToken))
```

此时 CAP 的 `ICapPublisher.Transaction` **没有被设置**，`Publisher.PublishAsync` 会走**立即发送**——消息发出去了，但**不在业务事务内**，Outbox 保证丢失。

admin 之所以是对的，是因为它**重写了 `SaveChangesAsync`**，改用 CAP 的 EF 事务扩展（`AdminUnitOfWork.cs:49`）：

```csharp
using (var capTransaction = Database.BeginTransaction(publisher, autoCommit: false))
{
    await transactionActionManager.CommitAsync(publisher.Transaction.Value.DbTransaction as IDbTransaction);
    var result = await base.SaveChangesAsync(cancellationToken);
    await capTransaction.CommitAsync(cancellationToken);
    return result;
}
```

**为什么"把事务传进去"没用**：这是最容易误解的一点。登记动作的签名虽然收 `IDbTransaction`，但 `MessageEventBus` **完全忽略这个参数**（`Bing.Events/Cap/MessageEventBus.cs:73-76`）：

```csharp
TransactionActionManager.Register(async transaction =>   // ← 这个 transaction 从未被使用
{
    await InternalPublishAsync(name, data, headers, callback, cancellationToken);
});
```

`InternalPublishAsync` 只是调 `Publisher.PublishAsync(...)`（`:90`），而 CAP 判断"要不要写发件箱"看的是**自己的环境事务**（`ICapPublisher.Transaction` 是否已开启），**不看**你传进来的那个 `IDbTransaction`。所以基类工作单元即使把事务对象递进去，CAP 也不认——它仍然走立即发送。

这就是 admin 必须用 `Database.BeginTransaction(publisher, autoCommit: false)` 的原因：**先让 CAP 建立起环境事务**，之后动作里的 `PublishAsync` 才会写进发件箱。

**结论**：要用 `send=false` 的可靠性，你的工作单元必须像 `AdminUnitOfWork` 这样接上 CAP 事务。用裸的 `UnitOfWorkBase` 子类而不重写，`send=false` 会退化成"立即发送、且在事务外"。

**前提二：必须真的发生一次保存。**

登记表只在 `SaveChangesAsync` / `CommitAsync` 里被排空。如果方法上没有 `[UnitOfWork]`、也没人手工调用提交，**登记的发送动作永远不会执行**——不抛异常、不打日志、没有任何痕迹。这就是 §0 第 4 条那个坑。

**前提三：发布与提交在同一个 DI 作用域内。**

`IMessageEventBus` 与 `ITransactionActionManager` 都是 Scoped。如果把发布塞进 `Task.Run(...)` 或另开作用域，登记进的是**另一个** `TransactionActionManager`，当前工作单元看不到 → 消息静默丢失。

### 4.3 事务里的顺序

注意 `TransactionCommitAsync` 的顺序是 **先发消息、再写业务数据**（`:590` → `:593`），两者在**同一个事务**里：

```csharp
await transactionActionManager.CommitAsync(transaction);   // 写 cap.published + 投递准备
await Database.UseTransactionAsync(transaction, cancellationToken);
result = await base.SaveChangesAsync(cancellationToken);   // 写业务数据
// …commit / rollback
```

所以业务失败回滚时，`cap.published` 里的记录**也一起回滚**——消息不会发出去。这就是 Outbox 语义：**要么都成，要么都不发**。

### 4.4 `send=true` 没有这层保护

`send=true` 直接 `Publisher.PublishAsync`，**与业务事务无关**。事务回滚了消息也已经发出去了。这不是缺陷，是语义选择——用在"发了就发了"的通知场景。

## 5. 订阅

### 5.1 处理器三件套

一个可用的订阅处理器需要三样：

1. **实现 `ICapSubscribe`**（`DotNetCore.CAP`）——CAP 靠它识别订阅者；
2. **方法上标 `[EventHandler("<消息名>")]`**；
3. **注册进 DI**。

### 5.2 `[EventHandler]` 与 `[CapSubscribe]` 的关系

`Bing.Events/EventHandlerAttribute.cs:8-16`：

```csharp
public class EventHandlerAttribute : TopicAttribute
{
    public EventHandlerAttribute(string name) : base(name) { }
}
```

CAP 的 `[CapSubscribe]` 也继承自 `TopicAttribute`，所以**两者功能等价**，只是本框架统一用 `[EventHandler]`。好处是 `Group` 这类基类属性依然可用：

```csharp
[EventHandler(MessageEventConst.UserLogin, Group = QueueGroupConst.UserLoginLog)]
```

### 5.3 方法签名允许的形态

```csharp
// 只要消息体
[EventHandler("app.x")] public Task HandleAsync(XMessage message);

// 消息体 + CAP 消息头（要读自定义头时必须）
[EventHandler("app.x")] public Task HandleAsync(XMessage message, [FromCap] CapHeader header);

// 可以是 async Task，也可以是返回 Task 的同步方法
```

⚠ 方法名、类名都与路由无关——**路由只认 `[EventHandler]` 里的字符串**。两端字符串哪怕只差一个字符，CAP 就会把它当成两条不同的消息。

### 5.4 处理器怎么被发现与注册

CAP 的默认消费者选择器会从 **DI 容器**里找 `ICapSubscribe` 的实现，并按 `TopicAttribute` 归组。**所以处理器必须注册进容器**。admin 的做法是手工集中注册（`Bing.Admin/Modules/CapModule.cs:77-81`）：

```csharp
protected void LoadEvent(IServiceCollection services)
{
    services.AddTransient<IUserLoginLogMessageEventHandler, UserLoginLogMessageEventHandler>();
    services.AddTransient<ITestMessageEventHandler, TestMessageEventHandler>();
}
```

注意它注册的是**接口 → 实现**，接口继承体系是独立的（`ITestMessageEventHandler` 只是个普通接口，不含 `ICapSubscribe`）；CAP 找到的是实现类。

> admin 里还有一行被注释掉的 `services.AddSingleton<IConsumerServiceSelector, CapConsumerServiceSelector>();`（`CapModule.cs:46`）——那是曾经想替换选择器，现在用的是 CAP 默认行为。

### 5.5 分组与并发

| 配置 | 位置 | 作用 |
| --- | --- | --- |
| `[EventHandler(name, Group = "…")]` | 处理器方法 | 同组消息在同一消费者组内竞争消费 |
| `o.UseDispatchingPerGroup = true` | `CapModule.cs:68` | 按组派发（admin 开启） |
| `o.ConsumerThreadCount = 1` | `CapModule.cs:67` | 消费线程数 |

`Group` 常量集中定义在 `Bing.Admin.Infrastructure/QueueGroupConst.cs`。

## 6. TraceId 贯通

### 6.1 发布端（自动）

`Cap/MessageEventBus.cs:125-131`：

```csharp
private static void InitTraceIdContext(IDictionary<string, string> headers)
{
    if (TraceIdContext.Current == null)
        TraceIdContext.Current = new TraceIdContext(string.Empty);
    if (!headers.ContainsKey(Headers.TraceId))
        headers[Headers.TraceId] = TraceIdContext.Current.TraceId;
}
```

**消息头名是 `"bing-trace-id"`**（`Cap/Headers.cs:11`，`internal`）。发布时自动带上当前 `TraceIdContext.Current.TraceId`。

### 6.2 消费端（两种，任选）

**方式一：替换 `ISubscribeInvoker`（全局，admin 用的就是这个）**

`Bing.Admin/Modules/CapModule.cs:87-130`：

```csharp
services.AddSingleton<ISubscribeInvoker, CapSubscribeInvoker>();

public class CapSubscribeInvoker : SubscribeInvoker
{
    protected override object GetInstance(IServiceProvider provider, ConsumerContext context)
    {
        var capHeader = new CapHeader(context.DeliverMessage.Headers);
        InitTraceIdContext(capHeader);          // ← 每个消费方法执行前注入
        return base.GetInstance(provider, context);
    }

    private void InitTraceIdContext(CapHeader capHeader)
    {
        if (capHeader == null) return;
        if (!capHeader.TryGetValue("bing-trace-id", out var traceId)) return;
        if (TraceIdContext.Current == null) TraceIdContext.Current = new TraceIdContext(traceId);
        else TraceIdContext.Current.TraceId = traceId;
    }
}
```

一次替换，**所有订阅方法**都生效。

**方式二：`[CapTrace]` 特性（按方法，AOP）**

`Bing.Events/Cap/CapTraceAttribute.cs` 是个 `InterceptorBase`，它找方法里标了 `[FromCap]` 的 `CapHeader` 参数并注入 TraceId。用法：

```csharp
[CapTrace]
[EventHandler("app.x")]
public Task HandleAsync(XMessage message, [FromCap] CapHeader header) { … }
```

⚠ 要求方法**必须有 `[FromCap] CapHeader` 参数**，否则拦截器直接 `next()` 什么都不做（`CapTraceAttribute.cs:19-24`）。admin 的 `TestMessageEventHandler` 里这行是**注释掉的**（`TestMessageEventHandler.cs:48`）——因为全局的 `CapSubscribeInvoker` 已经覆盖了，不必重复。

### 6.3 链路为什么重要

消费端后台线程没有 HTTP 上下文，**不会**自动继承发布端的 TraceId。少了这一步，消费端日志的 CorrelationId 与发布端对不上，链路在消息处断掉。详见 [日志与可观测性 §5](../operations/日志与可观测性.md)。

## 7. CAP 配置（以 admin 为实例）

`Bing.Admin/Modules/CapModule.cs:51-69` 的真实配置，逐项说明：

| 配置 | 值 | 说明 |
| --- | --- | --- |
| `UseEntityFramework<AdminUnitOfWork>()` | — | **Outbox 存储**。表建在 `AdminUnitOfWork` 指向的库，与业务数据同库（前提一） |
| `UseDashboard()` | — | 启用 CAP 面板 |
| `SucceedMessageExpiredAfter` | `24 * 3600` | 成功消息保留 24h 后清理 |
| `FailedRetryCount` | `5` | 失败重试次数 |
| `Version` | `"admin"` | 表名后缀，用于多应用共库隔离 |
| `UseRabbitMQ(...)` | ⚠ 硬编码 | `UserName` / `Password` / `HostName` **直接写在源码里** |
| `ConsumerThreadCount` | `1` | 消费线程数 |
| `UseDispatchingPerGroup` | `true` | 按组派发 |

**表名**：CAP 的 EF 存储默认前缀 `cap`，默认表是 `cap.published` / `cap.received`；设置了 `Version` 会把版本拼进表名（admin → `cap.published.admin` / `cap.received.admin`）。建表由 CAP 自动完成。

> ⚠ admin 的 RabbitMQ 凭据（`CapModule.cs:63-65`）是**明文硬编码**，且 `appsettings.json` 里也有 MySQL / Redis / JWT 密钥。这些已在 [安全指南](../operations/安全指南.md) 登记，本文只做标注、不改代码。

**另一个宿主的差异**：`Bing.Admin.FreeSQL` 用的是 `o.UseMySql(connection)` 而非 `UseEntityFramework<AdminUnitOfWork>()`，因为它走 FreeSQL 的事务体系。

## 8. 注册入口全表

| 入口 | 命名空间 | 签名 | 注册了什么 |
| --- | --- | --- | --- |
| `AddDefaultEventBus()` | `Bing.Events.Default` | `IServiceCollection AddDefaultEventBus(this IServiceCollection)` | `IEventHandlerManager`(Singleton)、`ISimpleEventBus`(Singleton)、`IEventBus`(Singleton) —— **无 CAP** |
| `AddCapEventBus(...)` | `Bing.Events.Cap` | `IServiceCollection AddCapEventBus(this IServiceCollection, Action<CapOptions>, Action<CapBuilder> = null)` | 上述三样 + `IMessageEventBus`(**Scoped**)、`IEventBus`(**Scoped**，CAP 版) + `AddCap(action)` |
| `AddCap(action)` | `DotNetCore.CAP` | CAP 原生 | CAP 基础设施 |

**两者都用 `TryAdd*`**，所以**先注册的生效**。若同时需要本地与 CAP，**只调 `AddCapEventBus` 就够了**（它把本地那套也注册了）；两个都调时先调的那个决定 `IEventBus` 的实现与生命周期。

## 9. 完整示例：admin 的登录消息

这条链路是仓库里最完整的分布式事件案例。

### 9.1 消息与事件（`Bing.Admin.Systems.Domain/Events/UserLoginMessageEvent.cs`）

```csharp
public class UserLoginMessageEvent : MessageEvent<UserLoginMessage>
{
    public UserLoginMessageEvent(UserLoginMessage data, bool send = true) : base(data)
    {
        Send = send;
        Name = MessageEventConst.UserLogin;
    }
}

public class UserLoginMessage : IEventSession
{
    public string Ip { get; set; }
    public string UserAgent { get; set; }
    public Guid UserId { get; set; }
    public string Name { get; set; }
    public string SessionId { get; set; }        // ← IEventSession
}
```

消息名 `MessageEventConst.UserLogin` = `"utopa.erp." + "UserLogin"`（`MessageEventConst.cs:11,16`）。

### 9.2 订阅端（`Bing.Admin.EventHandlers/Implements/Systems/UserLoginLogMessageEventHandler.cs`）

```csharp
public class UserLoginLogMessageEventHandler : MessageEventHandlerBase, IUserLoginLogMessageEventHandler
{
    public UserLoginLogMessageEventHandler(IAdminUnitOfWork unitOfWork,
        IUserLoginLogManager userLoginLogManager, …) { … }

    [EventHandler(MessageEventConst.UserLogin, Group = QueueGroupConst.UserLoginLog)]
    public async Task UserLoginAsync(UserLoginMessage message)
    {
        await Task.Delay(5000);                                    // ⚠ 疑似调试遗留
        await UserLoginLogManager.CreateAsync(message.MapTo(new UserLoginLogParameter()));
        await UnitOfWork.CommitAsync();                            // ← 消费端自己提交
    }
}
```

`MessageEventHandlerBase`（admin 自有基类，非框架）：

```csharp
public abstract class MessageEventHandlerBase : DotNetCore.CAP.ICapSubscribe
{
    [Autowired] public virtual ILazyServiceProvider LazyServiceProvider { get; set; }
    protected ILogFactory LogFactory => LazyServiceProvider.LazyGetRequiredService<ILogFactory>();
    protected ILog Log => LazyServiceProvider.LazyGetService<ILog>(
        provider => LogFactory?.CreateLog(GetType().FullName) ?? NullLog.Instance);
}
```

它把 `ICapSubscribe` 这个约束**替你实现了**，所以派生类只需关心 `[EventHandler]` 与业务逻辑。

> ⚠ 两点注意：`Task.Delay(5000)` 是仓库里就有的调试遗留；**消费端必须自己 `CommitAsync()`**，CAP 不会帮你提交消费逻辑里的事务。

### 9.3 一条消息再发一条（`TestMessageEventHandler`）

```csharp
[EventHandler(MessageEventConst.TestMessage1)]
public async Task TestMessage1Async(TestMessage message, [FromCap] CapHeader header)
{
    await MessageEventBus.PublishAsync(new TestMessageEvent2(message, message.Send));
    if (message.NeedCommit)
        await UnitOfWork.CommitAsync();
}
```

演示了消费端**再发布**与**条件提交**。注意它把 `message.Send` 透传下去——`Send` 的语义随消息走，不是全局开关。

## 10. 陷阱与防误用清单

### 10.1 陷阱

| # | 陷阱 | 后果 | 规避 |
| --- | --- | --- | --- |
| 1 | `send=false` 但没有工作单元保存 | **消息静默丢失**，无异常无日志 | 方法标 `[UnitOfWork]`，或手工 `CommitAsync()` |
| 2 | 工作单元不认识 CAP（用裸 `UnitOfWorkBase`） | Outbox 失效，消息**在事务外立即发** | 像 `AdminUnitOfWork` 那样重写 `SaveChangesAsync` |
| 3 | 在 `Task.Run` / 新作用域里发布 | 登记到别的 `TransactionActionManager`，**收不到** | 保持同一个 DI 作用域 |
| 4 | 两端消息名不一致 | 消息发出去**没人消费**，堆在 MQ / 出箱表 | 消息名抽成常量类（如 `MessageEventConst`） |
| 5 | 处理器没注册进 DI | CAP 发现不了，**永远不消费** | 参照 `CapModule.LoadEvent` 集中注册 |
| 6 | 同时用 `[CapSubscribe]` 和 `[EventHandler]` | 功能等价，但风格混乱、易漏改一处 | 统一 `[EventHandler]` |
| 7 | 消费端忘了 `CommitAsync()` | 消费逻辑的白写变更丢失 | 消费端显式提交 |
| 8 | 本地事件误用成 `IMessageEventBus` | 凭空多一次数据库写入 + MQ 投递 | 按 §3.4 选型 |
| 9 | 以为领域事件会自动跨服务 | 领域事件派发机制**未接通** | 见 [功能完成度 §7.1](../architecture/功能完成度.md) |
| 10 | `[CapTrace]` 却没有 `[FromCap] CapHeader` 参数 | 拦截器空转，TraceId 不注入 | 要么加参数，要么直接用全局 `CapSubscribeInvoker` |
| 11 | `using Bing.EventBus;` + `using Bing.Events;` | 类型名撞车，**歧义编译失败** | 一律用 `Bing.Events`（遗留包见 [事件与消息 §2](../architecture/事件与消息文档.md)） |

### 10.2 不存在的 API（防误用）

| 常见误写 | 实际 |
| --- | --- |
| `AddEventBus()` | ❌ 不存在。只有 `AddDefaultEventBus()` 与 `AddCapEventBus(...)` |
| `AddDistributedEventBus()` / `IDistributedEventBus` | ❌ 本框架没有。分布式入口是 `IMessageEventBus` |
| `ILocalEventBus` | ⚠ **存在，但在遗留包 `Bing.EventBus` 里**，与现行 `Bing.Events` 的同名类型撞车。新代码不要用 |
| `[CapSubscribe("x")]` | 能用，但本框架统一 `[EventHandler("x")]` |
| `IMessageEventBus.PublishAsync(evt, send: true)` | ❌ 泛型版**没有 `send` 参数**——`Send` 取自事件对象。要么在事件上设 `Send`，要么用原始重载 |
| `bus.PublishAsync("x", data)` 想立即发 | ⚠ 原始版 `send` 默认 `false`，会走事务登记。立即发要写 `send: true` |
| `EventHandlerAttribute.Group` 只能读 | ⚠ `Group` 是继承自 `TopicAttribute` 的**可写属性**，用对象初始化器赋值 |
| `LogContext` / `TraceIdContext` 手工传 TraceId | 发布/消费两端已自动处理，先确认默认链路是否已够 |

## 11. 如何自行复核

本文所有结论都能在源码里复核，最省事的几条命令：

```bash
# ① 谁引用了什么（确认没有偷偷用遗留包）
rg -n "using Bing\.EventBus" --glob "*.cs"

# ② 发布路径：register 与 publish 的分叉
rg -n "TransactionActionManager\.Register" framework/src/Bing.Events

# ③ 提交路径：谁排空登记表（这是 Outbox 的关键）
rg -n "transactionActionManager\.CommitAsync|Create<ITransactionActionManager>" framework/src

# ④ 确认基类工作单元不认识 CAP（本文 §4.2 前提一）
rg -n "ICapPublisher|DotNetCore\.CAP" framework/src/Bing.EntityFrameworkCore

# ⑤ 订阅端特性与分组
rg -n "\[EventHandler\(" modules framework
```

若 ④ 有命中，说明基类工作单元已经接上 CAP，§4.2 前提一需要改写；若 ③ 里出现了除 `UnitOfWorkBase` 与 `AdminUnitOfWork` 之外的调用点，说明还有别的事务排空路径。
