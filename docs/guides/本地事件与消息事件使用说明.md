## 1. 五分钟上手

### 1.1 本地事件（进程内）

```bash
dotnet add package Bing.Events      # 契约在 Bing.Core，实现与注册入口在 Bing.Events
```

```csharp
// ① 注册（Bing.Events.Default.Extensions.AddDefaultEventBus，:17）
services.AddDefaultEventBus();

// ② 事件类：继承 Event（Bing.Events.Event，Bing.Core/Bing/Events/Event.cs:9）
public class OrderCreatedEvent : Event
{
    public Guid OrderId { get; set; }
}

// ③ 处理器：实现 IEventHandler<T>（Bing.Events.Handlers.IEventHandler`1:14）
public class OrderCreatedEventHandler : IEventHandler<OrderCreatedEvent>
{
    public Task HandleAsync(OrderCreatedEvent @event)
    {
        // ... 进程内处理
        return Task.CompletedTask;
    }
}

// ④ ⚠ 处理器必须【手工】注册——AddDefaultEventBus 不扫描任何处理器！
services.AddTransient<IEventHandler<OrderCreatedEvent>, OrderCreatedEventHandler>();

// ⑤ 发布：注入 ISimpleEventBus
public class OrderAppService
{
    private readonly ISimpleEventBus _bus;
    public OrderAppService(ISimpleEventBus bus) => _bus = bus;

    public Task CreateAsync(Guid orderId) => _bus.PublishAsync(new OrderCreatedEvent { OrderId = orderId });
}
```

**第 ④ 步漏掉会怎样**：`GetHandlers<T>()` 返回空集合，`PublishAsync` **静默无操作**——不抛异常、不打日志、事件没人处理。这是本地事件最容易踩的坑。

### 1.2 消息事件（跨服务）

```bash
dotnet add package Bing.Events      # 内含 CAP 8.0.1
```

```csharp
// ① 注册（Bing.Events.Cap.Extensions.AddCapEventBus，:22）
services.AddCapEventBus(o =>
{
    o.UseEntityFramework<AdminUnitOfWork>();   // Outbox 落库
    o.UseDashboard();
    o.FailedRetryCount = 5;
    o.Version = "admin";
    o.UseRabbitMQ(x => { x.HostName = "localhost"; x.UserName = "admin"; x.Password = "***"; });
});

// ② 消息类：继承 MessageEvent<T>（Bing.Events.Messages.MessageEvent`1:52）
public class OrderCreatedMessageEvent : MessageEvent<OrderCreatedMessage>
{
    public OrderCreatedMessageEvent(OrderCreatedMessage data, bool send = true) : base(data)
    {
        Send = send;
        Name = "order.created";        // 主题名 = Name，不是类型名
    }
}

// ③ 订阅端：实现 ICapSubscribe，方法标 [EventHandler]
public class OrderCreatedHandler : ICapSubscribe
{
    [EventHandler("order.created", Group = "order_service")]   // ⚠ 不是 [CapSubscribe]
    public async Task HandleAsync(OrderCreatedMessage e) { /* 🔴 必须幂等 */ }
}

// ④ ⚠ 订阅端也必须【手工】注册（无自动扫描）
services.AddTransient<OrderCreatedHandler>();

// ⑤ 发布：注入 IMessageEventBus
await _bus.PublishAsync(new OrderCreatedMessageEvent(new OrderCreatedMessage { OrderId = id }));
```

**`send` 参数决定可靠性**：`send:true` 立即发（可能"业务回滚了消息已出去"）；`send:false` 延迟到事务提交时发。**深挖见 [分布式事件使用说明 §4](分布式事件使用说明.md)**——那里有三个必须同时成立的前提。

## 2. 定义：两套机制分别是什么

### 2.1 本地事件 = `ISimpleEventBus`

进程内的**同步分发**机制。事件的发布与处理发生在**同一个进程、同一次调用**里。

```csharp
// Bing.Core/Events/ISimpleEventBus.cs:6
public interface ISimpleEventBus : IEventBus { }        // 自身无任何成员

// Bing.Core/Events/IEventBus.cs:6
public interface IEventBus
{
    Task PublishAsync<TEvent>(TEvent @event) where TEvent : IEvent;   // ⚠ 无 CancellationToken
}
```

**`ISimpleEventBus` 就是 `IEventBus` 的别名式契约**——它不新增任何成员。这一点很关键：`AddDefaultEventBus()` 把 `ISimpleEventBus` 和 `IEventBus` **都注册到同一个实现**（`Bing.Events/Default/Extensions.Service.cs:20-21`）。

事件基类（可选，但推荐）：

```csharp
// Bing.Core/Bing/Events/Event.cs:9
public class Event : IEvent
{
    public Event(string eventName = default);   // :21  构造时生成 GUID + 当前本地时间（:23-24）
    public string Id { get; set; }              // :29
    public DateTime Time { get; }               // :32
    public virtual string GetEventName();       // :36  显式名 > EventNameAttribute > 类型全名
}
```

事件名解析规则（`Event.GetEventName()`，`:36-51`）：

1. 构造时传入的 `eventName` 最优先生效；
2. 否则非泛型类型读 `[EventName("xxx")]`（`Bing.Events.EventNameAttribute`，`:9`）；
3. 泛型类型读 `[GenericEventName(...)]`；
4. 都没有则回退到 **`Type.FullName`**。

> ⚠ 本地事件**不使用**这个事件名做路由——路由靠泛型类型 `IEventHandler<TEvent>`。名字只用于诊断与消息事件的主题。

### 2.2 消息事件 = `IMessageEventBus`

跨进程 / 跨服务的事件发布，底层是 **CAP 8.0.1**，消息经**出箱表（Outbox）**落库后由后台投递。

```csharp
// Bing.Core/Events/Messages/IMessageEventBus.cs
public interface IMessageEventBus
{
    // :14 — 强类型重载
    Task PublishAsync<TEvent>(TEvent @event, CancellationToken cancellationToken = default)
        where TEvent : IMessageEvent;

    // :24 — 名称重载（不要求事件对象）
    Task PublishAsync(string name, object data, string callback,
        bool send = false, CancellationToken cancellationToken = default);
}
```

**它与 `IEventBus` 没有任何继承关系**。二者是靠 `Bing.Events.Cap.EventBus` **组合**起来的（见 §7.3 两级发布）。

消息事件基座：

```csharp
// Bing.Core/Events/Messages/IMessageEvent.cs:6
public interface IMessageEvent : IEvent
{
    string Name { get; set; }       // :11  消息名称（即 Topic）
    object Data { get; set; }       // :16  事件数据
    string Callback { get; set; }   // :21  回调名称
    bool Send { get; set; }         // :26  是否立即发送
}

// Bing.Core/Events/Messages/MessageEvent.cs:8
public class MessageEvent : Event, IMessageEvent
{
    public string Name { get; set; }        // :13
    public object Data { get; set; }        // :18
    public string Callback { get; set; }    // :23
    public bool Send { get; set; }          // :28  ⚠ 无初始化器 → 默认 false
}

// :52
public class MessageEvent<T> : MessageEvent
{
    public MessageEvent(T data) { Data = data; }   // :58-61
}
```

> 🔴 **`Send` 默认值是 `false`**（`MessageEvent.cs:28` 无初始化器，`bool` 的 CLR 默认值）。这意味着直接 `new MessageEvent<X>(x)` 而不设 `Send`，走的是**延迟到事务提交时发送**的分支——在事务外调用会**静默丢消息**。
>
> admin 的 `UserLoginMessageEvent` 之所以看起来"默认立即发送"，是**它在自己的构造函数上写了 `bool send = true`**（`modules/admin/src/Bing.Admin.Systems.Domain/Events/UserLoginMessageEvent.cs:18`）——那是子类的参数默认值，**不是基类 `Send` 的默认值**。这两者极易混淆。

## 3. 对照：定义、区别与适用场景

### 3.1 核心对照表

| 维度 | 本地事件 `ISimpleEventBus` | 消息事件 `IMessageEventBus` |
| --- | --- | --- |
| **契约** | `ISimpleEventBus : IEventBus`（`Bing.Core/Events/ISimpleEventBus.cs:6`） | `IMessageEventBus`（不继承 `IEventBus`，`IMessageEventBus.cs:6`） |
| **事件基座** | `IEvent` / `Event` | `IMessageEvent` / `MessageEvent` / `MessageEvent<T>` |
| **处理器契约** | `IEventHandler<TEvent>`（`Bing.Core/Events/Handlers/IEventHandler.cs:14`） | `ICapSubscribe` + `[EventHandler]` 方法 |
| **传递范围** | **进程内**（同一次调用内的对象图） | **跨进程 / 跨服务**（经消息中间件） |
| **底层** | 纯内存，无中间件 | CAP 8.0.1（RabbitMQ / Kafka 等） |
| **持久化** | 无 | **有**——Outbox 表（同库同事务） |
| **可靠投递** | 不适用（同步调用，成败即时可见） | **至少一次**（At-Least-Once，消费端必须幂等） |
| **事务参与** | ❌ 不参与（`Bing.Events/Default/` 下搜 `TransactionActionManager` / `IUnitOfWork` 零引用） | ⚠ 取决于 `Send`：`true` 立即发（事务外）；`false` 登记到事务提交时发 |
| **延迟发布** | ❌ 无此概念 | ✅ `Send=false` 即延迟到提交 |
| **处理器发现** | **手工注册**（无扫描） | **手工注册**（无扫描，`CapModule.cs:77-81` 即范例） |
| **执行方式** | 异步但**串行**，按注册顺序逐个 `await` | 由 CAP 消费线程驱动，可配 `ConsumerThreadCount` / 分组并发 |
| **异常隔离** | ❌ **无 try/catch**——某处理器抛异常会**中断后续处理器**并把异常抛给发布方 | CAP 侧按 `FailedRetryCount` 重试；消费端异常不波及发布方 |
| **延迟量级** | 纳秒~毫秒（同一调用栈内） | 毫秒~秒级（落库 + 投递） |
| **额外成本** | 几乎为零 | **一次数据库写入 + 一次消息投递** |
| **注册入口** | `AddDefaultEventBus()` | `AddCapEventBus(...)` |
| **生命周期** | `ISimpleEventBus` / `IEventBus` = **Singleton** | `IMessageEventBus` / `IEventBus` = **Scoped** |
| **加 `CancellationToken`** | ❌ 契约上没有 | ✅ 两个重载都有 |
| **适用场景** | 同一进 程内的副作用解耦：领域副作用、缓存失效、审计留痕、模块间解耦 | 跨服务一致性、需要"业务成功则消息必达"、异步削峰、集成事件 |
| **不适用场景** | 跨服务（做不到）、需要可靠投递（无持久化） | 纯进程内（白白多一次落库 + 投递）、需要同步拿到结果 |

### 3.2 选型：30 秒决策

```
事件需要被【另一个进程 / 服务】消费吗？
├── 需要 ──→ 消息事件 IMessageEventBus
│            └─ 要求"业务回滚则消息不发"吗？
│               ├── 要求 ──→ Send = false + UoW 接 CAP 事务（⚠ 三前提见分布式篇 §4）
│               └── 不要求 ─→ Send = true（立即发，最简单）
└── 不需要 ─→ 本地事件 ISimpleEventBus
             └─ ⚠ 记得【手工】注册处理器，否则静默无效
```

### 3.3 一句话记忆

> **本地事件 = 方法调用 + 解耦**；**消息事件 = 数据库写入 + 网络投递 + 解耦**。
>
> 用错方向的代价：本地场景误用消息事件 → 每发一次事件多一次落库与投递；跨服务场景误用本地事件 → **另一个进程根本收不到，且不会报错**。

## 4. 本地事件：完整用法

### 4.1 发布链路（逐步、含源码位置）

调用 `ISimpleEventBus.PublishAsync(@event)` 之后：

| 步骤 | 发生了什么 | 位置 |
| --- | --- | --- |
| 1 | 解析所有 `IEventHandler<TEvent>` | `Default/EventBus.cs:31` |
| 2 | 解析动作 → `ServiceLocator.Instance.GetServices<IEventHandler<TEvent>>().ToList()` | `Default/EventHandlerManager.cs:16` |
| 3 | 按顺序 `foreach` 逐个 `await handler.HandleAsync(@event)` | `Default/EventBus.cs:34-39` |
| 4 | 若某处理器抛异常 → **中断循环，异常向上抛给发布方** | 无 try/catch（`:29-40` 整体） |

实现体原文（`Bing.Events/Default/EventBus.cs:29-40`）：

```csharp
public async Task PublishAsync<TEvent>(TEvent @event) where TEvent : IEvent
{
    var handlers = Manager.GetHandlers<TEvent>();
    if (handlers == null)
        return;
    foreach (var handler in handlers)
    {
        if (handler == null)
            continue;
        await handler.HandleAsync(@event);
    }
}
```

### 4.2 行为特征（四条，都与直觉可能不同）

1. **异步但串行**。`await` 逐个执行，不是并行。处理器 A 慢会阻塞处理器 B，也会阻塞发布方。
2. **无异常隔离**。第一个抛异常的处理器会**吃掉后面所有处理器**的执行机会，异常还会传播到发布方——如果发布方在事务里，整个事务可能回滚。
3. **不参与事务**。它只是普通的方法调用。处理器里写库会走当时生效的工作单元/连接，事件总线本身不做任何事务处理。
4. **无延迟发布**。没有 `Send=false` 的本地对应物。要"提交后再做"请自己在提交后调用，或改用消息事件。

### 4.3 处理器解析依赖全局服务定位器 ⚠

`EventHandlerManager` 用的是**全局静态** `ServiceLocator.Instance`，**不是**注入的 `IServiceProvider`：

```csharp
// Bing.Events/Default/EventHandlerManager.cs:16
public List<IEventHandler<TEvent>> GetHandlers<TEvent>() where TEvent : IEvent
    => ServiceLocator.Instance.GetServices<IEventHandler<TEvent>>().ToList();
```

后果有两条：

| 情况 | 结果 |
| --- | --- |
| 没走 `AddBing()` / 模块启动流程（`ServiceLocator` 未被初始化） | `GetServices<T>()` **直接抛异常**（`ServiceLocator.cs:170-173` 无 `IsProviderEnabled` 保护） |
| 走了 `AddBing()` | 正常，但解析走的是**根容器语义**——处理器里拿不到请求作用域的东西时别意外 |

另外，**处理器列表不缓存**，每次发布都实时解析一次。

### 4.4 处理器必须手工注册 ⚠⚠

`AddDefaultEventBus()` 只注册三个服务，**不扫描、不注册任何 `IEventHandler<>`**：

```csharp
// Bing.Events/Default/Extensions.Service.cs:17-23
public static IServiceCollection AddDefaultEventBus(this IServiceCollection services)
{
    services.TryAddSingleton<IEventHandlerManager, EventHandlerManager>();
    services.TryAddSingleton<ISimpleEventBus, EventBus>();
    services.TryAddSingleton<IEventBus, EventBus>();
    return services;
}
```

所以必须自己写：

```csharp
services.AddTransient<IEventHandler<OrderCreatedEvent>, OrderCreatedEventHandler>();
```

**漏写的表现是"静默无操作"**——`GetHandlers` 返回空集合，`foreach` 一次都不进，`PublishAsync` 正常返回。不报错、不打日志。这是本文最重要的一条 ❌。

> 想让注册别那么啰嗦，可以写个自己的扫描辅助，但**框架不提供**——不要臆造 `AddSubscriberAssembly()` 之类的入口（见 §9）。

## 5. 消息事件：使用摘要

> 本节只讲清"是什么、怎么写、参数含义"，**深挖内容一律反链到 [分布式事件使用说明](分布式事件使用说明.md)**，避免两处重复维护。

### 5.1 两个发布重载

| 重载 | 签名 | 用途 |
| --- | --- | --- |
| 强类型 | `PublishAsync<TEvent>(TEvent @event, CancellationToken ct = default) where TEvent : IMessageEvent`（`IMessageEventBus.cs:14`） | 常规用法。`Name` / `Data` / `Callback` / `Send` 全部取自事件对象 |
| 名称式 | `PublishAsync(string name, object data, string callback, bool send = false, CancellationToken ct = default)`（`IMessageEventBus.cs:24`） | 手上没有事件对象时；**`send` 默认 `false`** |

强类型重载的实现只是把它拆开转给名称重载（`Cap/MessageEventBus.cs:52-54`）：

```csharp
public Task PublishAsync<TEvent>(TEvent @event, CancellationToken cancellationToken = default)
    where TEvent : IMessageEvent =>
    PublishAsync(@event.Name, @event.Data, @event.Callback, @event.Send, cancellationToken);
```

**注意**：`Data` 是 `object`，序列化后进消息体；`Callback` 允许为 `null`（实现上给了默认值，接口上不是）。

### 5.2 `Send` 两条分支

```csharp
// Bing.Events/Cap/MessageEventBus.cs:64-77（节选）
public async Task PublishAsync(string name, object data, string callback = null, bool send = false, CancellationToken cancellationToken = default)
{
    var headers = new Dictionary<string, string> { { DotNetCore.CAP.Messages.Headers.CallbackName, callback } };
    InitTraceIdContext(headers);
    if (send)
    {
        await InternalPublishAsync(name, data, headers, callback, cancellationToken);   // 立即发
        return;
    }
    TransactionActionManager.Register(async transaction =>
    {
        await InternalPublishAsync(name, data, headers, callback, cancellationToken);   // 延迟到事务提交
    });
}
```

| `Send` | 行为 | 可靠性 |
| --- | --- | --- |
| `true` | 立刻调 `ICapPublisher.PublishAsync` | 立即发出，**与业务事务无关**——业务回滚消息也已出去 |
| `false`（**默认**） | 登记到 `ITransactionActionManager`，等事务 `CommitAsync` 时执行 | 理论上"业务成功才发"，**但需三个前提同时成立** |

> ⚠ `Send=false` 的三个前提（活动事务 / UoW 调 `TransactionActionManager.CommitAsync` / UoW 认识 CAP 事务）缺一即**静默丢消息**，且**基类 `UnitOfWorkBase` 不感知 CAP 事务**。完整分析见 [分布式事件使用说明 §4.2](分布式事件使用说明.md)。

### 5.3 主题名（Topic）怎么来

**就是 `@event.Name`**（`Cap/MessageEventBus.cs:54`），**不是类型名**。

所以 `Name` 必须显式赋值，否则消息发到一个空主题上：

```csharp
Name = "order.created";                       // 字面量
Name = MessageEventConst.UserLogin;           // 或走常量（admin 做法）
```

admin 的常量表在 `modules/admin/src/Bing.Admin.Infrastructure/MessageEventConst.cs`，分组常量表在 `QueueGroupConst.cs`。

### 5.4 订阅端三件套

```csharp
public class OrderCreatedHandler : ICapSubscribe          // ① CAP 订阅者标记接口
{
    [EventHandler("order.created", Group = "order_service")]   // ② 订阅特性（继承 CAP 的 TopicAttribute）
    public async Task HandleAsync(OrderCreatedMessage e)  // ③ 方法名随意，参数即消息体
    {
        // 🔴 必须幂等——至少一次投递
    }
}
```

| 要素 | 说明 |
| --- | --- |
| `ICapSubscribe` | 实现它 CAP 才会把它当订阅者类 |
| `[EventHandler(name, Group = ...)]` | `Bing.Events.EventHandlerAttribute`（`EventHandlerAttribute.cs:8`），**继承 CAP 的 `TopicAttribute`**，所以 `Group`、`Name` 等参数来自基类。⚠ **不要用 `[CapSubscribe]`** |
| 方法返回值 | `Task`，参数是反序列化后的消息体类型 |
| **注册** | **必须手工**：`services.AddTransient<OrderCreatedHandler>()`（`CapModule.cs:77-81` 是范例）。**框架不扫描订阅者** |
| TraceId | 框架提供 `[CapTrace]`（`Bing.Events.Cap.CapTraceAttribute`）注入消息头；admin 还用自定义 `CapSubscribeInvoker` 在消费端回填 `TraceIdContext`（`CapModule.cs:87-130`） |

### 5.5 消息头

| 常量 | 值 | 位置 |
| --- | --- | --- |
| `Headers.TraceId` | `bing-trace-id` | `Bing.Events/Cap/Headers.cs` |
| CAP 的 `CallbackName` | CAP 内置 | `DotNetCore.CAP.Messages.Headers` |

发布时框架自动写 TraceId（`Cap/MessageEventBus.cs:125-131`，取 `TraceIdContext.Current`）。

## 6. 关键参数与字段说明

### 6.1 事件侧

| 类型 | 成员 | 说明 |
| --- | --- | --- |
| `IEvent` | `Id` / `Time` / `GetEventName()` | 所有事件的基契约 |
| `Event` | `Event(string eventName = default)` | 构造即生成 GUID + `DateTime.Now`（**本地时间**，非 UTC） |
| `EventNameAttribute` | `EventNameAttribute(string name)` | 非泛型事件名；`GetNameOrDefault` 未声明时回退 `Type.FullName` |
| `IEventSession` | `string SessionId` | 可选载荷标记接口，用于串联同一调用链（`Bing.Core/Bing/Events/IEventSession.cs:6`） |
| `IMessageEvent` | `Name` / `Data` / `Callback` / `Send` | 消息事件必需四件套 |
| `MessageEvent<T>` | `MessageEvent(T data)` | 只帮你把 `Data` 赋值；`Name` 与 `Send` 仍需自行设置 |

### 6.2 处理器侧

| 类型 | 成员 | 说明 |
| --- | --- | --- |
| `IEventHandler` | 无成员 | 非泛型标记契约（`IEventHandler.cs:6`） |
| `IEventHandler<TEvent>` | `Task HandleAsync(TEvent @event)` | `TEvent : IEvent`；**无 `CancellationToken`**（`:20`） |
| `IEventHandlerManager` | `List<IEventHandler<TEvent>> GetHandlers<TEvent>()` | 每次实时解析，不缓存（`:13`） |
| `ICapSubscribe` | 无成员 | CAP 订阅者标记（第三方） |
| `[EventHandler]` | `EventHandlerAttribute(string name)`，可用 `Group` | 继承 CAP `TopicAttribute` |

## 7. 常见示例

### 7.1 本地事件：可编译的最小闭环

> ⚠ **仓库内无先例**：全仓 `ISimpleEventBus` **零生产调用**，也**找不到任何真实的 `IEventHandler<T>` 实现类**（生产与测试均无；唯一的测试 `framework/tests/Bing.Tests/Events/EventBusTest.cs:34-38` 那段 `Test_Publish` 是**被注释的**，且用的是 NSubstitute 替身）。
>
> 因此下面这套示例是**本手册构造**的，不是从仓库里摘的。照抄可用，但请知悉它没有经过仓库内验证。

```csharp
using Bing.Events;
using Bing.Events.Handlers;
using Microsoft.Extensions.DependencyInjection;

// ── 1. 事件 ────────────────────────────────────────────────
public class OrderPaidEvent : Event
{
    public Guid OrderId { get; set; }
    public decimal Amount { get; set; }
}

// ── 2. 处理器（可以写多个，会按注册顺序串行执行） ──────────
public class OrderPaidCacheHandler : IEventHandler<OrderPaidEvent>
{
    private readonly ICache _cache;
    public OrderPaidCacheHandler(ICache cache) => _cache = cache;

    public Task HandleAsync(OrderPaidEvent @event)
    {
        _cache.Remove($"order:{@event.OrderId}");
        return Task.CompletedTask;
    }
}

public class OrderPaidAuditHandler : IEventHandler<OrderPaidEvent>
{
    public Task HandleAsync(OrderPaidEvent @event)
    {
        // 记录审计
        return Task.CompletedTask;
    }
}

// ── 3. 注册（⚠ 三个都得写） ────────────────────────────────
services.AddBing();                                  // 让 ServiceLocator 被初始化
services.AddDefaultEventBus();                        // 注册事件总线本身
services.AddTransient<IEventHandler<OrderPaidEvent>, OrderPaidCacheHandler>();
services.AddTransient<IEventHandler<OrderPaidEvent>, OrderPaidAuditHandler>();

// ── 4. 发布 ────────────────────────────────────────────────
public class OrderAppService
{
    private readonly ISimpleEventBus _bus;
    public OrderAppService(ISimpleEventBus bus) => _bus = bus;

    public async Task PayAsync(Guid orderId)
    {
        // ... 业务
        await _bus.PublishAsync(new OrderPaidEvent { OrderId = orderId, Amount = 100m });
    }
}
```

**验证方式**：给处理器打个日志或断点，确认注册那条 `AddTransient` 生效——如果发布后毫无动静，第一件事就是检查它。

### 7.3 两级发布：`IEventBus` 的 CAP 版本

`AddCapEventBus()` 把 `IEventBus` 注册成了另一个实现——`Bing.Events.Cap.EventBus`。它做的是**两级发布**：

```csharp
// Bing.Events/Cap/EventBus.cs:36-42
public async Task PublishAsync<TEvent>(TEvent @event) where TEvent : IEvent
{
    await SimpleEventBus.PublishAsync(@event);                       // ① 先本地分发
    if (!(@event is IMessageEvent messageEvent))
        return;
    await MessageEventBus.PublishAsync(messageEvent);                // ② 实现了 IMessageEvent 才发消息
}
```

**这带来一个清晰语义**：

| 事件类型 | `IEventBus.PublishAsync` 的效果 |
| --- | --- |
| 只实现 `IEvent` | **纯本地**——只走进程内处理器 |
| 实现 `IMessageEvent` | **两级**——先本地分发，再跨服务广播 |

> 想"本地 + 远程都要"，就让事件实现 `IMessageEvent` 并注入 `IEventBus`（而不是分别注入两个总线）。
>
> 注意 `AddDefaultEventBus()` 与 `AddCapEventBus()` 都注册 `IEventBus`，**且都用 `TryAdd*`**——先注册的那个赢。只装 CAP 的宿主注册 `AddCapEventBus()` 就够了，不要两个都调用。

## 8. 常见问题与注意事项

### 8.1 🔴 会导致数据/事件静默丢失的四条

| # | 情况 | 后果 | 位置 |
| --- | --- | --- | --- |
| 1 | 本地事件处理器**没手工注册** | `PublishAsync` **静默无操作**，事件无人处理 | `Default/Extensions.Service.cs:17-23` |
| 2 | 消息事件用默认 `Send=false` 但**不在事务里发** | 登记的动作**无人触发**，消息**静默丢失** | `Cap/MessageEventBus.cs:73` |
| 3 | 消息事件 `Send=false` 且 UoW 是**裸 `UnitOfWorkBase`** | 基类**不感知 CAP 事务**，退化为"立即发送、事务外" | 见 [分布式篇 §4.2](分布式事件使用说明.md) |
| 4 | 消息 `Name` 没赋值 | 发到**空主题**上，订阅端永远收不到 | `Cap/MessageEventBus.cs:54` |

第 1、2 两条的共同特征：**不抛异常、不打日志**。排查时只能靠对照源码。

### 8.2 ⚠ 需要留意的行为

- **本地事件无异常隔离**：第一个抛异常的处理器会阻止后续处理器执行，异常还会传播给发布方——如果在事务里发布，可能导致回滚。
- **本地事件是串行**：单个慢处理器会拖慢整条发布链与发布方。
- **本地事件依赖全局 `ServiceLocator`**：没走模块启动流程会直接抛（`ServiceLocator.cs:170-173`）。
- **本地事件处理器列表不缓存**：每次发布实时解析。
- **`Event.Time` 是 `DateTime.Now`（本地时间）**（`Event.cs:24`），不是 UTC。跨时区排查时注意。
- **`Event.Id` 是 GUID 字符串**，与 CAP 的消息 Id 不是同一个东西（CAP 自己生成消息 Id）。
- **生命周期不一致**：`ISimpleEventBus` 是 Singleton，`IMessageEventBus` 是 Scoped（`Cap/Extensions.Service.cs:24-27`）。别把 Scoped 的东西塞进 Singleton 处理器。

### 8.3 ⚠ 跨服务侧（详见分布式篇）

- **至少一次投递**，消费端必须自己幂等；**框架不提供任何幂等辅助**（搜 `Idempot` / `Inbox` / `Deduplicat` 零命中）。
- **无消费端自动重试配置的框架封装**，用 CAP 的 `FailedRetryCount`。
- **无 CAP 单元测试**（`framework/tests` 下无相关工程）。
- **TraceId 跨消息传递依赖 admin 的自定义 `CapSubscribeInvoker`**（`CapModule.cs:87-130`），自己接 CAP 时需照做，否则消费端日志与发布端对不上。

### 8.4 与领域事件的区别（别混）

| | 本地事件 | 消息事件 | 领域事件 |
| --- | --- | --- | --- |
| 契约 | `IEventHandler<T>` | `ICapSubscribe` + `[EventHandler]` | `IDomainEventHandler<T>` |
| 收集方式 | 直接发布 | 直接发布 | 聚合根 `AddDomainEvent(...)` |
| **当前状态** | 可用（需手工注册） | 可用 | ⛔ **不会派发**（全仓无人调用 `DispatchAsync`） |

**领域事件当前是死的**——不要用 `AddDomainEvent` 传播事件，详见 [功能完成度 §7.1](../architecture/功能完成度.md) 与 [领域建模指南 §5](领域建模指南.md)。

### 8.5 与遗留包的区别（别用错）

`Bing.EventBus` / `Bing.EventBus.Abstractions` 是**遗留包**（`Bing.EventBus.Abstractions` 零引用，`Bing.EventBus` 只被自身测试引用），里面有**同名但无关**的类型：

| 遗留包里的名字 | 现行对应物 |
| --- | --- |
| `ILocalEventBus` / `IDistributedEventBus` | `ISimpleEventBus` / `IMessageEventBus` |
| `ILocalEventHandler<T>` / `IDistributedEventHandler<T>` | `IEventHandler<T>` / `ICapSubscribe` + `[EventHandler]` |
| `LocalEventBusOptions` / `LocalEventHandlerBase` | 无对应物 |

> 🔴 **同时 `using` 两个命名空间会因 `IEventBus` / `IMessageEventBus` 重名而歧义编译失败。**

## 9. 不存在的方法（防误用清单）

下表列出的**全部**在现行包中不存在，写出会编译不过或静默无效：

| 你可能想写 | 实际情况 |
| --- | --- |
| `ISimpleEventBus.PublishAsync(@event, cancellationToken)` | ❌ 契约**没有** `CancellationToken`（`IEventBus.cs:13`） |
| `handler.HandleAsync(@event, cancellationToken)` | ❌ `IEventHandler<T>.HandleAsync` **只有事件参数**（`IEventHandler.cs:20`） |
| `IEventHandler<TEvent, TResult>` | ❌ **不存在**双泛型处理器；本地事件没有返回值概念 |
| `IEventHandlerManager.GetHandlers<T>()` 的缓存开关 | ❌ 不缓存，也没有开关 |
| `ILocalEventHandler<T>` / `ILocalEventBus` / `IDistributedEventBus` / `IDistributedEventHandler<T>` / `LocalEvent` / `EventBase` | ❌ 属**遗留包** `Bing.EventBus*`，新代码不要用 |
| `[CapSubscribe("topic")]` | ❌ 本框架用 **`[EventHandler("topic")]`**（它继承 CAP 的 `TopicAttribute`） |
| `services.AddSubscriberAssembly(...)` / 订阅者自动扫描 | ❌ **不存在**；订阅端与本地处理器都必须手工 `AddTransient` |
| `IMessageEventBus.PublishAsync(new { OrderId = 1 })` | ❌ 泛型约束 `where TEvent : IMessageEvent` **不成立**，普通 DTO 编译不过。要么用名称式重载，要么写一个 `MessageEvent` 子类 |
| `services.AddEventBus()` / `AddSimpleEventBus()` | ❌ 入口是 **`AddDefaultEventBus()`** 与 **`AddCapEventBus(...)`** |
| 框架自有的 CAP `Options` 类型（如 `BingCapOptions`） | ❌ **不存在**；`CapOptions` 来自 CAP 本身 |
| `MessageEvent.Send` 默认 `true` | ❌ 默认 **`false`**（`MessageEvent.cs:28`） |
| 消费端幂等辅助 / 幂等表 | ❌ 框架**不提供**，需自行实现 |
