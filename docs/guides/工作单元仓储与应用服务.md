# 工作单元、仓储与应用服务使用说明

> **适用版本**：框架 `7.0.0`（`version.props`）｜ 目标框架：类库 `netstandard2.0`、Web / 应用 `net6.0`｜ 内容核对：2026-09-18｜ 版本历史见 [../ReleaseNotes.md](../ReleaseNotes.md)

> **一句话定位**：本文回答**「一次写操作从 Controller 到数据库，中间要经过哪几层、每层该怎么写」**。三块内容是同一个写路径上的三个环节，合在一篇讲是因为它们**必须配合使用**——拆开看容易写出「改了但不落库」的代码。
>
> 与既有文档的分工：[领域建模指南](领域建模指南.md) 讲**实体怎么建模**（本篇假设你已经有了实体）；本篇讲**怎么把它存进去**。[架构文档 §8](../architecture/架构文档.md) 讲模块系统，[最佳实践](最佳实践.md) 讲 Do/Don't。
>
> 类型签名以源码为准；若本文与源码冲突，请信任源码并回来修正本文。

## 0. 先记住这 6 条

读完这 6 条再去翻细节，能避开本篇 90% 的坑：

1. **`IUnitOfWork` 只有两个成员**：`Commit()` 和 `CommitAsync()`。没有 `Begin()`、没有 `RollbackAsync()`、没有 `SaveChangesAsync()`。
2. **`IUnitOfWorkManager` 没有 `Begin()`**。「开启一个工作单元」= **从 DI 解析一次 Scoped 工作单元**，它的构造函数会自动把自己登记进 Manager（`UnitOfWorkBase.cs:79 → :85-89`）。
3. **仓储自己不会落库**。`AddAsync` / `UpdateAsync` / `RemoveAsync` 只是往 `DbContext` 的变更追踪里加记录，**必须有人调 `CommitAsync()`**。
4. **手写应用服务若不提交，变更会静默丢失**——不抛异常、不打日志，请求结束 `DbContext` 释放，改动全废。
5. **`AppServiceBase` 不提供工作单元属性**。它只给 `LazyServiceProvider` / `CurrentUser` / `AsyncExecuter` / `LogFactory` / `Log`，**工作单元要自己注入**。
6. **`IUnitOfWorkManager.CommitAsync()` 会提交当前作用域内登记过的「所有」工作单元**，不是某一个。

### 2.1 契约（`Bing.Uow`）

### 2.2 「开启」工作单元的真实含义

框架**没有** `Begin()`。流程是：

```
DI 解析 Scoped 工作单元
   └─ 构造函数 UnitOfWorkBase(DbContextOptions, IServiceProvider)
        └─ RegisterToManager()                    // UnitOfWorkBase.cs:79
             └─ manager.Register(this)            // :88，内部 HashSet 去重
```

所以：**同一个请求内解析多少次都是同一个实例**（Scoped），且只登记一次。

```csharp
// framework/tests/Bing.Uow.Tests/UnitOfWorkManagerTest.cs:85-92
manager.Register(mock1.Object);
manager.Register(mock2.Object);
manager.Commit();                          // 一次提交两个
mock1.Verify(u => u.Commit(), Times.Once);
```

### 2.3 `[UnitOfWork]` 特性：AOP 自动提交

```csharp
// Bing.Ddd.Application.Contracts/Bing/Application/Aspects/UnitOfWorkAttribute.cs:12
public class UnitOfWorkAttribute : InterceptorBase, IScopeInterceptor
{
    public Scope Scope { get; set; } = Scope.Aspect;   // :17 嵌套时仅最外层生效

    public override async Task Invoke(AspectContext context, AspectDelegate next)  // :24
    {
        await next(context);                                          // :26 先执行方法
        var manager = context.ServiceProvider.GetService<IUnitOfWorkManager>();
        if (manager == null) return;
        await manager.CommitAsync();                                  // :30 成功后提交
        if (context.Implementation is ICommitAfter service)
            service.CommitAfter();                                    // :31-32
    }
}
```

**三个必须知道的点**：

- **只对接口代理生效**。这是 AspectCore 动态代理——直接 `new` 服务、或在类内部 `this.Method()` 自调用，**都不会触发**。
- **失败不提交、也不吞异常**。`await next(context)` 若抛异常，直接冒泡，`CommitAsync` 不执行。
- 框架只在 3 处标了它：`ICrudAppService.cs:50`（`CreateAsync`）、`:57`（`UpdateAsync`）、`:80`（`SaveAsync`）。**你自己写的服务默认没有。**

### 2.4 事务与回滚

`IUnitOfWork` **没有公开的 `RollbackAsync`**。回滚只发生在**手工事务分支**里：

```csharp
// EF：Core/UnitOfWorkBase.cs
public int Commit();                 // :369 → SaveChanges()
public Task<int> CommitAsync(ct);    // :400 → SaveChangesAsync(ct)
public override int SaveChanges();   // :430
```

`SaveChanges` 内部（`:430-439`）：

```
SaveChangesBefore()                        // 审计字段、版本号填充
  ↓
取 ITransactionActionManager
  ├─ Count == 0 → base.SaveChanges()      // 无显式事务，EF 自带隐式事务
  └─ Count  > 0 → TransactionCommit()      // :446 手工 BeginTransaction
                    ├─ transactionActionManager.CommitAsync(transaction)   // :465 CAP 出箱
                    ├─ base.SaveChanges()
                    └─ catch → transaction.Rollback()                      // :478
  ↓
SaveChangesAfter()                          // :787
```

**结论**：只有当你发了 CAP 消息（事务动作数 > 0）时，才会走显式事务与回滚路径；否则依赖 EF Core 自身的隐式事务，异常时由 EF 回滚。

### 2.5 只读工作单元

框架**没有** `IReadOnlyUnitOfWork`。admin 里有一对自定义类型，但**注册代码是注释状态**：

## 3. 第二部分：仓储

### 3.1 两套契约：怎么选

| | `IStore<TEntity,TKey>` | `IRepository<TEntity,TKey>` |
| --- | --- | --- |
| 文件 | `Bing.Ddd.Domain/Bing/Data/IStore.cs:17` | `Bing.Ddd.Domain/Bing/Domain/Repositories/IRepository.cs:37` |
| 实体约束 | `TEntity : class, IKey<TKey>` | `class, IAggregateRoot, IKey<TKey>` |
| 查询能力 | 继承 `IQueryStore<,>`（全部） | 同（继承） |
| 写入能力 | `Add/Update/Remove`(+Async) | 同 |
| **`GetUnitOfWork()`** | ❌ 无 | ✅ 有（`IRepository.cs:18`） |
| 自身声明成员 | 12 个写方法 | **0 个** |

> **`IRepository = IStore + GetUnitOfWork()`**，写入能力完全相同。
> 早期文档（含本仓库旧版）写过「本框架没有 `IRepository`」——**那是错的**，它一直存在。选择依据：
> - 实体是**聚合根**且希望在仓储内拿到 UoW → `IRepository`
> - 只是 PO / 非聚合根 → `IStore`
> - `CrudAppServiceBase` **强制要求** `IRepository`

### 3.8 ⚠ 仓储里不要自己提交

admin 全部 14 个仓储中**零处**出现 `CommitAsync` / `SaveChanges`。原因：

- 工作单元是 Scoped，被同请求所有仓储共享（都构造注入同一个 `IUnitOfWork`）；
- 仓储内提前提交会**提前结束该请求的事务**，后续仓储的变更落入新事务，**跨聚合的原子性丢失**；
- 外层再 `CommitAsync` 变成一次空提交（无变更）。

### 4.4 CRUD 基类与自动提交

`ICrudAppService` 上标了 `[UnitOfWork]` 的**只有 3 处**：`CreateAsync`（`:50`）、`UpdateAsync`（`:57`）、`SaveAsync`（`:80`）。

而 **`DeleteAsync` 没有标**（`IDeleteAppService.cs:18`）——因为基类内部自己提交了：

```csharp
// DeleteAppServiceBase.cs:125-136
public virtual async Task DeleteAsync(string ids)
{
    if (string.IsNullOrWhiteSpace(ids)) return;
    var entities = await _store.FindByIdsAsync(ids);
    if (entities?.Count == 0) return;
    DeleteBefore(entities);
    await _store.RemoveAsync(entities);
    await _unitOfWork.CommitAsync();      // :134  ← 基类自己提交
    DeleteAfter(entities);
}
```

⚠ **不要给 `DeleteAsync` 再加 `[UnitOfWork]`**——会变成两次提交（第二次是空提交）。

`ICommitAfter`（`ICommitAfter.cs:6-12`）是提交后的回调钩子，由 `UnitOfWorkAttribute.Invoke:31-32` 调用；`CrudAppServiceBase.CommitAfter() => SaveAfter()`。

## 5. 三者联合：一次写请求的完整链路

```
HTTP POST /api/application
   ↓
ApplicationController.CreateAsync([FromBody] CreateApplicationRequest)
   │   ├─ [Valid] 触发参数校验（AOP）
   │   └─ 调 ApplicationService.CreateAsync(request)
   ↓
ApplicationService.CreateAsync
   ├─ request.MapTo<Application>()            DTO → 实体（AutoMapper）
   ├─ ApplicationRepository.AddAsync(entity)  只登记变更，不落库
   └─ UnitOfWork.CommitAsync()                ← 真正落库
        ↓
   UnitOfWorkBase.CommitAsync (:400) → SaveChangesAsync (:553)
        ├─ SaveChangesBefore()                审计字段、版本号
        ├─ ITransactionActionManager.Count
        │    ├─ 0 → base.SaveChangesAsync()
        │    └─ >0 → 手工事务；CAP 出箱 → base.SaveChangesAsync()
        └─ SaveChangesAfter() (:787) → PublishEventsAsync() (:799 默认空实现)
   ↓
Controller return Success(id)
```

**如果用 `CrudAppServiceBase`**，中间那步 `UnitOfWork.CommitAsync()` 由 `[UnitOfWork]` 拦截器代劳。

## 6. 完整示例（可直接改）

### 6.1 应用服务（admin 真实代码）

```csharp
// modules/admin/src/Bing.Admin.Service/Implements/Systems/ApplicationService.cs
public class ApplicationService : Bing.Application.Services.AppServiceBase, IApplicationService
{
    protected IAdminUnitOfWork UnitOfWork { get; set; }
    protected IApplicationRepository ApplicationRepository { get; set; }

    public ApplicationService( IAdminUnitOfWork unitOfWork,
                               IApplicationRepository applicationRepository )
    {
        UnitOfWork = unitOfWork;
        ApplicationRepository = applicationRepository;
    }

    public async Task<Guid> CreateAsync(CreateApplicationRequest request)
    {
        var entity = request.MapTo<Admin.Systems.Domain.Models.Application>();
        await ValidateCreateAsync(entity);
        entity.Init();
        await ApplicationRepository.AddAsync(entity);
        await UnitOfWork.CommitAsync();
        return entity.Id;
    }

    public async Task UpdateAsync(UpdateApplicationRequest request)
    {
        var entity = await ApplicationRepository.FindAsync(request.Id.ToGuid());
        request.MapTo(entity);
        await ValidateUpdateAsync(entity);
        await ApplicationRepository.UpdateAsync(entity);
        await UnitOfWork.CommitAsync();
    }

    public async Task DeleteAsync(string ids)
    {
        if (string.IsNullOrWhiteSpace(ids)) return;
        var entities = await ApplicationRepository.FindByIdsAsync(ids);
        if (entities?.Count == 0) return;
        await ApplicationRepository.RemoveAsync(entities);
        await UnitOfWork.CommitAsync();
    }
}
```

### 6.2 Controller

```csharp
// modules/admin/src/Bing.Admin/Apis/Systems/ApplicationController.cs
public class ApplicationController : QueryControllerBase<ApplicationDto, ApplicationQuery>
{
    public IApplicationService ApplicationService { get; }
    public IQueryApplicationService QueryApplicationService { get; }

    public ApplicationController(IApplicationService service,
                                 IQueryApplicationService queryService) : base(queryService)
    {
        ApplicationService = service;
        QueryApplicationService = queryService;
    }

    [HttpPost]
    public async Task<IActionResult> CreateAsync([FromBody] CreateApplicationRequest request)
    {
        var id = await ApplicationService.CreateAsync(request);
        return Success(id);
    }

    [HttpPut]
    public async Task<IActionResult> UpdateAsync([FromBody] UpdateApplicationRequest request)
    {
        await ApplicationService.UpdateAsync(request);
        return Success();
    }

    [HttpPost("delete")]
    public async Task<IActionResult> DeleteAsync([FromBody] string ids)
    {
        await ApplicationService.DeleteAsync(ids);
        return Success();
    }
}
```

> 注意 admin 把**写服务**与**查询服务**拆开（`IApplicationService` / `IQueryApplicationService`）——这是它避免应用服务循环依赖的主要手法，值得模仿。

## 7. 防误用清单

| 你可能会写 | 实际情况 |
| --- | --- |
| `unitOfWorkManager.Begin()` | ❌ **没有这个方法**。解析一次 Scoped UoW 即等于开启 |
| `unitOfWork.RollbackAsync()` | ❌ **没有公开方法**。异常时由 EF / 手工事务分支回滚 |
| `unitOfWork.SaveChangesAsync()` | ❌ `IUnitOfWork` 上**没有**。用 `CommitAsync()` |
| `AddMySqlUnitOfWork<MyDbContext>(conn)` | ❌ **要两个泛型参数** `<TService, TImpl>` |
| `AddPostgreSqlUnitOfWork` | ❌ 叫 **`AddPgSqlUnitOfWork`** |
| 以为 `AddAsync` 返回新实体 | ❌ 返回 `Task`。ID 自己生成 |
| 在仓储里 `CommitAsync()` | ❌ 破坏跨聚合原子性，提交统一放应用服务 |
| 手写服务不提交 | ❌ **变更静默丢失，无任何异常** |
| 给 `DeleteAsync` 加 `[UnitOfWork]` | ❌ 基类已内部提交，会双提交 |
| 把 `IStore` 注入单例 | ❌ captive dependency，`IStore` 是 Scoped |
| 依赖自定义全局过滤器自动生效 | ❌ `FilterManager.IsEntityEnabled<T>()` 只认 `ISoftDelete`，须重写 `CreateFilterExpression<T>()` |
| 以为 `AppServiceBase` 自带 UoW | ❌ 只有 `LazyServiceProvider` / `CurrentUser` / `AsyncExecuter` / `Log`，UoW 自己注入 |
| `GetByIdAsync` 用在仓储上 | ❌ 仓储叫 `FindByIdAsync`；`GetByIdAsync` 是应用服务的 |
